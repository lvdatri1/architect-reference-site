## What this framework is

The Zachman Framework is not a methodology — it is a **classification schema**: a 6×6 matrix whose columns are the six interrogatives and whose rows are six levels of reification. Every artefact in an enterprise (a requirements list, a class diagram, an API spec) has a canonical home in one cell. Knowing the matrix tells you **what is missing** before it bites you.

```mermaid
flowchart TB
  R1[Row 1 · Scope · Executive<br/>context: business terms, budgets]
  R2[Row 2 · Business Model · Owner<br/>semantic models, bylaws]
  R3[Row 3 · System Model · Architect<br/>logical models, use cases]
  R4[Row 4 · Technology Model · Engineer<br/>physical designs, APIs, schemas]
  R5[Row 5 · Detailed Representations · Technician<br/>contracts, configs, data definitions]
  R6[Row 6 · Functioning Enterprise<br/>the running system itself]

  R1 --> R2
  R2 --> R3
  R3 --> R4
  R4 --> R5
  R5 --> R6
```

## The six columns

| Column | Interrogative | The question it answers |
| --- | --- | --- |
| Data | **What** | What things exist and their relationships? |
| Function | **How** | How are things transformed and processed? |
| Network | **Where** | Where do the actors and data physically sit? |
| People | **Who** | Who performs each part of the work? |
| Time | **When** | When do events and schedules occur? |
| Motivation | **Why** | Why does the enterprise do this at all (goals, rules)? |

## The full matrix (abbreviated)

| | What | How | Where | Who | When | Why |
| --- | --- | --- | --- | --- | --- | --- |
| **1 · Scope** | things important to the business | business processes | business locations | roles & org units | business events | goals & strategy |
| **2 · Business** | semantic data model | business process model | logistics network | work products & flows | master schedule | business plan |
| **3 · System** | logical data model | application architecture | logical distribution | system / user roles | processing structure | business rule model |
| **4 · Technology** | physical data model | system design | network architecture | human/tech interface | timing / control | rule design |
| **5 · Technical detail** | data definitions | program / module design | network protocols | security & audit | time slicing | rule specifications |
| **6 · Functioning** | deployed data | functioning processes | working network | working organization | actual events | strategy in operation |

## How an architect actually uses it

1. **Start a new initiative in Row 1** — agree the scope cells before any design work.
2. **Refine left-to-right, top-to-bottom**: pick a column (say *What* = data), then reify each row: business terms → logical model → physical schema → deployed database.
3. **Audit for gaps**: for any system, ask "do all 6 columns at Rows 3–4 have artefacts?" Missing *Why/Motivation* artefacts are the classic cause of architecture sign-off fights.
4. **Avoid the trap**: Zachman structures *what exists, slot by slot*. It does not tell you *how to build* — sequencing and method live in TOGAF (see below).

## A caution for testers and reviewers

- The matrix is **system-agnostic**: it describes a space, not a flow. Don’t look for an execution path inside it.
- Two different teams will label the *same* artefact differently — every cell needs an owner and a name.
- The framework does not mention technology stacks, vendors, or tools; those live in row 5, not row 1.
