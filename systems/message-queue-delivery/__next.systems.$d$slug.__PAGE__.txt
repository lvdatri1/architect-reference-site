## What this system is

When an API must not process work in the request-response cycle (sending emails, resizing images, running AI jobs), it writes a **message** to a queue and returns immediately. A **worker** later picks the message up. The price of decoupling is a new failure mode: messages are delivered at least once, so **your handler must be idempotent**.

```mermaid
flowchart LR
  API[API request] -->|persist first| DB[Database<br/>write + idempotency key]
  API -->|enqueue| Q[Message queue]
  Q -->|at-least-once| W[Worker<br/>consumer group]
  W -->|idempotent handler| DONE[Side effect<br/>dedupe → ack]
```

```mermaid
flowchart LR
  A[API writes to DB] --> B[(Database)]
  A -->|enqueue| Q[(Message Queue)]
  Q -->|consume| W[Worker]
  W -->|process + side effects| S[(Email / Image / AI job)]
  W -->|ack| Q
  B --> A
```

## Why “at least once”

Most brokers (SQS, RabbitMQ, Kafka) guarantee at-least-once, not exactly-once:

1. Worker reads message and starts processing a side effect (email sent).
2. Worker crashes before sending the **ack**.
3. Broker sees no ack, assumes failure, and redelivers — or the consumer group rebalances.
4. Same message is processed again → the email is sent twice.

```mermaid
flowchart TD
  M1[Message published] --> W1[Worker A reads]
  W1 -->|side effect: email sent| W1C[Worker A crashes before ACK]
  W1C --> Q2[Broker redelivers]
  Q2 --> W2[Worker B reads again]
  W2 -->|processes same id| SEND[Duplicate side effect!]
```

## How to stay safe

| Technique | What it does |
| --- | --- |
| **Idempotency key** | A stable header like `order-42`; the handler stores processed keys and skips repeats |
| **Outbox pattern** | API writes the business row *and* the message in the same DB transaction; a relay publishes rows from the outbox table — no dual-write race |
| **Dead letter queue (DLQ)** | Messages that fail after N retries move aside for inspection instead of looping forever |

## Tester checklist

- Replay a message manually — the second run must be a no-op.
- Kill a worker mid-handling and confirm redelivery + no partial side effects.
- Verify the DLQ buries poison messages instead of blocking the queue.
- Check ordering guarantees: are you relying on exactly-once ordering you were never promised?
