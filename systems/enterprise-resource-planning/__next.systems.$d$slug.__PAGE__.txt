## What this system is

An ERP is not a single app — it is a **suite of modules** (finance, procurement, manufacturing, inventory, HR) that share **one database and one master-data model**. The value proposition is brutally simple: one record of truth for the whole company, so the sales order the front office sees is the same sales order finance invoices and the warehouse ships. The price is equally simple: you configure within a package's boundaries instead of building your own.

```mermaid
flowchart LR
  MO[Master data - customers, vendors, materials, GL accounts] --> F[Finance]
  MO --> S[Supply chain]
  MO --> M[Manufacturing]
  MO --> P[Procurement]
  MO --> H[Human resources]
```

## The process chains that define ERP

Every module exists to serve one of five end-to-end chains. When someone says "ERP", they mean these five:

| Chain | Starts with | Ends with | Touches |
| --- | --- | --- | --- |
| **Order-to-cash** | Customer order | Cash in the bank | Sales, inventory, logistics, AR, GL |
| **Source-to-pay** | Purchase requisition | Supplier paid | Procurement, receiving, AP, GL |
| **Plan-to-produce** | Demand forecast | Finished goods in stock | Supply planning, manufacturing, inventory |
| **Record-to-report** | Business event | Financial statements | All modules, GL, reporting |
| **Hire-to-retire** | Job requisition | Ex-employee offboarded | HR, payroll, identity |

## Order-to-cash, the canonical chain

```mermaid
flowchart LR
  SO[Sales order] --> AC[Availability check]
  AC --> DL[Delivery / shipping]
  DL --> IN[Invoice to customer]
  IN --> AR[Accounts receivable]
  AR --> GL[General ledger posting]
```

Each arrow is a **state change on shared documents** (order status, delivery status, invoice status). An ERP forces those states to agree; a mess of point-to-point systems lets each step drift. This is why the ERP wins on process integrity and loses on agility — changing the chain means changing the whole suite.

## Config vs code

| Decision | In an ERP | In custom code |
| --- | --- | --- |
| Business rules | Configuration tables, workflows | If/else in a service |
| Changing a rule | Config change, retest the impact | Code change, redeploy |
| The famous trap | Config drift nobody can explain | Customizations that block upgrades |
| Best posture | Tune in-app config, keep custom code minimal and isolated | Only for true differentiators |

The upgrade problem is where architectures are decided: **every customization becomes an upgrade tax**. The architects' rule is *configure, then extend via APIs — don't modify the package*.

## The happy path, step by step

```mermaid
flowchart LR
  SO["Sales order"] -->|validate + ATP| ATP["ATP check"]
  ATP -->|fulfill| Del["Delivery"]
  Del -->|invoice| Inv["Invoice + GL"]
  Inv -->|settle AR| Cash["Payment received"]
```

## Tester checklist

- Chain integrity: create an order, fulfill, invoice, and pay — every downstream document must pick up the upstream state automatically (no manual re-keying).
- Master-data consistency: an address change on the customer master must propagate everywhere it is referenced, without duplicates.
- Kit/multi-location: a single order split across warehouses must reconcile to one invoice and one GL posting.
- Upgrade exposure: confirm no custom code bypasses standard validation posts (fields the suite expects).
