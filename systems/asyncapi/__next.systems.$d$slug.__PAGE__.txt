## What this system is

**AsyncAPI** is the industry-standard specification for describing **event-driven APIs** — the same role OpenAPI plays for REST. It captures:

- **Channels** (topics, queues, exchanges) and direction (publish/subscribe)
- **Message schemas** (payloads, headers, correlations)
- **Protocol bindings** (Kafka, AMQP, MQTT, WebSocket, HTTP, SNS/SQS, Solace, IBM MQ, etc.)
- **Servers** (broker clusters, connection details, security)
- **Components** (reusable schemas, parameters, traits, correlations)

```mermaid
flowchart LR
  Spec[AsyncAPI Document\nYAML/JSON] --> Gen[Code Generators]
  Spec --> Doc[Interactive Docs\nHTML/Markdown]
  Spec --> Gov[Governance\nLinting, CI checks]
  Spec --> Mock[Mock Servers\nTest Consumers]
  Gen --> Prod[Producer SDKs]
  Gen --> Cons[Consumer SDKs]
```

## Why it exists

REST + OpenAPI assumes **request/response**. Modern systems are **event-driven**:

| REST/OpenAPI | AsyncAPI |
|---|---|
| Synchronous, client pulls | Asynchronous, broker pushes |
| One schema per endpoint | Many messages per channel |
| HTTP verbs | Protocol-agnostic (Kafka, AMQP, MQTT, WS, ...) |
| Stateless | Stateful consumers, durable subscriptions |
| `GET /orders` | `orders.created` event on `orders` topic |

AsyncAPI gives you a **single source of truth** for the contract between event producers and consumers — across teams, languages, and brokers.

## Core concepts

```mermaid
flowchart TB
  A[AsyncAPI Document] --> B[info: title, version, contact, license]
  A --> C[servers: broker endpoints + protocol]
  A --> D[channels: topics/queues + messages]
  A --> E[components: schemas, parameters, traits, correlations, securitySchemes]
  A --> F[operations: publish/subscribe + traits]
  A --> G[tags, externalDocs]
```

### Channels

A **channel** is a logical pathway (Kafka topic, RabbitMQ queue, MQTT topic, etc.). Each channel defines:

- `publish` — what a producer may send
- `subscribe` — what a consumer receives
- `parameters` — path/templated parts (e.g., `orders/{region}/{tenant}`)
- `bindings` — protocol-specific metadata (Kafka partition key, MQTT QoS, etc.)

```yaml
channels:
  orders.created:
    description: "Emitted when an order is placed"
    publish:
      operationId: publishOrderCreated
      summary: "Publish new order event"
      message:
        $ref: '#/components/messages/OrderCreated'
    bindings:
      kafka:
        topic: orders.created
        partitions: 12
        replicationFactor: 3
```

### Messages

A **message** defines the payload + headers + correlations:

```yaml
components:
  messages:
    OrderCreated:
      name: OrderCreated
      title: "Order Created Event"
      summary: "Published when a customer places an order"
      contentType: application/json
      payload:
        $ref: '#/components/schemas/Order'
      headers:
        type: object
        properties:
          correlationId:
            type: string
            format: uuid
          causationId:
            type: string
            format: uuid
          traceparent:
            type: string
      bindings:
        kafka:
          key: '{correlationId}'
```

### Schemas

Payloads use **JSON Schema** (draft-07/2019-09 or 2020-12) — same as OpenAPI:

```yaml
components:
  schemas:
    Order:
      type: object
      required: [orderId, customerId, items, totalAmount, currency, placedAt]
      properties:
        orderId:
          type: string
          format: uuid
        customerId:
          type: string
          format: uuid
        items:
          type: array
          items:
            $ref: '#/components/schemas/OrderItem'
        totalAmount:
          type: number
          minimum: 0
        currency:
          type: string
          pattern: '^[A-Z]{3}$'
        placedAt:
          type: string
          format: date-time
```

### Protocol bindings

AsyncAPI is **protocol-agnostic**. Bindings map the abstract channel/message to a concrete protocol:

| Protocol | Binding covers |
|---|---|
| **Kafka** | topic, partitions, replication, key, headers, schema registry |
| **AMQP 0-9-1** | exchange, queue, routingKey, deliveryMode, TTL, dead-letter |
| **MQTT 3/5** | topic, QoS, retain, session expiry, user properties |
| **WebSocket** | subprotocol, headers, ping/pong |
| **HTTP** | webhook POST, CloudEvents mapping |
| **SNS/SQS** | topic ARN, queue URL, FIFO, message group ID |
| **Solace** | topic, queue, TTL, priority, DMQ |
| **IBM MQ** | queue, correlationId, messageId, persistence |

```yaml
servers:
  production:
    url: kafka://kafka.prod.example.com:9092
    protocol: kafka
    description: "Production Kafka cluster"
    security:
      - saslScram: []
    bindings:
      kafka:
        clientId: order-service
        groupId: order-consumer-group
```

### Security

Reuses OpenAPI security schemes + adds protocol-specific:

```yaml
components:
  securitySchemes:
    saslScram:
      type: http
      scheme: bearer
      bearerFormat: SCRAM-SHA-512
    mtls:
      type: http
      scheme: bearer
      description: "Mutual TLS with client certificates"
    apiKey:
      type: apiKey
      in: header
      name: X-API-Key
```

## Versioning strategy

AsyncAPI documents **have a version** (`info.version`), but **event schemas** evolve independently. Best practices:

1. **Schema version in topic** → `orders.v1.created`, `orders.v2.created`
2. **Schema registry** (Confluent, Apicurio, Karapace) — enforce compatibility (BACKWARD, FORWARD, FULL, NONE)
3. **AsyncAPI `components.schemas`** versioned per release; use `x-deprecated` + `deprecation` headers
4. **Consumer-driven contract testing** (Pact, Spring Cloud Contract) — verify consumers before deploying producers

```mermaid
flowchart LR
  V1[orders.v1.created] --> Reg[Schema Registry\nBACKWARD compat]
  V2[orders.v2.created] --> Reg
  Reg --> Prod[Producer deploys v2]
  Prod --> Cons[Consumers migrate\non their schedule]
```

## Governance in CI

```yaml
# .github/workflows/asyncapi.yml
name: AsyncAPI Governance
on: [pull_request]
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: asyncapi/actions/lint@v1
        with:
          files: "asyncapi/**/*.yaml"
  diff:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: asyncapi/actions/diff@v1
        with:
          old: "asyncapi/prod.yaml"
          new: "asyncapi/staging.yaml"
      - run: echo "Breaking changes detected" && exit 1
        if: ${{ steps.diff.outputs.breaking == 'true' }}
```

## Tester checklist

- Validate spec: `asyncapi validate asyncapi.yaml` passes
- Lint: naming conventions, required descriptions, no `any` schemas
- Diff against production: no breaking changes without version bump
- Generate consumer SDK → compile + unit test against schema
- Mock server: `asyncapi mock asyncapi.yaml` → run contract tests
- Verify protocol bindings match actual broker config (Kafka partitions, MQTT QoS, etc.)
- Check `correlationId` / `traceparent` propagation in generated code
- Confirm security schemes match deployed auth (SASL, mTLS, API keys)
