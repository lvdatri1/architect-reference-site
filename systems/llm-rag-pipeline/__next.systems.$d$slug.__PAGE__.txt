## What this system is

RAG (retrieval-augmented generation) lets an LLM answer questions *about your data* without retraining. Documents are split, embedded as vectors, and searched at query time; only the top matches are stuffed into the prompt. This page diagrams the two halves: **ingestion** and **query**.

## 1. Ingestion — build the searchable index

```mermaid
flowchart LR
  D[Source documents] --> S[Chunker]
  S -->|overlapping chunks| E[Embedding model]
  E --> V[(Vector database)]
  V -->|index: HNSW / IVF| I[ANN index]
```

1. **Chunk**: split documents into logical pieces (~500–1000 tokens) with overlap so meaning isn't severed at boundaries.
2. **Embed**: map each chunk to a fixed-size vector (e.g. 1536 dims); similar meaning → nearby points.
3. **Store**: write vectors into a store like pgvector, Pinecone, or Qdrant.
4. **Index**: approximate nearest-neighbor (ANN) indexes trade a tiny accuracy loss for huge speed on millions of vectors.

## 2. Query — answer with evidence

```mermaid
sequenceDiagram
  participant U as User
  participant P as API
  participant E as Embedding model
  participant V as Vector DB
  participant L as LLM

  U->>P: "What is our refund policy?"
  P->>E: embed the question
  P->>V: top-K nearest chunks
  V-->>P: 5 candidate passages + scores
  P->>L: prompt: system rules + passages + question
  L-->>P: grounded answer
  P-->>U: answer + citations
```

## Why the "retrieval" part is where systems die

The model is the easy 50%. Retrieval quality decides everything:

- **Chunk size trade-off**: too small → missing context; too large → diluted relevance.
- **Metadata filters**: `source = support/2024` constrains search and controls the price of retrieval.
- **Re-ranking**: a second, heavier model re-orders the top-N to fix embedding-only misses.

```mermaid
flowchart LR
    Q[User question] --> E[Embed question]
    Q -- terms --> K[BM25 keyword search]
    E -- query vector --> V[Vector search - top-K]
    V -- top-K --> HY[Hybrid merge]
    K -- top-K --> HY
    HY -- candidates --> R[Re-ranker]
    R -- 5 passages --> L[LLM - prompt + evidence]
```

## Why hybrid search exists

Embeddings are great at meaning and bad at exact matches (“CVE-2024-1234”). Keyword search is the opposite. **Hybrid retrieval** merges both, then a **re-ranker** picks the final passages — this is the pattern most production systems converge on.

## Tester checklist

- **Grounding**: ask something only in your docs — the answer must cite them, not hallucinate.
- **Blast radius**: inject an adversarial passage into the top-K — does the model follow a competing instruction? (Prompt injection.)
- **Latency budget**: every retrieval stage adds time; measure p95 against your SLO.
- **Version skew**: re-embedding after a doc change must update *all* chunks of that doc (chunk ids → doc ids).
