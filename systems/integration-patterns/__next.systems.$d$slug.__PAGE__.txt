## What this system is

Every integration in your estate is one of a small family of patterns. Gregor Hohpe's "Enterprise Integration Patterns" named the classical four; event streaming and webhooks modernized them. When an integration frustrates you ("why is nothing happening?", "did the file arrive?"), the root cause is almost always a pattern-property mismatch — you built a file-transfer guarantor that needs messaging's delivery semantics.

## The five families

| Pattern | Coupling | Delivery semantics | Latency | Classic use |
| --- | --- | --- | --- | --- |
| **File transfer** | Loose (files) | At-least-once by poll+checksum | Batch (minutes-hours) | ERP/legacy exchange, bank statements |
| **Shared database** | Tightest (schema shared) | In DB, locks copied | Real-time-ish | Internal monoliths, reporting |
| **RPC / streaming RPC** | Tight (interface shared) | At-most-once; caller handles the rest | Lowest | Service APIs, gRPC, sync calls |
| **Messaging** | Loose (payload contract) | At-least-once + retries + DLQ | Milliseconds | Work queues, fan-out |
| **Shared event stream** | Very loose (schema-as-weak-contract) | At-least-once + replay | Milliseconds-Batch | Pub/sub, CDC, event sourcing |

## How to choose

```mermaid
flowchart TD
  A[Need to connect two systems?] --> B{Who drives it?}
  B -->|Human scheduled batch| C[File transfer / SFTP]
  B -->|System triggers in real time| D{Are both sides alive?}
  D -->|Yes, both online| E{RPC / webhooks}
  D -->|No / need durability| F{Messaging}
  F --> G{One consumer or many?}
  G -->|One| H[Work queue / message]
  G -->|Many| I[Pub-sub / topic]
  B -->|Keep DBs in sync automatically| J[Change data capture]
```

## The two axes that explain most failures

- **Synchronous vs asynchronous**: RPC/webhooks are sync — the caller *waits* and must handle failure itself. Messaging and CDC are async — nothing waits, but "eventually" means retries, ordering caveats, and idempotency.
- **Push vs pull**: webhooks push (source owns delivery, hard to retrofit), files and queues pull or poll. If a receiver is offline for hours, only pull/queue patterns survive without data loss.

```mermaid
flowchart LR
  subgraph Sync["Synchronous (caller waits)"]
    A[RPC / gRPC]
    B[Rest API]
    C[Webhook]
  end
  subgraph Async["Asynchronous (eventually)"]
    D[Message queue]
    E[Pub/Sub topic]
    F[File drop folder]
    G[CDC stream]
  end
```

## Trade-off cheat sheet

| I want… | Pattern to reach for | Guarantee I must accept |
| --- | --- | --- |
| Immediate response, simple ops | RPC/webhook | Duplicates possible, caller owns retries |
| Durable, exactly-one-ish work | Message queue + idempotency | At-least-once, ordering per key |
| Many consumers see everything | Pub/Sub | Ordering per partition, replay responsibility |
| No app changes | CDC | Schema events, log footprint |
| Auditable, human-greppable | File transfer | Batch latency, folder drift |
