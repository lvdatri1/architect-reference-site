## What this system is

A **business process** is the sequence of activities, decisions, and hand-offs that turns an input into an outcome the business cares about — *a lead becomes a signed order*, *a goods receipt becomes a payment*. **Business process management (BPM)** is the discipline of making those processes *visible, measured, and improvable*: you cannot improve a process you cannot see.

```mermaid
flowchart LR
  M[Model the process] --> A[Automate or enable]
  A --> R[Run - events + records]
  R --> S[Measure - KPIs]
  S --> I[Improve - redesign]
  I --> M
```

A process is **not** the software that supports it. The process is the shared understanding of *who does what, when, and what if*; the software (a CRM, an ERP, an approval engine) is one possible mechanism for carrying it out. When the process and the system disagree, you have a live process bug.

## The anatomy of a process

Every process can be decomposed into a few load-bearing elements:

| Element | Question it answers | Failure mode |
| --- | --- | --- |
| **Activity** | What gets done? | Activity with no named owner |
| **Event** | What starts/stops it? | Process waiting on an event nobody publishes |
| **Decision** | Which branch do we take? | Rules hidden in someone's head |
| **Actor / role** | Who does it? | Hand-off to a role that has no inbox |
| **SLA / deadline** | How long is acceptable? | Deadline with no escalation |
| **Data / artifact** | What passes between steps? | "We always knew it" — but no system knows it |

The **flow** is the skeleton; the **decision rules** are the organs; the **escalation** is the immune system. A process modeled without deadlines and escalations is a diagram, not a process.

## Process decomposition

```mermaid
flowchart TB
  L1[Level 1 - value chain<br/>e.g. order-to-cash] --> L2a[Level 2 - process<br/>e.g. credit check]
  L1 --> L2b[Level 2 - process<br/>e.g. warehouse dispatch]
  L2a --> L3a[Level 3 - sub-process / task<br/>e.g. run credit report]
  L2a --> L3b[Level 3 - decision<br/>e.g. approve / reject]
  L3b --> L4[Level 4 - system step<br/>e.g. ERP approval workflow]
```

Decomposition answers a practical question: **who owns which level?** Executives own the value chain, process owners own level 2, teams own tasks, and system owners own the automated steps. The classic failure is modeling everything at one level — too abstract for the implementer, too granular for the decision-maker.

## The process lifecycle

1. **Model** — draw the current (as-is) process in BPMN, with swimlanes per role and explicit decisions. If a step has no swimlane, it has no owner.
2. **Automate or enable** — decide what the system does (rules, approvals, notifications) versus what a human must still judge. Over-automating a human-judgment step is how you build a bad workflow.
3. **Run** — the process executes; every step leaves a *process record* (who did it, when, how long) so the process is audit-able.
4. **Measure** — KPIs: cycle time, hand-off count, first-pass yield, wait time between steps. *The process record is the source of the KPI.*
5. **Improve** — the measured pain points get redesigned; the new process is modeled, automated, and run again.

## Where the process meets the system

```mermaid
flowchart LR
  Event[Business event - e.g. order placed] -->|triggers| Rules[Decision rules + policy]
  Rules -->|automate the routine| System[Workflow engine / ERP]
  Rules -->|route the judgement| Human[Human task - approvals, judgment]
  System -->|step executed| Record[Process record - audit trail]
  Human -->|decision logged| Record
  Record -->|aggregate| KPI[KPIs - cycle time, yield]
```

The integration pattern to teach: **the business event starts the process, the rules decide the route, the system automates the routine steps, the humans handle the judgment, and every step lands in a process record.** The record is what turns "we think it works" into "we measured it."

## Business Process Model and Notation (BPMN)

BPMN is the drawing language of processes: **events** (circles), **activities** (rounded rectangles), **gateways** (diamonds), **swimlanes** (who does what). Its superpower is precision — a BPMN diagram can be so unambiguous that an engine can *execute* it directly (BPMN is both diagram and code). The pitfalls are the same as any modeling:

- Model **decisions as gateways with named conditions**, not as arrows with vibes.
- Model **exceptions explicitly** — "what if the vendor rejects?" is a normal path, not an edge case.
- Keep the diagram **executable-or-explainable**: if an engine would get stuck, a human will too.

## Tester checklist

- Swimlane audit: walk the as-is process and confirm every activity sits in a named role's lane with a named owner.
- Exception drill: run the process with the rejection / error path (vendor rejects, customer cancels) and confirm the exception route exists and escalates.
- KPI provenance: pick one measured KPI and trace it back to specific fields in the process record — it must be computable, not asserted.
- Decision honesty: check that every gateway condition is explicit enough that a new analyst and the workflow engine would both pick the same branch.
- Hand-off latency: measure wait time between two swimlanes — the place most processes actually lose their time.
