## What this system is

Virtualization lets one physical server run many isolated operating systems by interposing a layer — the **hypervisor** — that shares and protects the hardware. Cloud computing runs on it: every EC2/Azure VM you rent is a guest OS inside a hypervisor on a machine someone else owns. The idea is three layers: **hardware → hypervisor → guest OSes**, each believing it owns the machine.

```mermaid
flowchart TB
  H[Physical server - CPU / RAM / disk / NIC]
  subgraph HV["Hypervisor (Type 1)"]
    V1[VM 1 - guest OS + app]
    V2[VM 2 - guest OS + app]
    V3["VM 3 - guest OS + app (…)"]
  end
  H --> HV
  V1 -.- I1[Isolated: own kernel, own IPs, own filesystem]
  V2 -.- I2[Isolated even from sibling VMs]
```

The crucial property is **isolation**: a guest can't read another guest's memory or disk, can crash and be restarted without affecting its neighbors, and each carries its own full OS — a boundary that's stronger than containers' but heavier to run.

## Type 1 vs Type 2: where the hypervisor lives

```mermaid
flowchart TB
  subgraph T1["Type 1 - bare metal (the cloud)"]
    A[Hypervisor - KVM / ESXi / Hyper-V<br/>runs directly on the hardware]
  end
  subgraph T2["Type 2 - hosted (developer laptops)"]
    B[Host OS] --> C[Hypervisor app - VirtualBox / VMware Workstation / Parallels]
  end
  HW[Physical hardware] --> T1
  HW --> T2
```

- **Type 1** runs directly on the silicon with no host OS beneath it — minuscule overhead, near-native performance, and it's what AWS, Azure, and VMware vSphere use. Think of it as the OS of the machine's *management* while guests are the *workloads*.
- **Type 2** runs as an application on top of a regular OS (macOS → Parallels, Windows → Hyper-V/VMware Workstation). Everything the guest does goes through the host OS first — slower, but free to install and perfect for local dev.

The rule: **Type 1 for anything that must be fast or served, Type 2 for your laptop.**

## CPU, memory, and the magic term: overcommit

```mermaid
flowchart LR
  P[Physical host - 64 cores / 256 GiB RAM] --> N[16 guest VMs]
  N --> U1[vCPU per VM × cores used &lt; physical cores?]
  N --> U2[Scheduled - not dedicated]
```

- Every guest exposes **vCPUs** — most allocate MORE vCPU and RAM than the host physically has. That's **overcommit**, and it works because guests rarely all peak at once; the hypervisor schedules vCPUs onto physical cores just like an OS schedules threads.
- RAM overcommit is riskier than CPU: the hypervisor typically needs a memory balloon or dedup to reclaim pages, and sudden global peaks cause the cloud's "insufficient capacity" or performance collapse. Cap total guest RAM below physical RAM and you buy safety at the cost of density.
- **NUMA** (which RAM is attached to which CPU socket) still leaks through at scale — good hypervisors pin vCPUs to the right socket, or guest performance mysteriously halves.

## Storage and networking for guests

```mermaid
flowchart LR
  subgraph Net["Virtual networking"]
    N1["A virtual NIC per guest"]
    N2["vSwitch - bridges / NAT / isolated VLANs"]
    N3["Same L2 semantics as physical"]
  end
  subgraph Disk["Virtual disks"]
    D1[Thin vs thick provisioning]
    D2[Snapshots - fast rollback]
    D3[Host RAID / storage pool underneath]
  end
```

- Guests see a **virtual NIC** plugged into a **virtual switch**; whether it's bridged (like a real NIC), NATted (host forwards), or on an isolated VLAN is invisible to the guest — and exactly how cloud VPCs present "your own" network.
- Virtual disks are just big files: **thick** preallocates (predictable, slower to create), **thin** grows on demand (compact, but can surprise you when a full host runs out). **Snapshots** let you roll back a guest — the killer feature for upgrades and patch testing.
- The high-level insight for architects: a hypervisor adds up-front overhead (cores, RAM, I/O) but buys tremendous *manageability* — clone, snapshot, migrate, rebuild in minutes instead of days.

## VM vs container: two kinds of isolation

| | Virtual machine | Container |
| --- | --- | --- |
| Isolation boundary | Full kernel per guest | Shared host kernel, namespaces |
| Startup | Minutes (boot a whole OS) | Milliseconds |
| Footprint | GBs (full OS) | MBs (one app + libs) |
| Overhead | ~small but real CPU/RAM per guest | Near-zero per container |
| Security boundary | Strong (kernel boundary) | Weaker (same kernel) — needs hardening |
| Portability | Same hypervisor family | Anywhere with a container runtime |

They're complementary, not rival: Kubernetes runs *on* VMs in every major cloud. The **VM is the unit of frontier security and ownership; the container is the unit of application packaging and scale.**

## Tester checklist

- **Isolation drill**: on one host, cause memory or I/O pressure in a guest and verify siblings stay stable — that's the hypervisor's headline promise.
- **Overcommit test**: prove your peak-load profile is genuinely below the host's physical capacity; don't discover it in an outage.
- **Snapshot discipline**: snapshot before patching, roll back, and verify the restored guest is exactly the pre-patch state (clock, stateful apps).
- **Pin/placement**: confirm vCPUs stay on the same NUMA node for latency-sensitive guests, or the perf graph will betray you.
- **Networking semantics**: verify guest MACs/IPs don't collide across vSwitches and that isolation (bridged vs VLAN) actually blocks what you think it blocks.
