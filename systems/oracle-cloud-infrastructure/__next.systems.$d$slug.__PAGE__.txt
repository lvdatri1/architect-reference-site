## What this system is

Oracle Cloud Infrastructure (OCI) is Oracle's public cloud — its reason to exist is running **Oracle database**. Where AWS and Azure are generic clouds, OCI is the only one where a managed Oracle database (Autonomous Database / Exadata) is a first-class native service rather than a port. The rest of OCI (VCNs, compute, storage, IAM) exists to support that core use case — and increasingly to host generic workloads too.

Everything in OCI hangs off **tenancy → compartment** organization. You don't deploy "into a region" so much as "into a compartment inside your tenancy," with IAM policies deciding who can touch which compartment tree.

## The OCI mental model

| Concept | What it is | The closest AWS/Azure idea |
| --- | --- | --- |
| **Tenancy** | Your root isolation boundary in OCI | AWS account / Azure subscription root |
| **Compartment** | Logical container for resources; IAM grants access to compartments | Resource group / organizational unit |
| **Region + AD** | Region = data center geography; availability domains inside | Region / availability zone |
| **VCN** | Your virtual network, sliced into subnets | VPC / VNet |
| **OCI IAM** | Policies (`allow group X to manage ... in compartment Y`) that are *statement-based*, not role-based | IAM policies (permission-based) / Azure RBAC |
| **OCI Object Storage** | Buckets with namespaces; `oci s3`-compatible API | S3 / Blob storage |

The big OCI difference: **IAM is statement-based, written in plain language.** You write `Allow group app_team to manage all-resources in compartment app-prod` — it reads like a sentence and composes from the root. The failure mode of this is overly-permissive sentences written once and copied forever.

## Compartments and IAM: the tree you govern

```mermaid
flowchart TB
  Root[Tenancy root] --> C1[Compartment: prod]
  C1 --> C1a[Compartment: app]
  C1 --> C1b[Compartment: data - Autonomous DB pool]
  Root --> C2[Compartment: non-prod]
  C2 --> C2a[Compartment: sandbox]
  Policy[allow group app_dev manage all-resources<br/>in compartment app] --> C1a
```

Policies attach to compartments; resources inherit placement inside a compartment's tree. Rules of thumb: **one compartment per cost owner**, never put prod and non-prod under the same grant, and put the database pool in its own compartment so "manage app" never means "manage the DB."

## The real OCI: running Oracle database natively

| Offering | What it is | When you reach for it |
| --- | --- | --- |
| **Autonomous Database (ADB-S)** | Fully managed Oracle DB: auto-patching, auto-backup, auto-scaling, tooling for DBAs is gone | "We want Oracle without hiring a DBA team" — the flagship |
| **DB Systems (RAC)** | Classic Exadata/DB on managed VMs, full RAC, upgrade windows you control | Lift-and-shift of an existing Oracle estate |
| **Exadata Cloud Service** | Oracle's engineered hardware as a service (RAC + flash + storage servers) | Heavy OLTP that needs the engineered stack |
| **Autonomous JSON / NoSQL** | Different data models on the same infra | Document or key-value needs |

The architectural point: **Autonomous DB removes the DBA doing the same boring tasks** — patching, backup, tuning knobs are serverless behaviors, not jobs. But what it doesn't remove is *design*: schema, indexing, partitioning, RAC topology, and capacity still live in the same [Oracle database architecture](../oracle-database-ecosystem) conversation. "Autonomous" controls the machinery, not your data model.

## Networking: VCNs, subnets, and getting Oracle DB privacy

```mermaid
flowchart TB
  VCN[VCN 10.0.0.0/16] --> SubPub[Public subnet - LB]
  VCN --> SubPriv[Private subnet - compute]
  VCN --> SubData[Private subnet - DB subnet]
  SubPub --> RT[Route table: IGW for public only]
  SubPriv --> NSG[Network security groups / SL]
  SubData --> P[Peering / IPSec to on-prem]
```

- **Public vs private subnets** behave like AWS: public route table with an internet gateway; private subnets with no internet route, egress via NAT.
- **Security lists** (stateless-ish rules per subnet) and **NSGs** (stateful, per-NIC) both exist; the newer NSG model is the one to build on.
- **DB should be in a private subnet** reached over private IPs — the same lesson as every other cloud. The private line to Autonomous DB or the on-prem-to-OCI tunnel is where your database traffic should live.

## The mistake repeatedly remembered

- Exposing the database subnet to the internet because "it's only control plane." (It's not.)
- Writing one enormous `allow group engineers manage all-resources in tenancy` policy and calling it simpler.
- Cross-cloud hybrid: Oracle DB landing in OCI while its direct consumers live in AWS/Azure with no private interconnect — the latency and egress bill write the memo.
- Treating Autonomous DB as "no design needed" — it's fully managed, not self-organizing.

## Tester checklist

- Validate compartment isolation: an app-role principal attempting to `create database` in the `data` compartment must be denied by policy, not by a friendly guard.
- On Autonomous DB: run a restore to a point-in-time (flashback) and time it; confirm backups are automatic and the restore target is a fresh instance.
- Confirm DB traffic never crosses a public endpoint: check the app's connection string and route table for a private path only.
- Expose an NSG mis-rule deliberately and verify the security list / NSG actually blocks it (rules are evaluated, don't assume).
- Scale a compute shape and an ADB service level and watch cost change — know what auto-scaling is and is not doing.
