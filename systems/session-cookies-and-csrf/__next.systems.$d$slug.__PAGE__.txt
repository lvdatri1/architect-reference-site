## What this system is

Cookies are the web's default "remember me". The browser stores a **session id** in a cookie and sends it on every request to your origin. That is powerful — and it opens the door to **CSRF**: a *different* site (or an HTML email) that makes the *same-origin-trusted* browser send a forged request on your victim's behalf.

```mermaid
flowchart LR
  A[User logs in] --> B[Server stores session<br/>id  →  user_id]
  B -->|Set-Cookie: session_id<br/>HttpOnly, Secure, SameSite| C[Browser cookie jar]
  C -->|every request carries cookie| D[Your API]
```

## The cookie flags that matter

| Flag | Effect | If you skip it |
| --- | --- | --- |
| `HttpOnly` | JS can't read the cookie | Any XSS reads the session cookie and hijacks accounts |
| `Secure` | Only sent over HTTPS | Cookie travels in cleartext over HTTP |
| `SameSite=Lax` | Blocks cross-site sends except top-level navigation | CSRF succeeds silently |
| `SameSite=Strict` | Blocks even top-level cross-site sends | Slightly worse UX (broken external links while logged-in) |
| `Path`/`Domain` | Restricts where it's sent | Cookie sent to unintended host → leak |

## The CSRF attack, step by step

```mermaid
sequenceDiagram
  participant V as Victim's browser
  participant A as Attacker's page
  participant B as Victim's banking app

  V->>B: login (gets session cookie)
  V->>A: visits evil.example (cookie NOT shared — but that doesn't matter!)
  A->>V: <img src="https://bank.com/transfer?to=attacker&amount=9999">
  V->>B: GET transfer... with session_id cookie (auto-sent!)
  B-->>V: transfers money
```

The mean trick: the attacker's site never *reads* your cookie (and doesn't need to). The **browser** attaches the cookie to the request because it's going to `bank.com` — the victim is logged in, so the forged request is "authenticated".

## Defenses, in the order to apply them

1. **`SameSite=Lax`** (default in modern browsers) — kills the common cross-site POST form/image CSRF.
2. **CSRF tokens** — a per-session unpredictable token the server requires in forms / `X-CSRF-Token` fetch headers; the attacker's page can't read or forge it.
3. **`Origin` / `Host` header checks** on state-changing endpoints — cheap extra layer.
4. **Double-submit cookie** — server expects the CSRF value both in a cookie and a header; they must match, so a foreign page can't supply both.

## Tester checklist

- Confirm `HttpOnly` + `Secure` + `SameSite=Lax` are set on session cookies.
- From a *second* origin, attempt POST / transfer-type endpoints — they must fail without a valid CSRF token.
- Confirm state-changing endpoints (not just GET) are CSRF-protected.
- Check logout actually invalidates the session server-side (cookie delete is not enough).
