## What this system is

**Kubernetes (K8s)** is a container-orchestration platform: it takes the containers you built with Docker and runs them reliably at scale — scheduling work onto machines, restarting what fails, scaling what's hot, and connecting the pieces by name. The model has two halves: the **control plane** (the brain: API server, scheduler, controllers) and the **worker nodes** (where containers actually run under a runtime).

```mermaid
flowchart LR
    CP[Control plane - API, scheduler, controllers] --> API[API server]
    API --> ETCD[(etcd - the source of truth)]
    API --> K[Kubelet on each worker node]
    K --> POD1[Pod - app containers]
    K --> POD2[Pod]
    K --> POD3[Pod]
    POD1 --> LB[Service - stable DNS name]
    POD2 --> LB
    POD3 --> LB
```

## Pods and how work is grouped

| Concept | What it is | The mental model |
| --- | --- | --- |
| **Pod** | One or more containers sharing a network namespace | The smallest deployable unit — a *sidecar* is a second container in the same pod |
| **Deployment** | The desired-state controller for stateless pods (replicas, rollouts, rollbacks) | "Always keep 3 of these pods up" |
| **Service** | A stable DNS name + load balancer in front of a pod set | Pods die; the service name does not |
| **ConfigMap / Secrets** | Config (and sensitive config) injected as env or volume | Config is data, not a rebuild — see [secrets](../secrets-certificates-and-pki) |
| **Namespace** | Logical partition for teams, environments, or isolation | A cut of the cluster, not a security boundary |

The core promise is **declarative operation**: you write the *desired state* (image, replicas, resource limits, probes) and controllers converge reality toward it. That convergence, not the deployment UI, is the real product — it's how a "Moron wipe" of a node self-heals the workload elsewhere.

## The reconciliation loop, end to end

```mermaid
sequenceDiagram
    participant U as Desired state YAML - kubectl apply
    participant A as API server - validates and persists
    participant E as etcd - source of truth
    participant S as Scheduler - places pods on nodes
    participant K as Kubelet - runs and watches pods
    participant H as Ready + serving - through Service

    U->>A: kubectl apply desired state
    A->>E: write
    A->>S: watch for work
    S->>K: bind pod
    K-->>H: reports ready + serving
```

Physically, these reconcile as: controllers keep *current state* equal to *desired state*. If a pod crashes or a node dies, the ReplicaSet control loop notices and spins a replacement. That's the whole trick — and it's why the failures you design Kubernetes for are different: **you now handle pod-restart policies, not process-monitor scripts.**

## When Kubernetes is the right (and wrong) answer

| Choose Kubernetes when | Reach for something simpler when |
| --- | --- |
| Workloads benefit from node pooling, autoscaling, and multi-region placement | A handful of long-running services and heavy ops free for them |
| You already have containers and want self-healing ops | You want a single HTTP service with no rolling/canary needs — see [containers vs plain](../dockerizing-applications) |
| The team has platform skills to own the control plane | Small team — a managed container service with a slick UI is safer |
| Compliance wants reproducible, codeless-image, immutable deploys | You need a super simple stateful datastore with no K8s operator |

The honest advice: **Kubernetes adds an operating system around your containers.** Clusters need a [CI/CD pipeline](../ci-cd-pipelines) to build them, [observability](../monitoring-and-observability) to survive them, and a team that treats the platform as a product. The most common failure on a greenfield Golang or GPT app isn't features — it's adopting K8s before you have (a) verified images, (b) health/liveness probes, and (c) resource requests+limits. Without probes and limits, the scheduler and the autoscaler are flying blind.

## Tester checklist

- Desired-state parity: scale a deployment to N and kill a persistent pod — the controller converges back to N within the SLA, with the replacement reporting Ready.
- Limits are real: a pod exceeding its memory `limits` is restarted (OOMKill) and evicted rather than crashing its node, and CPU `requests` shows in scheduling decisions.
- Probe honesty: a pod whose app is broken but process alive is taken out of the Service (readiness failure) without killing the pod or re-populating it.
- Team continuity: an upgrade of the control plane is rolled (not blown) — the API server stays available and existing workloads are unaffected.
- Secret hygiene: a secret injected via a [Secret object](../secrets-certificates-and-pki) is never visible in pod metadata/env dumps and rotates without a full redeploy path that leaks at any step.
- Security boundary: a namespace compromise doesn't become a cluster compromise — RBAC/NetworkPolicies are enforced as claimed, and a privileged pod is denied where it should be.
- Rollout control: a bad image triggers a rollout that rolls back cleanly to the last-good ReplicaSet, and no traffic loss window is exceeded by the deployment strategy.
