RESTful API design

Resources, verbs, and status codes done right: how to design URLs and semantics that stay consistent, versionable, and cacheable — and the versioning, pagination, and error-shape decisions that ship with them.

DeveloperBackendFrontendTester#api#architecture#performance

What this system is

REST (Representational State Transfer) is a style, not a standard: the idea that your API is a set of resources (nouns) manipulated with a small set of verbs (HTTP methods), where each response carries enough to know what's next, and caching is an explicit part of the protocol. A well-designed REST API is boring in the best way — predictable, consistent, and learnable in an afternoon.

Resources and verbs: the core contract

MethodSemanticsIdempotent?Typical status
GETRead a resource or collectionYes200
POSTCreate a new resource (or trigger an action)No201 + Location
PUTReplace a resource fullyYes200 / 204
PATCHPartial update — send only changed fieldsNo200 / 204
DELETERemove a resourceYes204

Rules that prevent most design drift:

  • URLs are nouns, never verbs. POST /users/{id}/send is a smell; a verb usually hides a missing resource (maybe POST /users/{id}/email-verifications is what you meant).
  • Plural collections, singular items: GET /users, GET /users/{id}. Consistency beats cleverness.
  • Nested only for true sub-resources: GET /users/{id}/orders — but a link (/orders?userId=42) is often more flexible and avoids deep nesting.
  • Idempotency matters for retries: POST isn't idempotent, so either make creation keyed by the client (Idempotency-Key header) or document that double-POST double-creates.
  • PUT vs PATCH: PUT replaces the whole entity (missing fields = cleared); PATCH merges only what you send. Confusing them is a data-loss bug.

Status codes: the shared vocabulary

The distinctions that win arguments: 401 vs 403 (not authenticated vs not allowed), 404 vs 403 (not found vs hidden — hide resource existence from unauthorized users), 409 (state conflict: version mismatch, duplicate) vs 422 (validation failed but the resource could be valid with different input).

Versioning, pagination, and errors: decisions you make once

Rendering diagram…
  • Version your URL (/v2/...) unless you have a strong reason not to — it's the only option where the version is visible everywhere, including CDN cache keys. Deprecate, don't break: a 410 Gone with a Deprecation header beats silently changing semantics.
  • Pagination: cursor-based (?cursor=...) is the modern default for big lists (stable across inserts); page-based (?page=2&limit=50) is simpler but shifts as new rows arrive. Always return metadata about the page in the response, and a stable order.
  • Errors are data, not strings: a consistent shape ({ "error": { "code", "message", "details", "request_id" } }) so clients can switch on code, show the message, and give you the request_id to debug.

Caching: REST's forgotten superpower

  • GET responses are cacheable by design — set Cache-Control and ETag, and let the edge cache do its job.
  • Never cache POST/PUT/DELETE bodies, and mark user-specific data Cache-Control: private.
  • 304 Not Modified with If-None-Match is how you turn "recheck every 5 minutes" into almost-free polling.

Tester checklist

  • Verify verbs do what they say: PUT clears absent fields, PATCH doesn't; double-check idempotency by replaying a PUT/DELETE with the same payload.
  • Confirm the error contract: every 4xx has the same shape, a machine-readable code, and a correlating request_id.
  • Test status-code intent: 401 when unauthenticated, 403 when unauthorized, 404 for a nonexistent id, and — importantly — that unauthorized access to an existing id looks identical to a 404.
  • Validate pagination stability: insert rows between page fetches and confirm cursor pagination doesn't skip or duplicate (page-based will).
  • Confirm caching: GET responses carry Cache-Control/ETag, and a conditional re-request returns 304.
