## What this system is

Users have identities; so do workloads. **Workload identity** gives every service, container, and pod a cryptographic identity, and **mTLS** uses it to encrypt *and* authenticate calls between services — closing the east-west traffic hole that firewalls never saw.

```mermaid
flowchart LR
  A["Service A<br/>spiffe://corp/catalog/a"] -->|sidecar| X1[Sidecar proxy]
  X1 -->|mTLS + SPIFFE trust| X2[Sidecar proxy]
  X2 -->|labeled untrusted unless verified| B["Service B<br/>spiffe://corp/orders/b"]
```

## User identity vs workload identity

| | User identity | Workload identity |
| --- | --- | --- |
| Proves | A human logged in | A workload *is* what it claims (its SPIFFE ID) |
| Carried in | Tokens / cookies | Short-lived X.509 certs presented on the connection |
| For you | SSO, OIDC, MFA | SPIFFE/SPIRE, service mesh, cloud SA (Workload Identity) |
| Expiry | Minutes-to-hours sessions | Hours-to-minutes certs, rotated continuously |

The mental model: **mTLS proves the *service*, tokens prove the *request*.** Both must hold — "known service" alone must never equate to "allowed to read everything."

## SPIFFE and SPIRE

```mermaid
sequenceDiagram
  participant W as Workload (pod)
  participant A as SPIRE agent
  participant S as SPIFFE server

  W->>A: request identity for spiffe://corp/catalog/a (attested by k8s metadata)
  A->>S: attestation check (agent valid, node trusted)
  S-->>A: short-lived identity (SVID cert + key)
  A-->>W: hand to workload, burned into sidecar memory
  Note over W,S: SVIDs rotate automatically - no human, no static keys
```

**SPIRE** is the reference implementation of producing short-lived service identities from the platform's own attestation (pod labels, node trust, instance metadata). The identity is whatever the platform says, per policy — no stored secrets, auto-rotating certs.

## The sequence of a secure call

```mermaid
sequenceDiagram
  participant SA as Service A (orders)
  participant SX as Sidecar X
  participant SY as Sidecar Y
  participant SB as Service B (payments)

  SA->>SX: local connection
  SX->>SY: TLS with client cert (spiffe://corp/orders/a), server cert (spiffe://corp/payments/b)
  SY->>SX: certs validated - both X.509 chain to the SPIFFE trust root
  SX->>SY: allow (or policy: only orders may call payments with v2 header)
  SY->>SB: plaintext into the pod
  SB-->>SA: response returns
```

Service meshes (Istio, Linkerd) implement this as zero-code: the sidecar proxies intercept all traffic, present/validate the identities, and apply L7 policy (who may call whom, with what).

## Why not just encrypt everything at the wall

A firewall/LB terminates TLS at the edge — inside the cluster it's usually plaintext. mTLS between every pair matters because **attackers are already inside** (assume breach): they land in one pod, and without workload identity they can impersonate any caller to any service. mTLS turns a one-command pivot into "attackers would need to steal a live rotated key from a trusted pod."

## Tester checklist

- Call service B impersonating service C's SPIFFE ID and confirm the handshake/client-cert validation fails.
- Kill a pod; its SVID must be invalidated quickly (short expiry, tight rotation, no golden access).
- Check that a *known* workload still cannot call endpoints policy forbids (identity grants authenticity, not authority).
- Rotate the trust bundle and verify all running workloads re-trust without downtime.
