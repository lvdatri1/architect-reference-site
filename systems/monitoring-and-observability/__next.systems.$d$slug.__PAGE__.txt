## What this system is

Monitoring answers *"is it broken?"* Observability answers *"why?"* The toolkit is the **three pillars** — **metrics** (numbers over time), **logs** (events with context), and **traces** (how one request traveled across services). Alerting converts them into pages; SLOs convert pages into numbers your product understands.

```mermaid
flowchart LR
  S[Your services] -->|OpenTelemetry SDK| I[Instrumentation]
  I --> M[Metrics - counters, gauges]
  I --> L[Logs - structured events]
  I --> T[Traces - distributed spans]
  M --> Store[(Time-series store<br/>Prometheus / CloudWatch / Azure Monitor)]
  L --> Store
  T --> Store
  Store --> Alert[Alert rules / SLO burn]
  Alert --> Page[On-call pages you actually act on]
  Store --> Dash[Dashboards - human eyes]
```

## The three pillars in practice

| Pillar | What it answers | Cloud home | Star resource when |
| --- | --- | --- | --- |
| **Metrics** | *How many / how fast / how full* | CloudWatch, Azure Monitor, Prometheus | Alerting, capacity, SLOs |
| **Logs** | *What exactly happened* | CloudWatch Logs, Log Analytics, Loki | Debugging, audit, forensics |
| **Traces** | *Where the time went* | X-Ray, App Insights, Jaeger/Tempo, OTEL | Slow calls across services |

**OpenTelemetry (OTEL)** is the standard instrumentation SDK — your app emits spans/metrics once, exporters send them anywhere. Instrument once, vendor later.

## The flow from service to page to runbook

```mermaid
flowchart LR
  Service[Your service] -->|instrument| OTel[OTel SDK - emit]
  OTel -->|counters| Metrics[Metrics]
  OTel -->|structured| Logs[Logs]
  OTel -->|spans| Traces[Traces]
  Metrics -->|push/pull| Store[Monitoring store]
  Logs -->|ingest| Store
  Traces -->|correlate| Store
  Store -->|alert rules| Alert[Alerts + runbooks]
  Store -->|aggregate| Dash[Dashboards + SLO]
```

## SLOs and the alert triage that matters

- **SLO / SLI / SLI burn**: an SLO ("99.9% of checkout requests under 300ms") is built on SLIs. Alert on **error-budget burn** (how fast you're spending it) rather than raw thresholds — that catches "slow but not dead" pain without paging on every blip.
- **Alert → runbook → owner**: an alert with no runbook is noise. Every alert should name its owning ticket and the play to try first.
- **The warning signs**: alerts that never fire (guard-dog not barking), and alert fatigue from ones that always fire. Both are bugs in the alerting system itself.

## Tester checklist

- Sink a background bad deploy: keep requests failing 5% and confirm an SLO-burn alert pages before users complain.
- Trace drill: pick one slow API call and walk its trace spans to the actual bottleneck service.
- Verify log structure: a structured-log query finds a UUID across all three pillars (metrics named + logs + trace ids).
- Measure the alert pipeline latency: from metric breach to on-call page — fix the chain if that's minutes long.
