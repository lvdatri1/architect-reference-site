## What this system is

Endpoint security is the set of layers that protects **every device that touches your data**: laptops, desktops, phones, tablets, and the servers that are also endpoints. It is not one product — it is a stack: enrollment and identity, OS hardening, antivirus/EDR, patch and update rings, full-disk encryption, policy and compliance, and the management plane that pushes all of it. In the [zero trust](../zero-trust-architecture) world, the endpoint is the new perimeter: **a device is not trusted because it's "inside" — it's trusted because it can prove identity, posture, and compliance on every request.**

```mermaid
flowchart TB
  subgraph Endpoint["The endpoint - any device"]
    ID[Identity -<br/>enrolled user + device cert]
    OS[OS hardening -<br/>config baseline]
    AV[EDR / AV -<br/>detect + respond]
    CRYPTO[Encryption -<br/>BitLocker / FileVault / full disk]
    PATCH[Patch -<br/>update rings + compliance]
  end
  ID --> Policy{Posture check}
  OS --> Policy
  AV --> Policy
  CRYPTO --> Policy
  PATCH --> Policy
  Policy -->|compliant?| Access[Access to apps + data]
  Policy -->|not compliant| Block[Quarantine / limited access]
```

## The endpoint security stack

| Layer | What it does | The archetypal products |
| --- | --- | --- |
| **Enrollment & identity** | Onboard the device, bind it to a user, issue a device identity | Microsoft Entra join, Intune, Jamf, Workspace ONE |
| **OS hardening** | A compliance baseline: settings, firewall, restrictions, no admin | Security baselines (Windows/Linux/macOS), CIS Benchmarks |
| **EDR / AV** | Detect and respond to malware and suspicious behavior | Defender for Endpoint, CrowdStrike, SentinelOne |
| **Encryption** | Full-disk and removable-media encryption, tamper protection | BitLocker, FileVault, LUKS |
| **Patch & update rings** | Controlled rollout of OS/app/security updates | Windows Autopatch, patch rings, WSUS/MECM |
| **Policy & compliance** | What a device must prove before accessing anything | Conditional Access, compliance policies, posture checks |
| **Management plane** | The single pane that enrolls, configures, and reports | Intune, MECM, Jamf, MDM + EMM |

The mental model: **the management plane defines the truth, and every endpoint continuously proves it holds.** A device that falls out of compliance (missing patches, AV disabled, disk unencrypted) loses access until it fixes itself — that loop is the whole architecture.

## The request path: endpoint → app

```mermaid
sequenceDiagram
  participant E as Endpoint (managed device)
  participant M as Management plane (Intune / MDM)
  participant P as Policy engine (Conditional Access)
  participant A as App / data

  E->>M: enroll - register device + user identity
  M-->>E: push config baseline + EDR + encryption policy
  E->>P: request access - present device cert + posture proof
  P->>P: check compliance (patch, AV, encryption, policy)
  alt compliant
    P-->>E: grant access
    E->>A: work - EDR watches behavior
  else not compliant
    P-->>E: block / limited access + remediation
  end
```

The key architectural fact: **the endpoint request is not trusted until the policy engine verifies posture.** The device doesn't "get on the network"; it gets access *conditionally*, per app, per request — which is why endpoint security and [identity & access management](../identity-and-access-management) are the same conversation.

## The layers that carry most of the value

- **Enrollment is the front door.** An unmanaged device is an untrusted device. Enrollment binds hardware to identity (device cert / attestation), so later posture checks have something to measure against. The failure is shadow-IT: devices using corporate data that were never enrolled, so every other layer has no hook.
- **EDR is detection + response, not just antivirus.** Classic AV matches known signatures; EDR adds behavioral detection on the endpoint, collects telemetry, and lets the [SOC](../security-operations-center-soc) respond remotely (isolate a host, kill a process, hunt laterally). The architecture question is coverage: an EDR only protects devices that run it and report — gaps in enrollment or agent health are the real holes.
- **Full-disk encryption is the lost-laptop layer.** BitLocker/FileVault mean a stolen device is a brick, not a data breach. It fails silently when keys are escrowed in a place the attacker can also reach, or when the drive isn't actually encrypted (a fleet of "BitLocker enabled" devices with TPM keys surrendered on request).
- **Patch rings are a risk calculation.** Patching is the #1 hygiene layer (most breaches are known vulnerabilities), but rolling updates everywhere at once is how you break the fleet. Rings: canary → broad → all, with health gates between, so a bad patch never lands everywhere.
- **Policy/compliance is the enforcement arm.** Conditional Access / compliance policies decide access based on posture in real time. This is what makes "device not compliant → no data" real instead of aspirational.

## Hardening: the baseline matters more than any single tool

```mermaid
flowchart LR
  B[CIS / vendor security baseline] --> D[Apply via management plane]
  D --> C[Continuous compliance check]
  C -->|pass| OK[Trusted device]
  C -->|fail| REM[Remediate automatically]
  REM --> C
```

A hardening baseline (CIS Benchmarks, vendor baselines) is the *configuration contract* every other layer assumes: local admin removed, firewall on, autoruns restricted, telemetry enabled. It's applied by the management plane and continuously checked — drift is found and fixed, not assumed. The honest priority: **no admin rights, prompt patching, and disk encryption prevent more incidents than an exotic EDR config.**

## Managing the fleet without breaking it

| Practice | Why | The failure mode it prevents |
| --- | --- | --- |
| **Patch rings + health gates** | A bad update is caught in canary before fleet | "The update broke everyone" |
| **Gradual policy rollout** | Policy bugs surface on a subset | "The policy locked out half the org" |
| **Self-service remediation** | Users fix posture without a ticket | Devices stuck non-compliant for weeks |
| **Agent/EDR health monitoring** | Know when a device loses coverage | "We thought it was protected" |
| **Retire/remove old OS versions** | Unsupported OS = unpatchable holes | Ancient Windows/Android in the estate |
| **Separation of duties** | Security team ≠ device admin permissions | One credential pwns the whole fleet |

## The failure modes an architect owns

- **Enrollment gaps**: the estate's devices were never all enrolled; every layer silently excludes them, so coverage is a fiction printed on the dashboard.
- **Posture theater**: compliance checks that only confirm *something* was installed, not that it's *running and current* (AV "enabled" but definitions three months old).
- **Local admin everywhere**: users (or malware via users) run with admin rights, defeating the hardening baseline.
- **Encryption with escrowed keys**: keys recoverable by the same actor who stole the laptop.
- **Patch lag on the crown jewels**: servers and critical machines patched last "because stability," while attackers target exactly them.
- **Agent health blindness**: no telemetry that the EDR/agent is reporting, so the SOC finds out a host went dark only during an incident.

## Tester checklist

- **Enrollment coverage**: query the management plane — every active corporate device must be enrolled, enrolled with a real user, and none show as unknown/unmanaged.
- **Posture gate**: disable AV on a test device and confirm access to data is actually blocked (or degraded) by the policy engine — not just logged.
- **Encryption reality**: sample devices and confirm full-disk encryption is genuinely on, keys are escrowed safely, and a lost-drive test yields no readable data.
- **Patch ring**: push a deliberate test patch to canary, verify it clears the health gate, then confirm broad rollout; verify an unhealthy canary *halts* promotion.
- **Remediation loop**: make a device non-compliant and confirm the user sees a remediation prompt and access is restored only after it fixes itself.
- **EDR response**: run a benign detection (test alert), confirm the [SOC](../security-operations-center-soc) sees the telemetry and can isolate the host remotely.
- **Local admin audit**: confirm the admin-rights baseline is enforced fleet-wide and exceptions are named and reviewed.
