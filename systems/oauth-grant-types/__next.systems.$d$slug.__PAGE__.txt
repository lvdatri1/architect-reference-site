## What this system is

OAuth 2.0 issues **tokens**, but not all tokens are obtained the same way. A **grant type** is the recipe for *how a client proves it may ask for a token* — and picking the right one (or the wrong one) is the single most consequential decision in your auth design. There are five that matter; the rest are legacy footnotes.

```mermaid
flowchart LR
  G[Grant type - how the client asks] -->|decide| P{Who is the client?}
  P -->|no secret| PUB[Browser / SPA / mobile - no secret to keep]
  P -->|secret-safe| CONF[Backend server - can keep a secret]
  P -->|no browser| DEV[TV / CLI - no browser]
  PUB -->|auth code + PKCE| T[access_token]
  CONF -->|client credentials| T
  DEV -->|device flow| T
```

## The five grants that matter

| Grant | Who it's for | How the token is obtained | Secret? |
| --- | --- | --- | --- |
| **Authorization code + PKCE** | Web apps, SPAs, mobile — anything with a user | Browser redirects to IdP, user consents, code exchanged for tokens | PKCE instead of a secret |
| **Client credentials** | Server-to-server, no user | Client signs with its own credentials, gets a token *for itself* | Yes — the client secret |
| **Device flow** | TVs, CLIs, IoT — no browser | User opens a URL on any device, enters a code | No |
| **Refresh token** | Long-lived sessions | Exchanged (server-side) for new access tokens | Where the access token came from |
| **Resource-owner password** | Legacy-only, discouraged | User's username+password sent to the IdP | Never do this in new code |

## The authorization code flow (with PKCE)

```mermaid
sequenceDiagram
  participant U as User (browser)
  participant A as SPA / mobile app
  participant P as Authorization server
  participant R as Resource API

  A->>A: generate code_verifier (random secret)
  A->>P: /authorize?code_challenge=SHA256(verifier)
  P->>U: login + consent
  U->>P: approve
  P-->>A: authorization code (via redirect)
  A->>P: POST /token code + code_verifier
  P->>P: verify verifier matches challenge
  P-->>A: access_token (+ refresh_token)
  A->>R: Authorization: Bearer access_token
  R-->>A: data
```

Why **PKCE** (proof key for code exchange) even when there's a client secret: the browser redirect carries the *code*, and a public client can't protect a secret the browser holds. The `code_verifier` proves that whoever is exchanging the code is the same party that started the flow — it kills a whole class of code-interception attacks. In modern OAuth (2.1), **PKCE is mandatory for everything**.

## Client credentials: the machine-to-machine grant

```mermaid
flowchart LR
  S[Backend service] -->|client_id + client_secret| P[Authorization server]
  P -->|access_token for the service itself| S
  S -->|Bearer token, no user involved| API[Another API]
```

When **no user** is in the conversation, the client authenticates *as itself*: it sends its `client_id` and `client_secret` to `/token`, and receives a token representing the **service**, not a person. Classic uses: a cron job calling an admin API, a backend calling a payment provider. The consequence to internalize: the token's authority is whatever that service is allowed to do — if you hand `scope: admin` to a client-credentials client, you've given a background job admin rights with no human in the middle.

## Device flow: when there's no browser at all

```mermaid
sequenceDiagram
  participant D as TV / CLI device
  participant P as Authorization server
  participant U as User's phone/browser

  D->>P: POST /device_authorization → device_code + user_code
  P-->>D: user_code: ABC-123, verification_uri
  D->>U: "go to URL, enter ABC-123"
  U->>P: login + approve
  loop polling
    D->>P: POST /token with device_code
    P-->>D: pending (poll again) / success
  end
  P-->>D: access_token
```

The device gets a `user_code` and a verification URL; the user approves on *any* device; the device **polls** until the token is ready. This is how "sign in with the code on your TV" works — and the tester-relevant detail is that the device must keep polling at a sane interval and stop once authorized or expired.

## Refresh tokens: extending a session safely

```mermaid
flowchart LR
  A[access_token expires] --> R{Have refresh_token?}
  R -->|yes - keep it server-side| B[POST /token grant_type=refresh_token]
  B --> C[new access_token + rotated refresh_token]
  R -->|no| D[Full re-auth]
```

Access tokens are short-lived; a **refresh token** lets a server-side client get a new one without making the user re-login. The discipline: the refresh token lives **server-side** (never in browser storage), is **rotated on each use** (a reused one is a sign of theft and gets revoked), and is itself revocable on logout. "Refresh token rotation" is the behavior your tester should poke at hardest.

## Picking and testing the right grant

```mermaid
flowchart TB
  Q{Is a user in the loop?} -->|no| M2M[Client credentials]
  Q -->|yes| B{Has a browser?}
  B -->|no| DEV[Device flow]
  B -->|yes| W{Can you keep a secret?}
  W -->|yes| CODE[Auth code + secret + PKCE]
  W -->|no| PKCE[Auth code + PKCE]
```

Tester checklist:

- **PKCE**: replay a stolen authorization code without the verifier — it must be rejected; reuse the verifier on two codes — second must fail.
- **Client credentials**: confirm the token's scopes are the *minimum* the service needs (an admin scope on a background job is a finding).
- **Refresh rotation**: use a refresh token twice — the second use must be denied (rotation + reuse detection).
- **Device flow**: confirm polling stops after expiry, the code expires, and the user's approval grants only the requested scopes.
- **No password grant**: if you see `grant_type=password` in logs or docs, that's legacy tech debt to flag, not copy.
