## What this framework is

TOGAF (The Open Group Architecture Framework) answers the question Zachman deliberately avoids: **how do you actually produce architecture?** Its engine is the **ADM** — Architecture Development Method — a staged cycle from vision to overshoot to closure control.

```mermaid
flowchart LR
  P[Preliminary<br/>Framework & principles]
  A[Phase A<br/>Architecture Vision]
  B[Phase B<br/>Business Architecture]
  C[Phase C<br/>Info Systems Architecture]
  D[Phase D<br/>Technology Architecture]
  E[Phase E<br/>Opportunities & Solutions]
  F[Phase F<br/>Migration Planning]
  G[Phase G<br/>Implementation Governance]
  H[Phase H<br/>Architecture Change Management]

  P --> A
  A --> B
  B --> C
  C --> D
  D --> E
  E --> F
  F --> G
  G --> H
  H -.->|requirements management| A
```

## What each phase produces

| Phase | Output your organisation can use | Typical audience question |
| --- | --- | --- |
| Preliminary | Principles, tooling choices, architecture repo | "How will we even keep this?" |
| A · Vision | Stakeholder map, value proposition, high-level roadmap | "Why are we doing this?" |
| B · Business | Capability map, value streams, target KPIs | "Which processes improve?" |
| C · Information Systems | Data + application architecture (see Zachman *What/How*) | "Which systems and data change?" |
| D · Technology | Technology reference architecture, platform choices | "Which servers, cloud, tooling?" |
| E · Opportunities | Work packages, project portfolio | "What do we build first?" |
| F · Migration | Transition architectures + a sequenced migration plan | "How do we get there safely?" |
| G · Governance | Architecture compliance reviews, change control | "Is the build still on-spec?" |
| H · Change | Architecture change requests, continuous refinement | "What happens when reality disagrees?" |

## The one thing that makes it "TOGAF"

The ADM is **iterative and requirement-driven**, not a one-shot waterfall. Every arrow from B→H is hybrid with the **Requirements Management** loop in the middle:

```mermaid
flowchart TB
  C1[Discovery] --> R[Requirements Management<br/>continuously re-fed]
  D1[Design] --> R
  G1[Governance] --> R
  R --> SA[Stakeholder acceptance]
```

Two traps kill ADM rollouts in practice:

1. **Phases A–D done with no E–G** — architecture becomes a shelf document nobody implements. TOGAF is explicit: opportunities, migration, and governance are part of the cycle, not afterthoughts.
2. **Method without a repository** — without an architecture repository (the "meta-model" that stores artefacts), every new proposal regenerates the same diagrams by hand.

## How a solution architect works the cycle

```mermaid
sequenceDiagram
  participant SA as Solution Architect
  participant Biz as Business Stakeholders
  participant EA as Enterprise Architect
  participant PA as Platform / Ops

  SA->>Biz: Phase A: document vision & concerns
  Biz-->>SA: business goals + constraints
  SA->>EA: align to current baseline architecture
  EA-->>SA: existing standards & reference models
  SA->>SA: Phase C+D: draft target data/technology design
  SA->>PA: feasibility check against platform
  PA-->>SA: gaps, risks, cost input
  SA->>Biz: Phase E: option & opportunity analysis
  SA->>EA: Phase G: compliance review of final design
  EA-->>SA: approve / reject with gaps
```

## Tester-friendly checklist

- Traceability: every Phase C requirement must map to an ADM artefact and back — a governance review will ask for it.
- Baseline-vs-target diffs: the *transition architecture* (Phase F) is what gets tested first, before the target exists.
- Compliance reviews (Phase G) need to run during implementation, not at go-live.
