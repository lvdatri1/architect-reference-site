## What this system is

SSO means the **identity provider (IdP)** authenticates you once, and every connected app trusts its assertion — no more N passwords, no more shadow accounts, and revoke-at-the-IdP ends access everywhere. Two protocols pull this off: **SAML** (older, XML, enterprise/SaaS legacy) and **OIDC** (modern, JSON, web/native).

```mermaid
sequenceDiagram
  participant B as Browser / user
  participant A as App - relying party
  participant P as Identity provider - holds the session

  B->>A: open protected page
  A->>P: redirect auth request
  P-->>A: authorization code
  A->>A: exchange code for tokens - id_token + access
  Note over A: app session minted
  Note over A,P: SLO kills both sessions
```

```mermaid
flowchart LR
  User[User] -->|one login| IdP[Corporate IdP - holds the session]
  IdP -->|assertions/tokens| A1[App A - SAML]
  IdP -->|assertions/tokens| A2[App B - OIDC]
  IdP -->|assertions/tokens| A3[App C - OIDC]
  IdP -->|kill session - everywhere at once| Revoke[Logout / deprovision]
```

## The flow your browser lives in (SP-initiated OIDC)

```mermaid
sequenceDiagram
  participant B as Browser
  participant A as App (RP)
  participant I as Identity provider

  B->>A: open protected page
  A->>B: redirect + auth request to IdP
  B->>I: already has IdP session - no prompt
  I->>B: authorization code back to App
  A->>I: exchange code + client secret for tokens
  I-->>A: ID token + access token
  A->>A: validate signature, lifetime, audience
  A-->>B: session granted on the app side too
```

Two sessions actually exist: the **IdP session** (your "logged in" at the IdP) and each **app's local session**. SSO saved you the IdP login; the app still mints its own cookie/token per login via the IdP.

## OIDC vs SAML — which road are you on

| | OIDC | SAML |
| --- | --- | --- |
| Format | JSON / JWT-friendly | XML assertions |
| Modern fit | Web, mobile, APIs, SPAs | SaaS platforms, legacy enterprise |
| Sits on | OAuth 2.0 | Standalone |
| Nit | IdP roles (authorize) and scopes | Assertion conditions, federation |

Two different protocols solving the same job; if you're building greenfield, OIDC wins. If your SaaS buyer only speaks SAML, you integrate SAML.

## What everyone forgets: logout

SSO that can't log out everywhere is a myth. **Single Logout (SLO)** tells every app's session to die when the IdP session dies. OIDC adds **RP-initiated logout** (app tells IdP, IdP tells the rest). Test it, because the default state of most stacks is: *the IdP session ends, the apps' sessions quietly survive* — a real exposure after a shared-computer session.

## SSO is authentication, not authorization

SSO proves *who*; it says nothing about *what you may do*. The ID token's scopes/claims seed the app's session, and the app's own [RBAC](../rbac-and-authorization)/policy decides access. "Trusting employee email" ≠ "employee may see the payroll ledger."

## Tester checklist

- Round-trip a full login and logout through every app: after SLO, hitting a protected page must bounce to the IdP login.
- Validate a token beyond its signature: expiry, audience, issuer, `nonce` — a well-signed spoof is still a forgery.
- Confirm no app keeps its own credential store (shadow identity = SSO divot).
- Kill the IdP session mid-flight and confirm each connected app loses it within expected bounds (session + refresh lifetimes).
