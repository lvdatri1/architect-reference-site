## What this system is

Azure's most distinctive ideas are **resource management** (every resource lives in a resource group inside a subscription, under a management hierarchy) and **PaaS first** (App Service, Functions, and managed SQL are the default path, with VMs as the escape hatch). The analogous reference deployment to the AWS one:

```mermaid
flowchart LR
  subgraph Pub["Public layer"]
    In[Internet] -- edge --> GW[Application gateway<br/>multi-zone]
  end
  subgraph App["App layer"]
    AV1[App Service - zone 1]
    AV2[App Service - zone 2]
  end
  subgraph Data["Data layer"]
    ASQL[(Azure SQL<br/>HA + geo-replica)]
    STG[(Blob storage<br/>static + backups)]
  end
  GW -- route --> AV1
  GW -- route --> AV2
  AV1 -- SQL --> ASQL
  AV2 -- SQL --> ASQL
  AV1 -- assets --> STG
  AV2 -- assets --> STG
```

```mermaid
flowchart LR
  In[Internet] --> GW[Application gateway<br/>multi-zone]
  GW --> AV1[App Service / VM<br/>zone 1]
  GW --> AV2[App Service / VM<br/>zone 2]
  AV1 --> SQL[(Azure SQL Database<br/>HA + geo-replica)]
  AV2 --> SQL
  AV1 --> ST[(Blob storage)]
  AV2 --> ST
```

## The management tree

```mermaid
flowchart TB
  Root[Microsoft Entra ID tenant]
  Root --> MG1[Management group - prod]
  Root --> MG2[Management group - non-prod]
  MG1 --> Sub1[Subscription - prod apps]
  MG1 --> Sub2[Subscription - prod data]
  Sub1 --> RG1[(Resource group: app-rg)]
  RG1 --> R1[App Service - web tier]
  RG1 --> R2[Function app - background]
  Sub2 --> RG2[(Resource group: data-rg)]
  RG2 --> R3[Azure SQL Database]
  RG2 --> R4[Storage account]
```

RBAC policies, budgets, and guardrails are inherited **top-down** from management groups → subscriptions → resource groups. Put sensitive data in its own subscription so a mis-wired policy can't silently cross the boundary.

## The services that matter, in one map

| Category | The workhorses | When to reach for them |
| --- | --- | --- |
| Compute | **VMs**, **App Service**, **Functions**, AKS | VMs; web apps; serverless; containers |
| Storage | **Blob storage**, Azure Files, disks | Object store; shared fs; volume |
| Network | **VNet**, Azure Load Balancer/App Gw, DNS | Private networks; entry points |
| Database | **Azure SQL**, Cosmos DB, PostgreSQL Flex | Relational; NoSQL; managed alternatives |
| Identity | **Microsoft Entra ID** (formerly AAD) | Users, service principals, device identity |
| Govern | Policy, budgets, RBAC | Guardrails + cost control |

## PaaS staging: the slot model

```mermaid
flowchart TB
  AppSvc[App Service] --> Slot1[Staging slot]
  AppSvc --> Slot2[Production slot]
  Slot1 -->|warm-up + swap| Slot2
```

App Service slots let you deploy to a **staging slot**, warm it, then `swap` it into production atomically — the simple, built-in answer to zero-downtime releases. AKS/Linux are the escape hatches when slots stop fitting.

## RBAC and identity: two different knobs

| | Azure RBAC | Entra ID roles |
| --- | --- | --- |
| Grants | Access to *resources* (read/write a storage account) | Tenant/admin powers (run identity, reset passwords) |
| Examples | Contributor on app-rg | Global admin, app admin |
| Mindset | Least privilege per resource | Only the few people with tenant-wide power |

A recurring incident source: someone with Entra-tier "Azure AD admin" authority — sure, it's not "resource access," but it can reset the identity of everything. Keep the two separate in your head.

## Governance knobs that stop incidents before they start

- **Policy**: enforce "production storage must encrypt + have network isolation" as *policy*, not a preference.
- **Budgets + alerts**: get woken when cost deviates, not at the month-end invoice.
- **Management groups**: a clear prod vs non-prod split is the cheapest firewall you'll ever buy.
- **Deletion locks** on resources you'd cry over.

## Tester checklist

- Swap a slot mid-traffic and confirm zero dropped requests and instant rollback by swapping back.
- Verify RBAC cascade: escalate into the data subscription from the app subscription should be *blocked by inheritance*, not by a friendlier rule.
- Break a region dependency (stop zonal resources) and confirm the HA pair (SQL geo-replica, second zone) takes over.
- Run a budget report: which top-3 resources tripled? Investigate right-sizing before you pay another invoice.
