## What this system is

**CI** (continuous integration) runs automated checks on every commit — lint, test, build — and the **CD** (continuous delivery/deployment) half packages the result into an **artifact** and promotes it through environments until it reaches production. The output is not "a deploy"; it's a repeatable, auditable path.

```mermaid
flowchart LR
  Commit[Commit / PR] -->|trigger| CI[CI: lint + unit]
  CI -->|gate: green| Build[Build image / bundle]
  Build -->|push versioned| Art[(Artifact registry - immutable SHA)]
  Art -->|promote| Staging[Staging env + smoke]
  Staging -->|gate: approve| Prod[Production]
  Prod -->|error rate| Rollback[Rollback on alarm]
```

```mermaid
flowchart LR
  Commit[Commit / PR] --> Lint[Lint + unit tests]
  Lint --> Build[Build image/bundle]
  Build --> A[(Artifact registry<br/>versioned + immutable)]
  A --> E2E[Integration + e2e tests]
  E2E -->|gate: tests green| Staging[Deploy to staging]
  Staging -->|gate: manual approve or smoke| Prod[Deploy to production]
  Prod --> Post[Post-deploy checks + rollback on alarm]
  Post --> Rollback[Automatic rollback]
```

## The stages that never change (even when tools do)

| Stage | Purpose | Typical checks |
| --- | --- | --- |
| Commit/PR | Fast feedback on the change | Lint, unit tests, type checks |
| Build | Encapsulate the app as one artifact | Build image, SBOM |
| Test | Prove it behaves | Integration, e2e, security scan |
| Package/Promote | Make the artifact official | Book that exact SHA, not "latest" |
| Deploy(staging) | Safe rehearsal | Env parity, smoke tests |
| Deploy(prod) | The real thing, controlled way | Canary/blue-green, rollback trigger |

The rule to hold onto: **you promote build artifacts, never recompile**. If prod rebuilds from source, you're not releasing the tested thing.

## Environment as a "gate"

```mermaid
flowchart TB
  A[Artifact v1.4.2] --> Dev[Dev env - do anything]
  Dev --> Stg[Staging - mirror prod config + secrets]
  Stg -->|manual approval or automated smoke| Prod[Prod - least privilege, audited]
  Prod -->|alarm / error rate| RB[Rollback to v1.4.1]
```

Environments are *promotion steps*, not copies: staging should run on the same config shape and secrets as production, or the gate proves nothing.

## Deployment strategies compared

| Strategy | How it releases | Downtime | Risk profile |
| --- | --- | --- | --- |
| **Recreate** | Stop old, start new | Downtime | Simplest, riskiest for live |
| **Rolling** | Replace nodes gradually | None | Single version alive at any moment, mixed briefly |
| **Blue-green** | New stack beside old, switch traffic | None (a cutover) | Instant rollback by switching back |
| **Canary** | Send small % to new, increase if healthy | None | Catch problems on real traffic, earlier |
| **Feature-flag release** | Ship code dark, toggle in prod | None | Decouple deploy from release |

The mature answer is usually **canary or blue-green for infra changes, plus feature flags for product changes** — "the code is in prod" and "users see it" become two different events.

## What makes a pipeline trustworthy (security too)

- **Secrets only via the pipeline's secret store** — never in the build step's logs or schema files.
- **Signed/sbommed artifacts**: pin checksums, so prod deploys exactly the tested bytes.
- **Every deploy is a git commit + tag**: you can name who/what/when by looking at the repo, not guessing.
- **Manual gates where context matters, automation elsewhere**: let humans click for prod, machines do the rest.

## Tester checklist

- Corrupt a build artifact and confirm promotion blocks it (integrity fails at staging, never a prod surprise).
- Verify staging truly mirrors prod: same secret keys, same env vars, same region/scale shape.
- Trigger an alarm on the canary wave and confirm rollback fires to the previous artifact within your MTTR.
- Prove *any* change to the pipeline definition is itself reviewed and versioned in git.
