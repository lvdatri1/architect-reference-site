## What this system is

Logging in with “Sign in with Google” is easier to describe as a chat between three actors than as a sequence of claims. OAuth 2.0 hands out **tokens** for accessing resources; OpenID Connect (OIDC) adds the `id_token` that proves *who* you are.

```mermaid
sequenceDiagram
  participant B as Browser / SPA
  participant A as Your app
  participant P as Identity provider
  participant API as Resource API

  B->>A: user wants access
  A->>P: redirect + authorize request
  P-->>A: authorization code
  A->>A: exchange code for tokens - id_token + access
  A->>API: call with Bearer token
```

```mermaid
sequenceDiagram
  participant U as Browser / SPA
  participant A as Your App
  participant P as Identity Provider (Auth Server)
  participant R as Resource Server (API)

  U->>A: Click "Sign in"
  A->>P: Redirect to /authorize?code_challenge=...
  P->>U: Login + consent
  U->>P: Approve scopes
  P-->>A: Authorization code (short-lived, one-time)
  A->>P: POST /token code + code_verifier
  P-->>A: access_token + id_token
  A->>R: GET /me  Authorization: Bearer access_token
  R-->>A: user profile
  A-->>U: Render signed-in UI
```

## The three actors

| Actor | Talks to | Example |
| --- | --- | --- |
| Resource owner | The user who approves access | You |
| Client | Your application, wants access | The SPA / backend |
| Authorization server | Issues tokens, owns identities | Auth0, Keycloak, Okta |

## Key design decisions

- **Authorization code flow** is the default for web apps: the code never shows to the browser, only the backend exchanges it for tokens, so refresh tokens stay server-side.
- **PKCE** (proof key for code exchange) works even on public clients: the browser sends a one-time *challenge* of a secret it holds.
- **The `id_token` is signed JSON** (a JWT). Verify the signature and audience before trusting it — anyone can mint an unsigned JWT.
- **Scopes** (e.g. `openid`, `email`, `profile`) describe permission boundaries; grant the minimum set.

## What a tester watches for

1. **Token leakage** — does the access token ever appear in a URL query string or in browser storage for a public client?
2. **State / PKCE validation** — can an attacker replay or swap authorization codes?
3. **Refresh token rotation** — is a reused refresh token rotated or revoked?
4. **Expired tokens** — does the client silently refresh or hard-fail? Does the resource server actually check expiry?
