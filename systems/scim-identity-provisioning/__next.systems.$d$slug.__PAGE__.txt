## What this system is

SSO answers *"may this user log in?"*; **SCIM** answers *"does this user exist in the app at all?"* (System for Cross-domain Identity Management, SCIM 2.0). It's a **REST + JSON** standard: the identity store (the source of truth) pushes users, groups, and roles into each connected app over a standard `/Users` and `/Groups` API — so onboarding and offboarding become automation, not tickets.

```mermaid
flowchart LR
  HR[(HR system - source of truth)] -->|join / move / leave event| ST[Identity store / IdP]
  ST -->|changes to sync| CL[SCIM client]
  CL -->|create user| US[App A - POST /Users]
  CL -->|assign groups| GR[App B - PUT /Groups]
  CL -->|active true| RD[Account ready - before first login]
```

```mermaid
flowchart LR
  HR[(HR system - source of truth)] --> IdP[Identity store / IdP]
  IdP -->|SCIM push| App1[App A - /Users]
  IdP -->|SCIM push| App2[App B - /Groups]
  IdP -->|SCIM push| App3[App C - roles mapping]
  IdP -->|SCIM delete on leave| App1
  IdP -->|SCIM delete on leave| App2
```

## The standard in one picture

| SCIM resource | What it represents | Key fields |
| --- | --- | --- |
| `/Users` | One person's account | `userName`, `emails`, `active`, `groups` |
| `/Groups` | A collection that becomes app roles | `displayName`, `members` |
| `/ServiceProviderConfig` | What this app supports | schemes, patch, bulk |

Operations are plain HTTP semantics: `GET` read, `POST` create, `PUT`/`PATCH` update, `DELETE` remove. A `bearer token` in the client authenticates the pushes; TLS + that bearer token is the whole security model.

## The typical sync flow

```mermaid
sequenceDiagram
  participant IdP as Identity provider
  participant App as SaaS app / directory
  participant User as New hire

  IdP->>IdP: HR event: user.department = engineering
  IdP->>App: POST /Users { userName, email, active:true }
  App-->>IdP: 201 created with app user id
  IdP->>App: PUT /Groups/dev-group members + new user
  App->>User: app account exists before first login
  Note over IdP: on termination - PATCH active:false and group removal
```

The result worth bragging about: a new person's accounts **exist before they need them**, and a leaver's accounts die the day they leave — because provisioning is driven by the [joiner-mover-leaver](../joiner-mover-leaver) events, not by someone's 4pm Friday ticket.

## SCIM vs SSO (the pair everyone conflates)

| | SSO | SCIM |
| --- | --- | --- |
| Asks | *Who are you?* (authentication) | *Should this account exist?* (provisioning) |
| Carry | Assertions/tokens | User/group JSON objects |
| Lifecycle | Sessions, logout | Create, update, suspend, delete |
| Wrong without | (still works, one by one) | you get shadow/ghost accounts |

An app with SSO *and* no SCIM users "logs in" but never gets accounts created, updated, or removed — the classic ghost-account factory.

## Tester checklist

- Trigger a join event end-to-end: SCIM creates the user *before* first sign-on, in the same groups as their role.
- Test the leaver path: `active:false` + group removal fire promptly — verify the app can't be logged into afterwards.
- Replay resilience: SCIM is idempotent-by-design; a retried `POST` must not duplicate the user (check `externalId`/`userName`).
- Check deprovisioning really deletes or suspends in the *app*, and that SCIM bearer tokens are scoped per-app, not shared.
