## What this system is

Git is the shared memory of your codebase: every change is a **commit** (snapshot + message + author), changes happen on **branches**, and they come together through **merges or pull requests**. Done well, history is a legible story with a release at each chapter. Done badly, it's a tangle of force-pushes and "fixed" commits.

```mermaid
flowchart LR
  Branch[feature/checkout-ui] -->|push| PR[Pull request]
  PR -->|required checks| Review[CI + review - protected branch]
  Review -->|squash merge| Main[main - always deployable]
  Main -->|release| Tag[Release tag - v1.4.0]
```

```mermaid
flowchart LR
  F1[feature/checkout-ui] -->|PR + review| M[main]
  F2[bugfix/118-timeout] -->|PR + review| M
  M -->|tag v1.4.0| R[(Release branch / tag)]
  R -->|hotfix from tag| M
```

## The development flow

```mermaid
flowchart TB
  A[Issue in tracker] --> B[Branch from main]
  B --> C[Work in small commits]
  C --> D[Open pull request]
  D --> E{CI + review}
  E -->|green + approved| F[Squash-merge to main]
  E -->|fail| C
  F --> G[Deploy via pipeline]
  G --> H[Monitor + feedback]
```

**Protect main**: no direct pushes, required reviews, required CI. `main` should always be *deployable* — anything else turns releases into archaeology.

## Merge vs rebase vs squash

| Operation | Shape of history | When to use |
| --- | --- | --- |
| **Merge** | Adds a merge commit, preserves branch history | Long-lived branches, preserving context |
| **Rebase** | Replays your commits on top, linear history | Cleaning a local branch before PR; avoid on shared/pub branches |
| **Squash merge** | One commit summarizes the whole branch | Most PRs — clean main, single blame point |

Rule that prevents grief: **never rebase a shared branch** (rewrites history others built on; force-push tears down clones and CI). Squash-merge on main, rebase your own local work.

## Things that actually go wrong

- **Force-push accidents**: only allow force-push on your own unpushed work; protect-main blocks it everywhere else.
- **Revert ≠ undo**: `git revert` creates a new commit and is safe on shared history; `git reset`/`reset --hard` rewrites history and is the foot-gun.
- **Large/secret files in history**: deleting a file now does not remove it from history — `.gitignore`, BFG/filter-repo, secret scanning, and rotate secrets.
- **Merge conflicts are feedback**: they say two changes overlapped; the fix is domain understanding, not `git checkout --theirs`.

```mermaid
flowchart TB
  subgraph Good["Commit messages that behave"]
    A[Short subject + why not just what]
    B[Reference issue: JIRA-118 fix timeout]
    C[One logical change per commit]
  end
```

## Tester checklist

- Rebase a branch onto a drifted main and confirm re-runs of CI pass before the PR (not after merge).
- Verify upstream `main` protection: a direct push must fail; only PRs with passing checks land.
- Try the dangerous path with a backup: `git reset --hard` gone wrong — can you still recover the commit? (reflog!)
- Check history hygiene: log scan for secrets and large blobs as part of the pipeline, not a reaction.
