## What this system is

A **JWT** (JSON Web Token) is a signed, self-contained statement like *"this is user 42, role admin, valid until noon"*. Because it is signed, an API can trust the token's claims **without asking anyone** — that statelessness is both the benefit and the danger.

```mermaid
sequenceDiagram
  participant C as Client
  participant A as Auth server
  participant API as Protected API - stateless verify

  C->>A: login + MFA
  A-->>C: issue signed token - header.payload.signature
  C->>API: Bearer header with JWT
  API->>API: verify signature + exp only
  API-->>C: response
```

```mermaid
flowchart LR
  A[header<br/>alg: HS256] --> B[payload<br/>sub: 42, role: admin, exp: ...]
  B --> C["signature<br/>HMAC(header.payload, secret)"]
  C --> D[token: header.payload.signature]
```

## The three parts

| Part | Contents | Purpose |
| --- | --- | --- |
| Header | `alg`, `typ` | Says which algorithm signed it |
| Payload | claims: `sub`, `exp`, `iss`, `aud`, `role`, `scope` | The identity + permissions |
| Signature | digest over `header.payload` with the secret | Integrity + authenticity |

The whole token is `base64url(header) + "." + base64url(payload) + "." + base64url(signature)` — remember: **payload is readable by anyone** (it's only encoded, not encrypted). Never put secrets in a JWT.

## How verification (should) work

```mermaid
sequenceDiagram
  participant C as Client
  participant API as API
  participant IDP as Identity Provider

  C->>IDP: login
  IDP-->>C: access_token (JWT)
  C->>API: GET /me  Authorization: Bearer <token>
  API->>API: 1. split token, 2. verify signature w/ secret,<br/>3. check exp + aud, 4. read claims
  API-->>C: 200 (no DB lookup needed)
```

The API proves the token was minted by the IDP by checking the signature with a **shared secret** (HMAC) or the IDP's **public key** (RSA/EC). Once it trusts the signature, it trusts the claims — unless it needs to check revocation.

## The stateless-vs-stateful trade-off

| | Stateless JWT | Session (stateful) |
| --- | --- | --- |
| Where identity lives | Inside the token | In the server's session store |
| Server lookup on each request | None (fast, scalable) | Yes (Redis / DB hit) |
| Logout / revoke | Hard — must wait for `exp` or keep a blocklist | Instant — delete the session |
| Info exposure | Payload readable if token leaks | Nothing in the token |

If you need instant revocation (logout, account ban), you'll add a **token blocklist/denylist** or keep short-lived tokens with refresh tokens (see OAuth/OIDC guide).

## The attacks that keep failing teams

- **`alg: none`** — never accept unsigned tokens; pin the algorithm server-side.
- **Algorithm confusion** — `RS256`-signed tokens replayed as `HS256` will "verify" *only* if the API wrongly uses the public key as the HMAC secret.
- **Weak secret brute force** — a guessable HMAC secret is a signed-anything pass.
- **Stale `exp`** — check expiry, always, on every endpoint.
- **`aud`/`iss` not checked** — tokens minted for another app or issued by a different IDP are accepted.
- **Token in a URL query string** — leaks into logs and browser history; keep tokens in memory / short-lived, never in `localStorage` unless fully understood.

## Tester checklist

- Try the `alg=none` variant and a tampered payload with the same signature — both must be rejected.
- Verify that `exp`, `aud`, and `iss` checks actually fire (craft tokens with bad values).
- Confirm tokens are never logged, not even in API gateway request logs.
- Check the refresh-token rotation: a used refresh token must not be reusable.
