## What this system is

A housing management system (property management, PMS) runs the **asset side** of residential real estate: the buildings and units you own or manage, their physical state, who is responsible, and the maintenance and inspections that keep them rentable. Where the [tenancy management system](../tenancy-management-systems) owns *who rents what*, the housing system owns *what the building is*. The two are joined at the unit — the master object both sides operate on.

```mermaid
flowchart LR
  P[Portfolio] --> B[Building / development]
  B --> U[Unit - the core object]
  U --> O[Occupancy state]
  U --> M[Maintenance + inspections]
  U --> L[Linked tenancy records]
```

## The object model

| Object | Holds | Owned by | Failure mode |
| --- | --- | --- | --- |
| Portfolio / estate | Grouping of buildings | Asset owner | Reporting across the wrong scope |
| Building / development | Address, blocks, common areas | Property team | Unit → building links drift |
| **Unit** | Number, type, area, condition, features | Housing system | The integration hub both sides trust |
| Unit status | Let / vacant / maintenance / hold | Housing system | Stale status blocks new lettings |
| Work order | Job, trade, status, cost | Maintenance | Vendor never completed but status says closed |
| Inspection record | Condition, photos, date | Inspections | Photos lost, disputes lose |

The **unit** is the record of truth: tenancy, rent, maintenance, and inspections all hang off it. If the housing system and the tenancy system disagree about a unit's status, that disagreement is a live booking bug.

## The unit lifecycle

```mermaid
flowchart LR
  AC[Acquire / build] --> IN[Setup - config, features, spec]
  IN --> AV[Available to let]
  AV --> OC[Occupied - under tenancy]
  OC --> MT[In maintenance / hold]
  MT --> AV
  OC --> RE[Returned to portfolio / sold]
```

The unit's **status is a state machine with rules**: you cannot let a unit that is in maintenance, and you cannot move a tenancy in before the prior one has signed out. Most integration bugs in property software are *status races* — two systems updating the same unit's state without a single owner.

## The maintenance pipeline

```mermaid
flowchart LR
  R[Issue raised - tenant or inspection] --> A[Assess + prioritise]
  A --> V[Assign vendor / internal trade]
  V --> W[Work order + cost approval]
  W --> D[Done - photos + sign-off]
  D --> B[Billing - to owner, tenant, or insurance]
```

Maintenance is where housing management spends money, so the costing and approval trail matters: who authorised the work, at what estimate, against which budget. The auditability of this chain decides whether a dispute becomes an argument or a report.

## The unit → occupancy path

```mermaid
stateDiagram-v2
  [*] --> Unit: setup
  Unit: Unit setup
  Unit --> Available: ready
  Available: Available to let
  Available --> Tenancy: lease signed
  Tenancy: Tenancy created
  Tenancy --> Occ: move-in
  Occ: Occupied
  Occ --> Maint: life in service
  Maint: Maintenance + rent
  Maint --> [*]
```

## Tester checklist

- Status integrity: force a conflict (unit shows occupied in tenancy system, vacant in housing) — the reconcile must surface it, not silently accept.
- Let-gating: a unit in maintenance must not be lettable; a let attempt must be blocked at the source.
- Maintenance audit trail: every work order must carry approval, estimate, actual cost, and completion sign-off — a closed-but-incomplete order must trip a flag.
- Inspections: photos and notes must be bound to unit and date, surviving a re-let of the same unit.
- Billing split: work charged to owner vs tenant vs insurance must post to the right account (check the finance link).
