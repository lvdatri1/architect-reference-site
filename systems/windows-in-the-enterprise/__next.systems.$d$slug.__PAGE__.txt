## What this system is

Corporate Windows is not the retail OS. Every device is **identity-bound** (joined to a domain / Entra ID), **policy-managed** (GPO or Intune), and **monitored** (inventory, compliance, telemetry). The goal: a user opens a laptop, it is corporate-configured, compliant, patched, and remotely wipeable — with nobody touching it manually.

```mermaid
flowchart LR
    D[New laptop] -- boot + call home --> AU[Autopilot - device hash]
    AU -- auto-join --> E[Entra ID / AD]
    E -- enroll + report --> I[Intune - policies + apps]
    I -- apply config --> D
    I -- BitLocker + Defender --> C[Compliance check]
    C -- allow or quarantine --> H[Healthy - access]
```

```mermaid
flowchart LR
  D[New laptop] -->|Autopilot profile| A[Entra ID / AD] -->|identity + policy| I[Intune]
  I -->|push app + config| D
  D -->|enroll + report inventory| I
  I --> C{Compliant?}
  C -->|yes| E[Healthy device → allow access]
  C -->|no| F[Block / quarantine until fixed]
```

## The enrollment lifecycle

```mermaid
sequenceDiagram
  participant D as Device (out-of-box)
  participant ABM as Vendor / Autopilot
  participant Entra as Entra ID / AD
  participant Intune as Intune MDM
  participant App as Corporate portal

  D->>ABM: boot, calls home with serial
  ABM-->>Entra: known hardware hash → auto-join
  D->>Entra: enroll device identity
  Entra->>Intune: MDM enrollment token
  Intune->>D: push policies + apps
  D->>App: user signs in, device now managed
  Note over Intune,D: device stays enrolled: inventory, patch, compliance, remote wipe
```

## GPO vs Intune policy

| | Group Policy (GPO) | Intune policy (MSP) |
| --- | --- | --- |
| Scope | On-prem AD domain members | Cloud (Entra ID-joined) devices |
| Where policy lives | DC-based | Cloud-delivered, device-specific |
| Best for | Legacy/desktop workflows | Modern endpoint management |
| Venue | Apply at boot / re-eval every ~90 min | Check-in every few minutes |

Both can collide; the modern estate converges on Intune (or SCCM co-management) as the single source of truth. **Autopatch** handles the drumbeat: rings where updates roll out in waves (rings = pilot → broad → canary) so a bad patch poisons only a fraction of devices.

## What "compliant" means (and why it gates access)

Compliance is a *claim check*, not a promise: BitLocker on, Defender on and updated, OS ≥ version, password policy met, no jailbreak-type mutations, hardware healthy. The **conditional access** layer (part of [zero trust](../zero-trust-architecture)) releases access only on a *healthy* device — this is the modern "device is an identity" idea.

## Tester checklist

- Enroll a fresh device via Autopilot/automated provisioning and verify zero manual steps (guy affirms: no local admin fiddling).
- Validate policy application **timing**: GPO drift vs Intune check-in cadence — then audit one device and see both outputs.
- Test the compliance loop: disable BitLocker or strip Defender and confirm access is blocked/quarantined, then restored on fix.
- Do a real patch drill: bad update in a ring must quarantine in that ring, not spread to all.
