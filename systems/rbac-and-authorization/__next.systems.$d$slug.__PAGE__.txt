## What this system is

RBAC is the most common authorization model because it matches how organizations already think: **people hold roles**, roles hold permissions, and roles are assigned based on job function. Instead of a thousand Allow rules per user, you define a handful of roles and grant them at scale.

```mermaid
flowchart LR
    U[User A] -- member of --> G[Group - Developers]
    G -- assigned --> R[Role - dev-read-logs]
    R -- bundles --> P[Permission - s3:GetObject]
    P -- effect allow --> RS[Resource - logs at scope]
```

```mermaid
flowchart LR
  U1[User A] --> G1[Group: Developers]
  U2[User B] --> G1
  G1 --> R1[Role: code-writer]
  G1 --> R2[Role: read-prod-logs]
  R1 --> P1[Push to repo]
  R2 --> P2[Read log bucket]
```

## The three pieces

| Piece | What it is | Example |
| --- | --- | --- |
| **Permission** | The smallest actionable right | `s3:GetObject` on `logs/` |
| **Role** | A named bundle of permissions | `dev-read-logs` |
| **Assignment** | A user/group linked to a role, often with a scope | User A ← `dev-read-logs` *on prod* |

Effective access = **the union of all assignments** (both direct and via groups). Never let that fractal fact surprise you: nested groups multiply. "Why can they see it?" is usually answered by a cluster of groups, not a single row.

## How authority should flow

```mermaid
sequenceDiagram
  participant M as Hiring manager
  participant L as Identity team / system
  participant U as User

  M->>L: "Hire Alice as Senior Dev" (HR-driven)
  L->>L: auto-assign: Developers + dev-read-logs(on dev)
  L->>L: no prod write by default
  Note over L: removal is automatic on offboard - not a someday
```

The healthy pattern: **roles come from HR/manager input, not engineer discretion**. If a developer can mint themselves `prod-admin`, RBAC is decoration. Which brings us to the rule that hurts:

## Separation of duties and the access review

- **Separation of duties (SoD)**: the person who *writes* a payment amount must not be the one who *approves* it. RBAC encodes this as incompatible roles — assigning both is an alert.
- **Access reviews**: because roles drift (people move, gain rights "for a task", never lose them), reviews are the periodic audit: *"does this role still describe this person?"* Automate the invitation; make "no answer" become removal, never retention.

## RBAC vs ABAC (and the other letters)

| | RBAC | ABAC / conditional access |
| --- | --- | --- |
| Decides by | What role the user holds | Context attributes (device, time, location, risk) |
| Setup | Roles + assignments | Policies over attributes |
| The fail mode | Role explosion, stale grants | Policy sprawl, opaque denials |
| Where they meet | Coarse roles | Narrowing *when* the role works |

Prod: RBAC says "you may", conditional access ([policy engines](../conditional-access-and-policy-engines)) says "but only from a healthy device this hour."

## Tester checklist

- Recreate a user in a role and enumerate *effective* access including nested groups — the union must match intent.
- Break SoD: assign a user two incompatible roles and confirm the system flags the assignment.
- Run an access review as "no answer = remove" and confirm removals actually revoke, not just disappear from the review list.
- Check that *no one* can self-grant a role with prod-write; even admins go through an approval (see [PIM](../privileged-identity-management)).
