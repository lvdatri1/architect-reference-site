## What this system is

A full-stack framework (Next.js/Nuxt/SvelteKit/Remix) closes the loop between the two halves of a web app: **one codebase** where the server renders the page (fetching its own data) and the client hydrates it — so you never write a separate REST layer, fetch-from-the-client bootstrap, and a duplicated loading state by hand. The alternative it competes against is **SPA + separate API**.

```mermaid
flowchart LR
  Req[Request] --> Server[Server component / loader]
  Server --> D[(Database / API)]
  D --> Server
  Server --> HTML[Server-rendered HTML with data]
  HTML --> Client[Client hydration]
  Client --> Action[Server actions - mutations]
  Action --> Server
```

## The mental model that replaces REST glue

| | SPA + separate API | Full-stack framework |
| --- | --- | --- |
| Data for the page | Client fetches after mount (loading spinners) | Server fetches during render (no empty shell) |
| Duplicated logic | Fetch/state code on both sides | Server renders, client hydrates, same framework |
| Ops | Independent deploy of API and SPA | One app; page speed tightly coupled |
| Mutations | POST to an endpoint, refetch/optimistic update | Server actions get called, forms revalidate |
| Type sharing | Manual DTOs/Typescript types | Framework pulls types from the same data layer |

That last row is the real trade — a full-stack framework **couples** your frontend release to its data layer. Useful, but you've lost the "API as a product" boundary that a split team (or a public API) needs.

## Server components vs client components

```mermaid
flowchart TB
  subgraph Server["Server component - runs on server"]
    A[SQL/data access]
    B[Secrets, or consumers don't see]
    C[Render text, layout, static parts]
  end
  subgraph Client["Client component - 'use client'"]
    D[Event handlers, state]
    E[browser APIs, effects]
    F[Interactive widgets - hydrated]
  end
  Server --> Client
  Client --> Browser[Browser]
```

**Server components** fetch and render on the server (data stays off the wire, secrets stay server-side). **Client components** opt-in interactivity. The discipline is default-to-server, escape-hatch-to-client — refuse that split and you rebuild the SPA accidental complexity you were escaping.

## The request → happy path

```mermaid
flowchart LR
  Req[Request] -->|load + fetch| SC[Server component<br/>fetch data]
  SC -->|SSR render| HTML[Rendered HTML + RSC payload]
  HTML -->|reuse DOM| H[Client hydration]
  H -->|time-to-interactive| Ready[Interactive page]
```

## Tester checklist

- Verify the page renders server-side without JS (crawler/no-JS profile) — server components must not require client fetch to paint.
- Confirm server-only code (env secrets, DB) never leaks into the client bundle — grep the shipped JS for a canary secret.
- Check data mutation: a form submission via server action changes server state and the page reflects it after a route refresh.
- Watch cold-start latency: server work per request shifts caching and load-balancers (SSR cost vs static pre-render).
