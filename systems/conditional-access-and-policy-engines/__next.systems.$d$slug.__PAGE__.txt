## What this system is

A Zero Trust architecture executes decisions through a small engine: a **policy enforcement point (PEP)** intercepts every request, and a **policy decision point (PDP)** answers *allow, deny, or step-up* — by combining user, device, location, risk, and data signals on every request, not at login.

```mermaid
flowchart LR
  U[User / machine] -->|request| PEP[Policy enforcement point<br/>proxy / gateway / SDK]
  PEP -->|evaluate| PDP[Policy decision point]
  PDP --> S1[Identity signal]
  PDP --> S2[Device posture]
  PDP --> S3[Location / network]
  PDP --> S4[Risk / anomaly scoring]
  S1 --> PDP
  S2 --> PDP
  S3 --> PDP
  S4 --> PDP
  PDP -->|allow / deny / step-up| PEP
  PEP -->|allow + minimal scope| App[Backend app]
```

## The signals a PDP weighs

| Signal | What it proves | Can be spoofed? |
| --- | --- | --- |
| Identity (tokens + MFA) | "Who" | Requires the credential — the core |
| Device posture (endpoint compliance) | "From a healthy device" | Only if the endpoint is compromised |
| Location / IP / network | "From where" | Yes — VPN, proxies |
| Anomaly / risk score (velocity, geo, peer) | "Behaves like the user" | Indirect — heuristic, not proof |
| Trusted app / capability | "From a known appliance" | The app's own auth |

The art is **weighting**: a risk signal alone never *grants*; it only *raises or lowers* the bar. "Logged in from an unusual country + new device + admin role" is not access — it's a step-up prompt or a block.

## Per-request vs continuous evaluation

```mermaid
flowchart TB
  A[Session token issued] --> B{Per-request: PDP check<br/>every request}
  B -->|pass| C[Allow with minimal scope]
  B -->|fail live signal| D[Step-up or kill session]
  D --> E[Re-auth with higher bar]
```

- **Per-request**: stateless checks on each call (cheap, catches token/lacency changes).
- **Continuous/risk-adaptive**: background telemetry watches for changes (device just got quarantined, token used from a second IP) and downgrades live.

Where these go wrong: caching the decision at login ("trusted once, trusted forever") — which is exactly the old perimeter habit ZT is supposed to kill.

## Just-in-time and privilege elevation

Privileged access is the crown jewel. **JIT / PAM** makes admin rights *temporary and requested*: a user asks, a grant appears for a window, then it evaporates. Never "admin by default." The principle extends to service accounts too — short-lived workload credentials ([workload identity](../workload-identity-and-mtls), [PKI](../secrets-certificates-and-pki)) are the machine analog.

## Tester checklist

- Trigger a live signal change mid-session (quarantine the device) and confirm the next request is denied, *not* the next login.
- Verify step-up actually re-authenticates: reaching a sensitive scope from an abnormal context requires MFA again.
- Check that a *risk-only* signal can never authorize — only block or escalate.
- Time-box a JIT grant and confirm it expires on schedule with auditing of who requested it.
