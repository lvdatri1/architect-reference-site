## What this system is

TCP/IP is the plumbing under everything you ship. Every HTTP request, database connection, stream, and SSH session is a TCP socket riding over IP. Understanding the layers is how you read a `traceroute`, diagnose `connection refused`, and reason about why that packet arrived late.

```mermaid
flowchart LR
  C[Client app] -->|GET /users| A[Application layer]
  A -->|wrap with TCP header| T[Transport - TCP segment]
  T -->|SYN to SYN-ACK to ACK| I[Internet - IP packet]
  I -->|route hop-by-hop| L[Link - Ethernet frame]
  L -->|deliver frame| S[Server socket on 443]
```

```mermaid
flowchart TB
  A[Application layer] -->|HTTP / TLS / DNS| B[Transport layer]
  B -->|TCP segments or UDP datagrams| C[Internet layer]
  C -->|IP packets with source/dest address| D[Link layer]
  D -->|Ethernet frames on the wire| E[Physical medium]
```

## The stack, top to bottom

| Layer | Unit | What carries | Your cast of characters |
| --- | --- | --- | --- |
| Application | Message | Protocols like HTTP, DNS, TLS | NGINX, curl, browsers |
| Transport | Segment / datagram | Ports, reliability, ordering | TCP, UDP |
| Internet | Packet | IP addressing, hop-by-hop routing | IP, ICMP, routing tables |
| Link | Frame | MAC addressing on a local net | Ethernet, Wi-Fi |
| Physical | Bits | Signal on copper/fibre/radio | NICs, switches |

Each layer **wraps** the one above — the classic encapsulation dance:

```mermaid
flowchart LR
  App[GET /users] --> Transport[TCP header + GET]
  Transport --> Internet[IP header + TCP header + GET]
  Internet --> Link[Ethernet header + IP + TCP + GET + CRC]
```

## The three-way handshake

```mermaid
sequenceDiagram
  participant C as Client (port 44300)
  participant S as Server (:443)

  C->>S: SYN (seq=x)
  S->>C: SYN-ACK (seq=y, ack=x+1)
  C->>S: ACK (ack=y+1) — connection established
  C->>S: request bytes…
```

Once open, TCP gives you **ordered, reliable, retransmitted** delivery — but each byte is burdened with ACKs, congestion control, and head-of-line blocking.

## TCP vs UDP

| | TCP | UDP |
| --- | --- | --- |
| Reliability | Guaranteed, retransmitted | Fire-and-forget |
| Ordering | Ordered stream | None |
| Connection | Static handshake, connection state | Connectionless |
| Latency tax | Handshake + ACK flow control | Minimal — no state |
| Use cases | HTTP, SQL, SSH, file transfer | DNS, VoIP, video, game position, QUIC's base |

## TLS on top of TCP

TLS sits *between* transport and application. Same TCP socket, but the bytes are sealed: the handshake exchanges keys, then every record is encrypted + authenticated. That handshake is why your first request to a cold TLS endpoint feels slow — two TCP round-trips of handshake, then 2+ TLS round-trips, before the first HTTP byte.

```mermaid
flowchart LR
  TLS[Application + TLS<br/>records encrypted/authenticated] --> TCP[TCP segments] --> IP[IP packets]
```

## Tester checklist

- Reproduce a slow response: is it app latency or TCP? Packet loss is the cause of retransmits — see it in `tcpdump`.
- Confirm `TIME_WAIT`/`CLOSE_WAIT` states: a leak of `CLOSE_WAIT` connections is a server that isn't finishing sockets.
- Verify every service you expose only listens on the ports+interfaces you intend (`ss -ltnp`).
- Check TLS: certificate validity, supported ciphers, and that the private key stays server-side.
