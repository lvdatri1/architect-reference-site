Defense in depth

Layered security controls — people, process, technology — designed so that a breach at any single layer never hands the attacker the whole system.

Security ArchitectEnterprise ArchitectSolution ArchitectDevOps Engineer#security#architecture#network#zero-trust

What this system is

Defense in depth is the strategy of building many independent layers of control so that defeating one does not defeat the system — the military idea of successive rings around the objective. One firewall, one password, or one antivirus is a point defense; defense in depth assumes any single control will eventually fail and therefore never lets a single failure equal total compromise.

Each layer should also be diverse — different vendor, different mechanism, different owner — because identical layers fail for the same reason.

An attacker entering at the network layer still has to defeat host, application, and data controls before the mission-critical asset — which is why each layer gets its own detection, not just prevention.

The layers aren't a checklist to all boil down to tools — people and process are controls too (security awareness, incident response, change management), and they often fail first.

Defense in depth + Zero Trust

Defense in depth and Zero Trust are complementary, not competing:

  • Zero Trust answers who and under what conditions gets access, per request.
  • Defense in depth answers what happens when access is somehow granted anyway — the blast radius inside the network, host, and data.

In practice: Zero Trust shrinks the perimeter to the identity; defense in depth makes sure a compromised identity still can't reach the crown jewels silently.

Principles that make it work

  1. Assume failure — design for the control that will be evaded, and detect it.
  2. Diversity of mechanisms — don't stack five logins and call it depth; vary vendors, protocols, and owners.
  3. Detection for every prevention — logging, alerting, and response at each layer, feeding a SOC.
  4. Fail safe, deny by default — when a control errors, it should deny, not allow.
  5. Crown-jewel focus — deepest layers protect the data that, if exfiltrated, ends the company.

Tester checklist

  • For each layer, enumerate what it prevents and what it lets through — verify the next layer catches the overflow.
  • Confirm controls have different failure modes: same vendor signature-based detection at two layers is one layer.
  • Check that a control failure trends toward deny (fail closed), not allow.
  • Verify detection layers actually produce usable alerts and that response is exercised (tabletop a breach).
  • Look for the classic gap: a control on paper but not enforced in the critical path (e.g., encryption configured but app plaintexts to another internal service).
