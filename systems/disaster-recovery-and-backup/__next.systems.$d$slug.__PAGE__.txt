## What this system is

**Backups** recover *loss* (a deleted table, a bad deploy). **Disaster recovery (DR)** recovers *re-availability* (a whole region, an entire service) — automation plus a plan that turns "the primary is gone" into "traffic keeps serving." Every DR architecture is a trade-off between cost and the two numbers that matter: **RPO** (how much data you can lose) and **RTO** (how long you can be down).

```mermaid
flowchart LR
  Data[Data loss tolerance] --> RPO[RPO - minutes / hours / days]
  Outage[Recovery speed needed] --> RTO[RTO - seconds / minutes / hours]
  RPO --> Strategy[Choose DR strategy]
  RTO --> Strategy
  Strategy --> Cost[Cost it honestly - every level up the ladder is more expensive]
```

## The four strategies on the ladder

```mermaid
flowchart LR
  subgraph Cheap["Cheap to run"]
    A[Backup + restore] -->|hours| B[Pilot light - small always-on core]
  end
  subgraph Expensive["Expensive to run"]
    subgraph Warm["Pilot light + scaled replicas"]
      C[Warm standby - runs, not serving]
      D[Multi-site active-active]
    end
  end
  B --> C
  C --> D
```

| Strategy | What exists on standby | RTO/RPO picture | Cost |
| --- | --- | --- | --- |
| Backup + restore | Only backups/snapshots | RTO hours, RPO depends on backup cadence | Lowest |
| Pilot light | Tiniest core (DB replica, load balancer) running | RTO ~1hr, RPO minutes | Low |
| Warm standby | Full copy running, not serving | RTO tens of minutes, RPO near-zero | Medium |
| Multi-site active-active | Both sites serving live, traffic split | RTO ~seconds (failover), RPO zero | Highest |

The classic error is skipping the ladder: jumping to "active-active!" as a slogan, then discovering no one knows the runbook and nobody tested the network cutover.

## The DR flow (failover, practiced)

```mermaid
flowchart LR
  Primary[Primary region] -->|cadenced backup| Backup[Backups - immutable]
  Primary -->|sync / async replication| Replica[Replica / standby region]
  Replica -->|promote on outage| Failover[Failover decision]
  Backup -->|restore path| Failover
  Runbook[Runbook + regular drills] -->|verified steps| Failover
  Failover -->|validated in drill| Serve[RTO met - serving resumes]
```

## The truths that make a DR plan survive contact

1. **Replication lag is data loss.** "Async replication to the second region" means an outage loses the last N minutes — if that's unacceptable, you need sync, and sync costs latency on every write.
2. **RPO is not "backup schedule".** Snapshots protect *damage* (ransomware, bad deploy) — a restore from t-minus-3-hours is a loss of 3 hours. Different tools.
3. **The plan is a lie until it's tested.** An untested failover runbook is a screenplay. Draft and tabletop it, then execute real drills (kill a region in staging first).
4. **Backups belong off-path of the attackers.** Immutable/air-gapped, versioned, tested-for-restore — because the common destroy path is *inside* the compromised account.
5. **Return is the second half.** Failover without a tested *failback* plan keeps you "temporarily in the new region" for years.

## Tester checklist

- Run a restore test: pick a random week-old backup and restore it into a scratch environment — it must actually work, not just "look complete."
- Chaos drill: in staging, cut the primary region and run the runbook with a timer — stopwatch your RTO, measure the real RPO.
- Verify backup immutability: a compromised admin account cannot delete snapshots/backup copies.
- Practice failback: return traffic to the primary after recovery, within the same expectations as the forward failover.
