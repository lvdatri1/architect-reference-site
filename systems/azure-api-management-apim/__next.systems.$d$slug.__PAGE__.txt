## What this system is

Azure API Management (APIM) is a managed **front-of-house** for APIs: every call to your backend services passes through its gateway, which enforces keys, applies transformation policies, meters usage, and can mock or fail safely. It's the Azure-native answer to "put something in front of our APIs that isn't a bespoke gateway". Three surfaces matter: the **gateway** (runtime), the **publisher portal** (you/control plane), and the **developer portal** (your consumers discover and try your APIs).

```mermaid
flowchart LR
  C[Consumer app] -->|HTTPS| G[APIM gateway]
  G --> P[Policies:<br/>keys, rate limits, transforms]
  P --> B[Backend services<br/>- e.g. Function App / AKS / Logic Apps]
  C -. try + subscribe .-> Dp[Developer portal]
  Op[Publisher portal / CLI / GitHub Actions] -. configure .-> G
```

## The request path

```mermaid
sequenceDiagram
  participant C as Client
  participant G as APIM Gateway
  participant P as Policy pipeline
  participant B as Backend

  C->>G: GET /products?x-api-key=…
  G->>G: validate subscription key (or OAuth)
  G->>P: inbound policies - rate limit, quota, transform
  P->>B: forward to backend URL
  B-->>P: response
  P->>P: outbound policies - header strip, encoding
  P-->>C: response to client
```

Every request runs through the **policy pipeline** twice: once *inbound* (auth, limit, transform before hitting your backend) and once *outbound* (normalize responses, strip internal headers, add caching). That's APIM's whole superpower: behavior is added between consumer and backend without touching backend code.

## Tiers and where to put it

| Tier | Positioning | Fits |
| --- | --- | --- |
| Developer | Testing, low SLA, no SLA uptime guarantee | Dev/QA only |
| Basic | Entry production, cheaper, limited features | Small APIs, low traffic |
| Standard | Production default, SLA, more policies | Most production workloads |
| Premium | VNet injection, multi-region, >10k calls/sec | Enterprise, regulatory, DR |

APIM is typically deployed **in front of** your other PaaS (Functions, App Service, AKS, Logic Apps) — acting as the single entry point, so those backends can be locked down to accept traffic only from the gateway. Putting it *behind* your own network (Premium + VNet) is how APIM becomes an internal API router too.

## Identity: keys AND OAuth

```mermaid
flowchart LR
  subgraph Keys["Subscription keys"]
    K1[Ocp-Apim-Subscription-Key header]
    K2["Identify the caller - app, not user"]
    K3["Fine for server-to-server burst control"]
  end
  subgraph OAuth["OAuth 2.0 / JWT"]
    O1[validate-jwt policy]
    O2["Identify the human or service principal"]
    O3[Claims: roles, audiences]
  end
  C[Requests] --> Keys
  C --> OAuth
```

The three layers of APIM identity most teams need:

- **Subscription keys** prove *who's calling* (which registered app), used for metering/quotas — but they are **not** security: they travel in plaintext headers and are shared. Never rely on them as an authz boundary.
- **`validate-jwt`** policy checks the JWT a caller presents: issuer, audience, expiry, and claims. This is where *your* identity provider's tokens actually gate access.
- **Client certificates / mTLS** for machine-to-machine when keys are too weak — APIM can require the caller's cert on the connection.

## The policy DSL

Policies are declarative XML that read like no-code middleware:

```xml
<inbound>
  <rate-limit calls="100" renewal-period="60" />
  <validate-jwt header-name="Authorization" failed-validation-httpcode="401">
    <required-claims>
      <claim name="aud" match="all">
        <value>https://api.myapp.com</value>
      </claim>
    </required-claims>
  </validate-jwt>
</inbound>
```

The patterns that matter in production: **rate-limit & quota** (protect the backend), **validate-jwt** (identity), **set-backend-service** (route to a different backend per environment), **mock** (return canned responses so the frontend can build while the backend catches up), and **cors** (or better, keep CORS off and front it properly).

## Key gotchas

- **Keys ≠ authz.** Treat subscription keys as throttling/metering, never as a security perimeter.
- **The gateway adds latency** — a few ms, but every request pays it; benchmark with APIM in and out of the path.
- **Default response caching just caches**: set proper `Cache-Control` and policy `cache-store` to benefit, or you cache stale mutable data.
- **Don't let every backend call route through APIM** for high-throughput internal chatter — use it as the *front door*, not the plumbing.
- **Policy errors silently 500** unless you add error handling: put `retry`, `on-error` sections so transient backend failures have a story.

## Tester checklist

- **Auth matrix**: no key, wrong key, expired/malformed JWT, wrong audience — verify each gets the intended status (401/403/429), not a leak to the backend.
- **Rate limit**: burst past the limit and confirm 429s + headers; confirm quota resets on the defined window.
- **Transform fidelity**: a header-transform policy on outbound actually strips internal headers (server, internal IPs).
- **Backend lockdown**: call the backend URL directly (bypassing APIM) and confirm it rejects with no key.
- **Latency budget**: measure p95 through APIM vs direct to confirm the front-door tax is within your SLA.
