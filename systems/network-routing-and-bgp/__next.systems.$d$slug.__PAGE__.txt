## What this system is

Routing is how a byte for `8.8.8.8` leaves your server, crosses several companies' networks, and arrives at Google's. Every router keeps a **routing table**; on arrival it looks up the destination, matches the **longest prefix**, and forwards on. The difficult part is *populating* those tables at internet scale — that is BGP's job.

```mermaid
flowchart LR
  SV[Your server] -->|forward| ED[Your edge router - routing table]
  ED -->|longest prefix match| TR[ISP / transit AS]
  TR -->|BGP best path - AS path| DA[Destination AS]
  DA -->|local delivery| TG[8.8.8.8]
```

```mermaid
flowchart LR
  S[Your server] --> R1[Your core router]
  R1 --> R2[ISP A router]
  R2 --> R3[Transit network]
  R3 --> R4[ISP B router]
  R4 --> D[8.8.8.8 — Google]
```

## Longest prefix match

Routers don't know the whole path — only the next hop. A table entry `10.0.0.0/16 → via 10.0.0.1` and `10.0.2.0/24 → via 10.0.0.9` both match `10.0.2.55`; the **/24 (longest) wins**. This is how a default route (`0.0.0.0/0`) coexists with precise prefixes.

| Routing type | Scope | Who builds the table | Convergence speed |
| --- | --- | --- | --- |
| Static routes | Your edge, small DCs | You, by hand | Instant (but manual to fix) |
| OSPF (IGP) | Inside one AS / enterprise | Routers exchange link state | Fast (seconds), scales to ~hundreds |
| EIGRP/RIP | Cisco shops / tiny nets | Router metrics | Medium |
| BGP (EGP) | Between autonomous systems | Peers advertise prefixes | Minutes — engineered, not eager |

## BGP: the internet's glue

The internet is thousands of **autonomous systems (ASes)** — companies with an AS number and their own routing domain. BGP lets each AS tell its neighbors "I can reach `1.2.3.0/24` (via me)". Every router independently picks the best path by AS-path length, then policy, then tie-breakers.

```mermaid
sequenceDiagram
  participant A as AS64512 (your edge router)
  participant B as ISP peer AS15169

  A->>B: TCP handshake + OPEN (hold timer)
  B-->>A: UPDATE: network 8.8.8.0/24, ASPATH [15169]
  A->>A: install route, pick best path (AS path + policy)
  loop every 60s
    A->>B: KEEPALIVE
  end
  Note over A,B: session dies → route withdrawn → slow world until convergence
```

## Why routing breaks (skills worth keeping)

- **Blackholes**: a route advertised but silently dropping traffic — the classic failure when a path dies but BGP doesn't know.
- **Slow convergence**: BGP is *policy-first, speed-later*; a session flap at a tier-1 ISP can take minutes, and every dependency waits.
- **Prefix hijacking**: mis-advertised prefixes route traffic to the wrong AS (BGP has no built-in auth; [RPKI / MANRS](../zero-trust-architecture) tries to fix that).
- **AS-path prepending** trick: adding your own AS twice just to *downgrade* a path in someone's selection — traffic engineering by lying politely.

## Tester checklist

- Walk a real path with `traceroute`/`mtr` when users report latency — identify which hops add the ms.
- Verify failover: disable the primary uplink and confirm traffic shifts to the backup within your expected SLAs (seconds? minutes?).
- Use a looking glass (e.g. RouteViews, your upstream's LG) to confirm your prefixes are announced and not being suppressed.
- Confirm your static routes fall back correctly when an interface flaps — a static route to a dead next-hop *forwards into the void* unless you track reachability.
