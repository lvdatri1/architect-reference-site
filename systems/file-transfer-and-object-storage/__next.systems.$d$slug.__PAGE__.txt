## What this system is

Integrating with files is the least glamorous but most durable pattern in architecture: banks, ERPs, and legacy systems trade data as files. This page compares the traditional **drop folder** and the modern **object store + event** designs.

```mermaid
flowchart LR
  PTNR[External partner] -->|upload file| BUCK[Object storage<br/>incoming prefix]
  BUCK -->|ObjectCreated| Q[Queue: file-ready event]
  Q -->|consume| IMP[Importer: verify checksum]
  IMP -->|archive + record| RC[Move to processed/ prefix]
```

```mermaid
flowchart LR
  subgraph Classic["Classic SFTP"]
    A1[External partner] -->|upload file| B1[SFTP drop folder]
    B1 --> C1[Poll for new files]
    C1 --> D1[Parse + import]
  end

  subgraph Modern["Object storage + events"]
    A2[Producer] -->|upload to bucket prefix| B2[(Object storage)]
    B2 -->|event notification| C2[Queue / function]
    C2 --> D2[Parse + import]
  end
```

## The options, compared

| | SFTP / FTP | Shared network drive | Object storage (S3, GCS) |
| --- | --- | --- | --- |
| Push or pull | Partner pushes | Both | Push + event fell; pull allowed |
| Preset | Server, keys | VPN + mount | Managed, REST API, fine-grained IAM |
| Trigger | Poll the folder | Poll | Native event notifications (S3→SNS/SQS, GCS→Pub/Sub) |
| Scale | Moderate | Small | Massive, versioned, cheap |
| Big files | Fine | Fine | Multi-part uploads, range reads |

## The event-driven modern flow

```mermaid
sequenceDiagram
  participant P as Bank / partner
  participant B as Bucket
  participant Q as Queue
  participant W as Importer

  P->>B: upload statement-2026-08.csv (public? no - presigned / IAM)
  B-->>Q: event: ObjectCreated
  W->>Q: consume file-ready event
  W->>B: download object (checksum verify)
  W->>W: parse + import rows
  W->>B: write receipt + move to processed/ prefix
```

## The rules that keep file integrations honest

1. **Name files with immutable IDs + version/date** — nobody should overwrite a file that is mid-import.
2. **Ship checksums** (`sha256sum` file, or object checksum) and verify after download.
3. **Encrypt at rest, and ideally PGP-encrypt the file payload** for regulated data — storage encryption should not be the only barrier.
4. **Treat the folder as a claim-check (outbox)** — the file is the event; the event that *says* a file exists is a hint, not the source of truth. Always confirm the object exists before importing (at-least-once again).
5. **Move, don't delete** — archive to a `processed/` prefix so drift is auditable.

## The classic failure: "I don't see my file"

```mermaid
flowchart TB
  A[File uploaded to wrong prefix] --> X1[No event fired]
  B[File name collides - overwrite] --> X2[Partial import of mixed data]
  C[Polling poll misses during outage] --> X3[Gap never caught up]
  D[Tar file, not csv] --> X4[Import crashes, no retry]
  E[Checksum mismatch undetected] --> X5[Silent data corruption]
```

## Tester checklist

- Drop a corrupt/oversized/unexpected-format file and confirm the pipeline fails loudly into a DLQ, not silently.
- Replay by re-uploading the same name — must not import twice (dedupe by content hash).
- Test the event gap: delete the event but leave the object — the importer must still find the file (no data lose).
- Verify permissions end-to-end: the importer can only read its bucket/prefix, partners cannot.
