## What this system is

Mobile Device Management (MDM) is the control plane for the **phones and tablets** employees carry: it enrolls the device, pushes configuration profiles, delivers apps, enforces passcodes and encryption, and reports compliance. In the [endpoint security](../endpoint-security-architecture) stack it plays the enrollment + policy role for mobile, and in the [zero trust](../zero-trust-architecture) model it is what a phone must prove to get access to corporate data. The promise is a phrase every admin has repeated: **"corporate data on the device, managed."**

```mermaid

  subgraph Platform["MDM platform - the control plane"]
    ENR[Enrollment -<br/>ID + token + attestation]
    PROF[Profiles -<br/>Wi-Fi, VPN, certs, passcode]
    APP[App delivery -<br/>VPP / managed apps]
    POL[Compliance policies]
  end
  subgraph Devices["The fleet"]

  PROF --> P1
  APP --> P2
  POL --> P3
```

## The enrollment split that changes everything

Before anything else, MDM decisions hinge on one question: **who owns the device?**

| Mode | Device ownership | What MDM can do | What MDM won't touch |
| --- | --- | --- | --- |
| **Corporate-owned (COPE / fully managed)** | The org | Full profile control, app forcing, remote wipe of whole device | Nothing — entirely company-controlled |
| **BYOD (personally enabled)** | The employee | A managed-work-profile container | Personal apps, photos, SMS, location — the company enforces policy only *inside* its container |
| **Dedicated (Kiosk)** | The org, single-app | Lock the device to one app | Everything else — it's a purpose-built appliance |

The platform boundary is the entire governance story: **in a BYOD world the company manages the work container (profiles, apps, compliance inside it) but must not reach into the personal side.** Android does this via **work profiles**, iOS/macOS via **User Enrollment / managed app installation**. The architecture failure is treating BYOD as if it were corporate-owned — pushing broad "all-out" commands (full wipe) onto personal devices, which is both a legal problem and a user revolt.

## The device lifecycle

```mermaid
sequenceDiagram
  participant U as User
  participant D as Device
  participant M as MDM platform
  participant P as Policy engine

  U->>M: enroll (email + registration)
  M->>D: issue enrollment profile + identity token
  D->>M: attest device + report capabilities
  M->>D: push profiles, certs, managed apps
  D->>P: request data access (with posture)
  P->>P: check compliance (passcode, OS version, container health)
  alt compliant
    P-->>D: allow app + data access
  else device compromised / non-compliant
    P-->>D: block or restrict to remediation
  end
```

Each stage is a step in a continuous loop, not a one-time setup: enroll → configure → deliver apps → check compliance → remediate → repeat. The management plane owns the "current state" truth and the phone spends its life proving it.

## What MDM actually pushes

| Capability | What it looks like in practice | The failure mode |
| --- | --- | --- |
| **Configuration profiles** | Wi-Fi, VPN, email, certs, passcode policy pushed silently | A profile that quietly weakens settings (long passcode, no timeout) |
| **Managed app delivery** | Business apps pushed/updated from VPP/app stores, app config XML | Apps in the personal store that nobody can force-update or configure |
| **Compliance policies** | Require passcode, current OS, no jailbreak/root, container health | Compliance checks that pass on install date, not current state |
| **Remote actions** | Wipe, lock, remove work data, retire device | Wipe fired on a BYOD device (legally + reputationally toxic) |
| **Cert/identity issuance** | A device identity/cert so Conditional Access trusts it | Expired certs silently kill access with no remediation path |
| **Telemetry & inventory** | OS, model, apps, compliance status in one pane | Gaps in enrollment make the dashboard a fiction |

## MDM vs the alternatives you'll confuse it with

| Thing | What it actually is | Versus MDM |
| --- | --- | --- |
| **EMM** (enterprise mobility management) | The superset: MDM + MAM (app-level) + app config + identity | MDM is the device branch; EMM is the umbrella |
| **MAM** (mobile app management) | Manage *apps and data inside them* rather than the device | Only makes sense for BYOD — doesn't need to control the OS |
| **UEM** (unified endpoint management) | One pane for PCs *and* mobile (Intune, Workspace ONE) | The convergence trend: mobile isn't a separate silo anymore |
| **App wrapping / SDK** | Embed app-level controls (VPN in app, DLP) | Heavier than MDM config; used when you must govern app-level behavior |

The strategic read: pure MDM is increasingly folded into **UEM** (one platform for Windows/macOS/iOS/Android — precisely the [endpoint security](../endpoint-security-architecture) management plane). A modern mobile strategy asks "does the same pane manage the laptop and the phone?" rather than running a separate mobility team per OS.

## The failure modes an architect owns

- **BYOD treated as corporate-owned** — broad remote-wipe commands and deep profiles on personal devices = legal exposure and user revolt.
- **Container leak** — the managed work profile and the personal side share storage/backups, so "managed" data escapes the container into personal iCloud/Drive.
- **Compliance theater** — checks confirm *a* passcode/OS but not *the enforced current* state; jailbroken devices pass because the check looks at install-time evidence.
- **Enrollment coverage gaps** — legacy devices or shadow phones were never enrolled, so the posture and inventory story has holes that nobody tracks.
- **Expired identities** — device certs/identity tokens expire and access dies without a remediation loop, so every renewal window is an outage.
- **Human-centered drift** — pushing overly aggressive lockouts in the name of "now," until genuine users are locked out of work and find their own way around ("just use personal Gmail").

## Tester checklist

- **Enrollment round trip**: enroll a fresh device and confirm it receives the profile, certificates, and managed apps without a user manually configuring anything.
- **BYOD boundary**: on a BYOD device, confirm the company can wipe/restrict the *work container only*, that personal data survives a work wipe, and that MDM cannot see personal photos/messages.
- **Compliance realness**: set a short passcode policy; instrument the device to bypass it; confirm the policy engine actually gates access rather than trusting install-time metadata.
- **Jailbreak/root detection**: root/jailbreak a test device and confirm posture flips to non-compliant and access degrades to remediation.
- **Remote wipe drill**: wipe a corporate device and confirm the data (not just the apps) is gone and the device is unenrolled cleanly.
- **Expiry drill**: expire a device identity/cert in test and confirm the user hits a clear remediation path, not a silent black-hole of access.
