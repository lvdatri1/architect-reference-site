## What this system is

Change data capture (CDC) turns the **database's own write-ahead log** into an event stream. Instead of the application remembering to emit events on every write (and getting it wrong when it forgets), a CDC connector reads the binary log / WAL and publishes each committed change. Debezium is the reference open-source implementation; every cloud vendor has a managed cousin.

```mermaid
flowchart LR
  App[Application] -->|INSERT / UPDATE| DB[Source DB<br/>transaction log]
  DB -->|read WAL| CDC[CDC connector<br/>Debezium / cloud]
  CDC -->|publish change| T[Events topic<br/>db.customers]
  T -->|consume → re-index| S[Search index]
  T -->|consume → load| WH[Data lake / warehouse]
```

```mermaid
flowchart LR
  App[Application] -->|INSERT / UPDATE / DELETE| DB[(Source DB<br/>postgres / mysql)]
  DB -->|transaction log / binlog / WAL| CDC[CDC connector<br/>Debezium / cloud CDC]
  CDC --> T[events topic<br/>db.customers]
  T --> S[Search index]
  T --> C[Cache warm-up]
  T --> L[Data lake / warehouse]
  T --> N[Notifications]
```

## How a change becomes an event

```mermaid
sequenceDiagram
  participant App as Application
  participant DB as PostgreSQL
  participant CDC as Debezium
  participant T as Kafka topic

  App->>DB: UPDATE customers SET city='Oslo' WHERE id=7
  DB->>DB: write row image + LSN to WAL
  CDC->>DB: rewind binlog from last LSN
  DB-->>CDC: change record (id, before{Oslo}, after{Oslo})
  CDC->>T: publish "U" record, partition by PK
  S->>T: consume and re-index customer 7
```

A single **Kafka Connect** pipeline can fan out one database change to a search index, a cache, a warehouse, and downstream systems — no dual-write, no missing events, no application-level publish.

## Outbox vs CDC

| | Dual-write (app emits event) | Outbox pattern | CDC |
| --- | --- | --- | --- |
| How events get created | App publishes after write | App writes event row in the *same* DB transaction; relay publishes | Connector reads the DB log |
| Consistency risk | Event and write can split (crash between) | Atomic — safe | Atomic — safe |
| Requires app changes | Requires it at every write | One insert per event | **None** |
| Catalog of changes | Only what you chose to emit | Only what you chose to emit | **Everything**, including schema events |
| Best for | Thin events, custom semantics | Reliable business events | Bulk sync, search/cache/analytics targets |

## Where CDC hurts

- **Schema changes** become events (`ALTER TABLE` is in the log) — consumers wired to the old shape break until they migrate.
- **Initial snapshot + continuous** mode is where bugs hide: the boundary between "backfill everything" and "only-delts" is easy to get wrong (miss rows, or duplicate).
- Order is per-table (by PK in the log); deleting is represented by a "before, no after" tombstone.
- **DDL-heavy or high-write databases** produce enormous logs; you are paying to stream every write, even ones nobody consumes.

## Tester checklist

- Restart the connector mid-stream and confirm exactly-to-exactly-connection (no missing, no duplicated rows) via LSN/offset replay.
- Suspend the source DB for hours — confirm lag is bounded and recoverable rather than data loss.
- Verify tombstones (hard deletes) propagate as deletes to the target, not as stale copies.
- Test `ALTER TABLE` exposure: consumers must tolerate or visibly fail, not silently corrupt.
