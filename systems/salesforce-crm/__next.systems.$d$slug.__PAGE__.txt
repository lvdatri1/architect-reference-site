## What this system is

Salesforce is the dominant **CRM platform** — but the phrase hides a bigger fact: "Salesforce" is a development platform wearing a CRM hat. The mental model that makes everything click is **metadata, not code**: almost every customization is configuration stored as metadata (objects, fields, page layouts, flows, permission sets), and a tiny amount is real code (Apex, a Java-like language). "Building in Salesforce" means pushing metadata to an org — which is why it integrates, reviews, and *releases* differently from a codebase.

```mermaid
flowchart LR
  subgraph Org["Sales org"]
    LF[Leads] --> O[Opportunities]
    O --> C[Contracts - via CPQ]
    A[Accounts - the company view]
    CT[Contacts - people within accounts]
    CSE[Service cloud - cases]
    MK[Marketing cloud - journeys]
  end
  subgraph Platform["The platform"]
    MET[Metadata - objects, fields, flows]
    FL[Flows - automation]
    AP[Apex - the edge cases]
    UI[Lightning UI + app builder]
  end
  Org --> Platform
```

## The data model: Salesforce's five core objects, minimally

| Object | The row meaning | The question it answers |
| --- | --- | --- |
| `Account` | A company (or household/org) | "Which companies do we touch?" |
| `Contact` | A person **inside** an account | "Who is the human on the account?" |
| `Lead` | An unqualified prospect not yet an account/contact | "Who might become a customer?" |
| `Opportunity` | A potential sale with stage, amount, close date | "What is the pipeline?" |
| `Case` | A support record (Service Cloud) | "What are customers asking?" |

Every enterprise adds its **own objects** (custom objects + custom fields on those five) — `InsurancePolicy__c`, `LoanApplication__c` — which is what makes Salesforce universal: it is a CRM core with an extensible schema. The `__c` suffix is the tell: names ending `__c` are custom, names without it are platform objects. That distinction governs every "whose data is this?" argument.

## Config vs code: the two-speed model

```mermaid
flowchart LR
  subgraph Config["Configuration (no deploy - switch on in the org)"]
    OBJ[Create objects + fields]
    LAY[Page layouts + Lightning app builder]
    FL[Flows - automation]
    PERM[Permission sets - who sees what]
  end
  subgraph Code["Code (a real release pipeline)"]
    AP[Apex]
    TR[Triggers]
    VF[LWC / Lightning Web Components]
    SOAP[API integrations]
  end
  Trust{Where does the change live?} --> Config
  Trust --> Code
```

The classic governance failure: **an admin clicks a field into existence, but a developer needed it, and now a production page breaks for a segment.** Salesforce's answer exists in the platform — change sets, sandboxes, and a proper metadata release via SFDX/adopting their DevOps tooling — but the *culture* of "config is change" has to be adopted too, because a config change is a production change even when it has no deployment pipeline.

## Flows and Apex: automation decisions

| Approach | What it is | Reach for when |
| --- | --- | --- |
| **Flow** | Point-and-click declarative automation (no-code) | Classic business rules: field updates, email, record creation, approvals, screen steps |
| **Formula fields** | On-the-fly calculated values | Simple derived data, no side effects |
| **Apex** | The Java-like language | Real computation, integration to external systems, Batch/DML-heavy jobs, anything flows can't express |
| **Triggers** | Apex fire on record save | Side effects beyond what `after update` flows cover — with governor limits in mind |

The default posture that survives contact with production: **flows first, Apex only when flows hit their limits.** Flows are inspectable, admin-maintainable, and safer; Apex is faster and more powerful but becomes technical debt when overused and is subject to **governor limits** (how many SOQL queries, DML statements, and heap per request) that force batch-aware design at scale.

```mermaid
sequenceDiagram
  participant U as User / system
  participant F as Flow (declarative)
  participant A as Apex (when needed)
  participant DB as Salesforce DB

  U->>F: record saved / button clicked
  F->>F: update fields, send email, route
  alt complex or external
    F->>A: invoke Apex (bulk-safe)
    A->>DB: SOQL + DML within governor limits
  end
```

## Integration: how the rest of the world reaches in

```mermaid
flowchart LR
  ERP[ERP / finance - invoices, orders] -->|REST / SOAP API| SF[Salesforce]
  SF -->|outbound webhook| M[Middleware - OIC / Azure integration / Mule]
  M --> O[Other SaaS + data warehouse]
  BI[BI tools] -->|Analytics API| SF
  PY[Other code] --> R[REST - consumer key + secret]
  R --> SF
```

- **REST/SOAP APIs** are first-class: every object + custom object is exposable, authenticated with a connected app (consumer key + secret). This is how an ERP pushes orders and how a warehouse pulls the pipeline.
- **Outbound integrations** usually travel through middleware (OIC, Azure integration services, MuleSoft) rather than letting every tool talk directly — the same front-door lesson as API Management.
- **The special Salesforce gotcha is data fallout**: because the schema is deeply configurable, an integration that "just syncs opportunities" must handle custom fields, picklist values, and record types or it mis-maps data to the wrong picklist — test with a real shape.

## Salesforce vs ServiceNow vs CRM

| Judgment | Salesforce | ServiceNow | When you choose the other |
| --- | --- | --- | --- |
| Core purpose | Customer-facing (sales, marketing, service to customers) | Employee-facing service management | Not customer revenue — ServiceNow for internal ops |
| Data model | Sales + your objects | IT/ESM tables + CMDB | You're tracking assets, not pipeline |
| Automation | Flows + Apex | Flow designer + platform forms | Either works; pick the vendor's ecosystem |
| Fit signal | Pre-sales → revenue → support | Incident → change → asset | Division of labor: you may run both, integrated |

They overlap more than vendors admit — both are low-code record platforms with workflow engines and a "native, buy-vendors-call-it" integration story. The practical split is **customers vs employees**: [CRM systems](../crm-systems) is customer real; [ServiceNow ESM](../servicenow-esm) is employee-service real. Enterprises commonly run *both*, connected through the middleware of their choice.

## Tester checklist

- **Object drill**: create an Account → Contact → Opportunity and verify the relationship links and required-field rules actually fire.
- **Flow behavior**: a Flow-triggered field update must run on create *and* update, with the right order, and must not fire twice when the record is re-saved.
- **Governor limits**: a bulk Apex job inserting 500 records must complete within SOQL/DML limits or throw a catchable exception — not an empty silent skip.
- **Picklist fidelity**: an integration posting a picklist value must fail loudly (or map) on a mismatched value, not silently save blank.
- **API auth**: a connected-app REST call with the wrong secret must 401 cleanly, and a valid one must respect the org's permission sets (not just "API enabled").
- **Deploy parity**: a sandbox-tested configuration change must behave identically when released to production via the metadata release path.
