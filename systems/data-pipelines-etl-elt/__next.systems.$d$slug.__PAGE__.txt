## What this system is

A data pipeline moves data from source systems into analytical storage — reliably, repeatedly, and at the right freshness. The two recurring choices are **batch vs streaming** and **where you transform** (ETL: transform before loading into the warehouse; ELT: load raw, transform inside the warehouse). Every pipeline debate in a room with data engineers is really one of these two choices.

```mermaid
flowchart LR
  SRC[Source<br/>database / API / files] -->|change feed / query| EXT[Extract<br/>CDC / query / pull]
  EXT -->|batch job| PIPE[Pipeline orchestrator<br/>DAG of tasks]
  PIPE -->|stream events| LOAD[Load broker<br/>message queue / sink]
  LOAD -->|land raw| LAKE[Raw layer<br/>bronze / landing]
  LAKE -->|transform to gold| OUT[Refined tables<br/>gold for analytics]
```

```mermaid
flowchart LR
  S[Source] -->|CDC / query| E[Extract]
  E -->|batch| O[Orchestrator - DAG]
  E -->|stream| Q[(Message queue / stream)]
  O --> L[Load to raw layer]
  Q --> L
  L --> T[Transform to refined tables]
  T --> BI[BI / analytics / ML]
```

## Batch vs streaming in one table

| | Batch | Streaming |
| --- | --- | --- |
| Freshness | Hours-to-daily, on a schedule | Seconds-to-minutes, continuous |
| Volume shape | Big chunks, aligned windows | Continuous small events |
| Complexity | Simpler, retryable, well-understood | Stateful, exactly-once machinery |
| The right question | "Is yesterday's data good enough?" | "Does the report need to move in real time?" |

The architect's default is **batch**, upgraded to streaming only when a *business need* demands freshness — because every streaming pipeline adds state, ordering, and exactly-once complexity that batch just doesn't have. "We need real time" is a functional requirement, not a quality badge.

## ETL vs ELT: where does the transform live?

```mermaid
flowchart TB
  ETL[ETL - transform before load<br/>older warehouse era] --> L1[Load transformed, clean data]
  ELT[ELT - load raw first<br/>modern cloud warehouse] --> L2[Land raw cheaply, transform in-warehouse]
  L2 --> S1[Powerful engines: ray of cloud compute]
  L2 --> S2[Raw preserved for reprocessing]
```

| | ETL | ELT |
| --- | --- | --- |
| Extract | Same | Same (get the raw data out) |
| Transform | Before the load, in the pipeline tool | After the load, **inside the warehouse** (SQL) |
| Why it shifted | Warehouses were costly → clean before you pay to store | Cloud warehouses made compute cheap → store raw, transform on demand |
| Strength | Load only clean, curated output | Raw data preserved, transforms in one SQL engine, reprocess anytime |

The modern answer is usually **ELT**: land raw (bronze) in the lake/warehouse cheaply, then build refined views (gold) in SQL. It preserves the source of truth and defers modeling until you know what you need — transformation becomes a query, not a one-way trip.

## The pipeline's three contract rules

Apache Airflow-style **DAGs** (`extract → validate → transform → load → notify`) give retries, scheduling, and lineage for free. Three rules keep them honest:

1. **Idempotency** — re-running a job must give the *same* result, not double-count. Keys (natural keys or load IDs) plus full-refresh-or-upsert semantics are the guarantee. A pipeline that doubles rows when re-run is a pipeline that lies.
2. **Backfills** — at some point raw data arrives late or a transform changes. The golden-layer views must be *recomputable* from raw (that's why ELT stores raw), so a backfill = re-run transforms, not re-fetch sources.
3. **Observability** — a pipeline is only "healthy" if row counts, freshness, and schema are checked on every run. Alerts fire on "this table didn't update for 24 h", not just on job failure.

```mermaid
sequenceDiagram
  participant O as Orchestrator
  participant T as Transform job
  participant W as Warehouse

  O->>T: run task (idempotent)
  T->>W: declare transaction
  T->>W: write rows keyed by load id
  T->>W: validate: count = expected
  W-->>T: commit (re-run = same result)
  T-->>O: success + metrics
```

## Source extraction: CDC above full dumps

```mermaid
flowchart LR
  OLT[OLTP source] --> CDC[Change data capture<br/>log-based, only changes]
  CDC --> KW[(Kafka / stream)]
  KW --> PIPE[Pipeline]
```

For frequent, fresh loads the extract is **CDC (change data capture)** reading the source's transaction log (`WAL`) — you capture *changes*, not whole tables. Full-table dumps scale badly and hammer the source. But CDC is front-loaded complexity (ordering, duplicates, schema drift), so the right call for a small low-churn table is still a simple periodic full refresh — pick the minimal mechanical comedy that meets the freshness SLA.

## Tester checklist

- **Idempotency test**: run a pipeline twice and confirm row counts and aggregates are identical (no double counting).
- **Backfill test**: change the golden transform, re-run it from raw for a past time window, and confirm the time-travelable historical numbers change — not by appending.
- **Freshness guard**: pause the source feed, and confirm the alerting flags the stale table within the SLA window, not after a human notices.
- **Schema drift**: rename a source column and confirm the pipeline either transforms or *fails loudly* with validation, never loads corruption silently.
- **Exactly-once (streaming)**: deliberately restart a consumer mid-batch and verify no event is lost or duplicated end to end.
