## What this system is

Data governance is the **answer to "whose data is this, what does it mean, who may use it, and is it true?"** — enforced by a data catalog (inventory + metadata), ownership (every data set has a human answerable for it), access rules (who may see what), and quality checks (does the data match its claims). Without it, every analytics team independently builds "the real revenue" and nobody agrees on what the number means.

```mermaid
flowchart LR
  P[Data producers<br/>systems + pipelines] -->|register| C[Data catalog<br/>metadata + lineage]
  C -->|assign steward| O[Owners<br/>one answerable human per set]
  C -->|expose rules| A[Access control<br/>roles + policies]
  C -->|monitor| Q[Quality checks<br/>freshness + accuracy]
  A -->|grant| CON[Consumers<br/>BI, ML, reporting]
  Q -->|trust| CON
  CON -->|discover + feedback| C
```

```mermaid
flowchart LR
  P[Producer] -->|register + document| C[Catalog]
  C --> O[Owner / steward assigned]
  C --> A[Access policies per role]
  C --> Q[Quality + freshness monitors]
  O --> CON[Consumer trusts + uses]
  A --> CON
  Q --> CON
```

## The four pillars

| Pillar | The question it answers | What it looks like in practice |
| --- | --- | --- |
| **Catalog** | What data exists, where, and what does it mean? | Searchable inventory: tables, columns, descriptions, tags, owner |
| **Ownership** | Who is answerable for this data? | A named owner/steward per data set, reviewable and on-call for it |
| **Access** | Who may read/modify it, and why? | Role-based permissions, PII classification, approval flows |
| **Quality** | Is it current, complete, and correct? | Freshness, row-count, and validity checks with alerts |

## Ownership: one human per data set

```mermaid
flowchart TB
  DS[Data set: sales_orders] --> O1[Owner: the business lead]
  DS --> O2[Steward: the data engineer who knows the pipes]
  DS --> O3[Consumer: BI team]
  O2 --> Q[Owns: accuracy, freshness, definition of each metric]
```

"Governance" collapses into a single enforceable rule: **every data set has one named owner**, and that owner signs off on its definition, quality, and who may access it. The failure mode to avoid is an **orphan data set** — created three years ago by a team that left, trusted by nobody, cached everywhere. Orphan data is how "the real number" starts having five versions.

## The catalog is the nervous system

```mermaid
flowchart TB
  C[Catalog entry] --> M1[Metadata: owner, description, tags, PII flags]
  C --> M2[Lineage: upstream sources → this table → downstream reports]
  C --> M3[Quality: last refreshed, row count, check status]
  C --> M4[Access: who has what, pending requests]
  D[Discover: analysts search the catalog before building] --> C
```

The catalog turns "where is the customer data?" from a tribal-knowledge question into a search. **Lineage** (this table comes from `orders` via pipeline `p1`, feeds report `r2`) is what makes impact assessment possible: "if we change this column, what breaks?" Without lineage, every schema change is a roll of the dice against every report nobody can find.

## Access and classification: the security spine

- **Classify first, gate second**: mark PII (personal data), sensitive, and public at the catalog level; access rules and masking attach to the classification, not to ad-hoc roles.
- **Row/column-level security** for the sensitive columns: a consumer can read `customers` but *not* `customers.email` — masking at the catalog/engine layer, not "just don't select it."
- **The least-privilege audit**: the recurring finding is a BI group with a warehouse-wide "analyst" role that quietly reads PII they don't need. Access follows a *purpose*, granted on request, reviewed.

```mermaid
flowchart LR
  R[Request access] --> C{Is the purpose approved?}
  C -->|yes| G[Grant scoped role]
  C -->|no| D[Deny + record]
  G --> M{Need to see PII?}
  M -->|no| MASK[Masked view]
  M -->|yes| PII[Explicit, justified, logged]
```

## Quality checks: the trust contract

| Check | Catches |
| --- | --- |
| Freshness | "Last loaded 3 days ago" — the report is stale and nobody knows |
| Row-count / volume | Pipeline silently stopped or partially loaded |
| Null/validity rate | A column that's suddenly 80% null is a broken transform |
| Duplicate-key check | Double-counted fact rows |
| Definition agreement | Two dashboards disagreeing on the same metric |

**One definition per metric** is the governance hill to die on: `revenue` is either defined (same SQL, same grain, same timezone, certified in the catalog) or it isn't a metric at all. The technical trick that makes this stick is **metrics as governed artifacts** (a shared metrics/SQL layer), not copied formula snippets in each dashboard.

## Tester checklist

- Pick a data set in the catalog and verify it has: an owner, a description, quality checks, and lineage to both its source and its consumers. If any are missing, that's the governance gap.
- Try to access a PII column with a role that has no justification: it must be masked or denied, not simply "not mentioned."
- Find two dashboards that show the "same" metric and confirm they read the *same* certified definition (or surface the disagreement).
- Kill a source pipeline and confirm the freshness monitor alerts within the SLA — not after someone asks why the report is wrong.
- Verify lineage impact: identify what downstream reports would break if a column is renamed, and confirm the catalog tells you that list before the change.
