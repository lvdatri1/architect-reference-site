## What this system is

Jira (and its Atlassian siblings) is the **issue tracker** that records *what must change and why*, from epics down to tasks, and tracks each through a state machine: who owns it, whether it's in progress, whether it's verified. Its superpower is **traceability**: every commit, PR, and test points back at a ticket, so "shipped but forgotten" becomes rare.

```mermaid
flowchart LR
  E[Epic: New checkout flow] --> S1[Story 1: guest checkout]
  E --> S2[Story 2: payment validation]
  S1 --> T1[Task: API endpoint]
  S1 --> T2[Task: UI form]
  S1 --> B1[Bug: empty-cart crash]
```

## The issue types (know what each is for)

| Type | Level | When you create one |
| --- | --- | --- |
| **Epic** | Container | A big initiative spanning releases (a checkout rewrite) |
| **Story** | Vertical slice | A user-visible outcome with acceptance criteria |
| **Task** | Work item | Engineer work that isn't a user story (CI setup) |
| **Bug** | Defect | Something that should work but doesn't |
| **Sub-task** | Sibling | Breaking a story into trackable pieces |

The trap is inventing issue types every sprint — stick to Epic/Story/Task/Bug and let fields (priority, labels, sprints) carry the nuance.

## The workflow states (a state machine you control)

```mermaid
flowchart LR
  TD[To Do] --> IP[In Progress]
  IP --> CR[In Review]
  CR --> IP
  CR --> RF[Done - code merged]
  RF --> V[Verified on prod]
  V --> C[Closed]
  TD --> CN[Blocked]
  CN --> TD
```

- **In Review** means "reviewer owns it now" — move it when you *send* it, not when it's approved.
- **Done vs Closed**: `Done - code merged` is not `Verified` — a truthful team distinguishes shipped from *confirmed-in-prod*.
- **Blocked** is a first-class state with a visible cause, or it silently rots.

## Scrum vs Kanban boards

| | Scrum | Kanban |
| --- | --- | --- |
| Sprints | Fixed timeboxes (1-2 weeks) | Continuous flow, no timebox |
| Planning | Sprint goal + committed scope | Pull-based, WIP limits |
| Metrics | Velocity, burndown | Cycle time, throughput, WIP |
| Fits | Predictable product iterations | Ops/support streams (tickets, incidents) |

Both are delivery *lenses* over the same issue types — the choice is about flow, not about which tool.

## Definition of Done is the quality contract

A story is Done when its **acceptance criteria pass**, code is merged with review, CI builds and tests green, and it's **deployed and verified**. Anything less is "in progress wearing a disguise." The `verified` state exists precisely to catch stories marked Done that never got a second look in prod.

## Tester checklist

- Take a Story whose acceptance criteria exist and confirm every criterion maps to a test that actually ran (not a "should be ok").
- Follow a Bug end-to-end: reproduce → in progress → in review → verified on the fix branch vs prod.
- Audit stale states: how many issues sit in `Done - code merged` but never reach `Verified`? (that's your leak)
- Confirm the code↔ticket link both ways: the commit references the ticket, and the ticket links the PR/commit.
