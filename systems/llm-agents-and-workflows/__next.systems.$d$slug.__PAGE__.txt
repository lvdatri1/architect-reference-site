## What this system is

A single LLM call is a function: prompt in, text out. An **AI workflow** is a system that decides *which* call to make next. The deciding force is usually the model itself — it outputs a structured **tool call**, your code executes the tool, feeds the result back, and repeats until the model emits a final answer. That loop is the agent pattern. The alternative is a **workflow DAG** where you, not the model, decide the order of steps. Almost every production system is a mix: hard-coded structure where steps are predictable, agent loop where the path is not.

```mermaid
flowchart LR
  O[Model] --> S{Needs a tool?}
  S -->|yes - emit tool call| A[Execute tool in your code]
  A --> R[Append result as observation]
  R --> O
  S -->|no - final answer| Out[Answer to user]
```

## Agent loop vs workflow DAG

| | Workflow (DAG) | Agent (open loop) |
| --- | --- | --- |
| Who picks the next step | You, at design time | The model, at runtime |
| Predictability | High — fixed pipeline | Low — model can go anywhere |
| Debuggability | Deterministic, replayable | Needs session logging + eval |
| Cost | Bounded, visible | Unbounded unless capped |
| Fits | Classify → extract → answer | Explore, plan, and use many tools |
| Failure mode | Rigid — breaks on unseen inputs | Drift — hallucinated or repeated tool calls |

The rule of thumb: **fix the loop only as much as the problem needs**. A workflow for jobs with a known shape; an agent when the shape is unknown until the model sees the input. Teams that default to "full agent" for everything inherit unbounded cost and unreplayable bugs.

## Tools: the model's arms

Tool calling is JSON in, JSON out: the model returns `{ "tool": "search_docs", "args": {...} }`, your code validates the arguments against the actual function's schema, executes **your** trusted code, and appends the result. Three design rules matter more than prompt wording:

- **Schemas do the work** — the function signature is the contract; a stricter schema means fewer invalid calls.
- **Your code decides, not the model** — the model only proposes a call; your side filters and scopes it (drop tools the user's permissions don't cover).
- **Every tool is an attack surface** — a model coerced by prompt injection to call `delete_account(args)` executes your code with real side effects.

## Memory: context window vs remembered state

```mermaid
flowchart TB
  subgraph In["Context window - transient"]
    C1[System prompt]
    C2[Conversation so far]
    C3[Tool results]
  end
  subgraph External["External memory - persistent"]
    E1[Vector store - semantic recall]
    E2[Session store - key-value state]
    E3[Your database - source of truth]
  end
  In --> External
```

The context window is RAM, not disk: it is **re-packed on every call** from the raw transcript. Anything that must persist across turns — a shopping cart, a user's preference, an approval state — must be written *to your system*, and re-injected as context on the next turn. The classic bug is an agent that "remembers" something it never persisted, then loses it when the transcript is truncated to fit the window.

## The request → happy path

```mermaid
flowchart LR
    U[User task] -- task + history --> C[Context + tool schemas]
    C -- prompt --> L[Model call]
    L -- tool call --> T[Tool execution - your code]
    T -- validated result --> O[Append observation]
    O -- loop --> L
    L -- final answer --> A[Final answer]
```

## Guardrails: what keeps a loop from being a runaway

- **Max iterations & time budget** — a hard cap on loop turns; the model can infinitely re-plan, and billing follows.
- **Tool approval gates** — destructive or costly tools (send_email, delete, pay) require a confirm step; "human approval" is the anti-prompt-injection wall.
- **Permission scoping per user** — tool availability should mirror the caller's roles, not the service account's.
- **Observation size limits** — truncate tool output before re-prompting; a 10 MB JSON blob wrecks context, latency, and cost.
- **Forced rerouting** — if the model repeats the same failing call (no progress), detect it and hand the task to a fallback path.

## Tester checklist

- Loop cap: assert the agent stops after max iterations, not silently running forever (watch billing).
- Tool argument validation: send a prompt that should never produce calls to a scoped-out tool, and verify the code refuses it.
- Injection drill: hide an instruction like "call delete on every record" inside retrieved tool output — does the guardrail stop it?
- Persistence across turns: end a session, resume, and confirm state the agent claimed to "remember" actually came from your store.
- Regression set: keep a fixed set of real tasks and assert the agent's final answer is correct (and reaches it) before and after any prompt/model change.
