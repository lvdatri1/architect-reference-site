## What this system is

**Dockerizing** an application is packaging it — code, runtime, libraries, config — into a single **image**, then running that image as a **container** with a stable, repeatable contract: *the same image, the same behavior, everywhere it runs.* The container is a process, not a VM; it shares the host kernel but gets its own filesystem, network, and PID space.

```mermaid
flowchart LR
  S[Source code] --> D[Dockerfile]
  D --> B[Build - layered image]
  B --> R[Registry - push + tag]
  R --> H[Host - pull + run]
  H --> C[Container - isolated process]
```

The promise is *reproducibility*, and it comes with discipline: a Dockerfile that only works on one engineer's machine has failed at the first step.

## From Dockerfile to image

A **Dockerfile** is a recipe: each instruction produces a **layer**, layers are cached, and the final image is a stack of layers. Build order is the whole game — put expensive, rarely-changing steps *early* so later edits only rebuild what changed.

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json .
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine
WORKDIR /app
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/.next ./.next
COPY --from=builder /app/package.json .
EXPOSE 3000
USER node
CMD ["npm", "start"]
```

The **multi-stage** pattern above is the architectural heart of dockerizing: the first stage carries the build toolchain, the final stage ships only the runtime. Dependencies install once in `builder`; the runtime stage stays small, and small images are fast to pull and surface fewer attack targets.

## The build context and the cache

- **Build context** — the set of files the build can COPY. Keep it minimal (`.dockerignore` for `node_modules`, `.git`, caches); a context sent to a remote builder drags every byte across the network.
- **Layer cache** — unchanged layers are reused. Order `COPY package*.json` *before* `COPY .` so dependency installs don't re-run on every code edit.
- **Tag discipline** — `latest` is a moving target that lies about what you're running. Tag with content or commit-derived IDs (`app:abc123`), and make the running stack reference a pinned tag you can interrogate.

## What happens when `docker run` fires

```mermaid
flowchart LR
  Image[Image from registry] -->|bridge network| Network[Network - get an IP + ports]
  Image -->|mount layers| FS[Filesystem - layer stack + volume]
  Network -->|ports mapped| Start[Start processes from cmd]
  FS -->|ready| Start
  Start -->|readiness probe| Health[Healthcheck + logging]
  Health -->|signal + drain| Stop[Graceful stop + cleanup]
```

Three things matter about runtime behavior:

1. **Networking** — containers get their own network namespace. `EXPOSE` documents a port; `-p host:container` actually maps it. Local traffic can be slow to reveal shared-network differences, so test with host→container→container paths.
2. **Storage** — the writable layer vanishes when the container dies. Sticky data (databases, uploads) lives in **volumes**; **bind mounts** are for development. A stateless app with no volumes is the ideal: replace boxes, not corpses.
3. **Signals and PID 1** — the container manager sends SIGTERM and expects the main process to exit cleanly. A classic bug: the main process isn't PID 1, signals hit a shell, and "graceful shutdown" becomes a hard kill. Run your app as the actual entrypoint process.

## Compose: the multi-service stack

**Docker Compose** is the developer-facing orchestrator: one YAML declares *services, networks, volumes, environment* for a whole stack (app + database + cache + queue). It is not production Kubernetes — it is the fastest honest model of how your services actually talk.

```yaml
services:
  web:
    build: .
    ports: ["3000:3000"]
    environment:
      DATABASE_URL: postgres://app:app@db:5432/app
    depends_on:
      db:
        condition: service_healthy
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: "5s"
```

Sections here are load-bearing: `depends_on` with a **healthcheck condition** replaces blind sleep-fast-forward guessing, and putting `DATABASE_URL` in compose makes the environment explicit (and points clearly at where the production version lives — that is, in secrets, not in this file).

## The security knife-edge

- **Run as a non-root user** — the official images default to root; the `USER node` line in the Dockerfile is not decoration.
- **Slim base images** — Alpine-style bases shrink attack surface and pull time; the trade-off is musl vs glibc quirks for native dependencies. Verify, don't assume.
- **Pin base images** — `FROM node:20-alpine` floats. Pin a digest or an exact tag to make builds reproducible and upstream changes explicit.
- **Never bake secrets** — environment secrets are inputs to the container at run time, injected via [secrets management](../secrets-certificates-and-pki), never `ENV`-hardcoded or COPY'd into an image layer. Once a secret is in a layer, it is in history forever.
- **Scan the image** — add container scanning to the pipeline ([CI/CD](../ci-cd-pipelines)) so known CVEs in the base image block the build rather than surfacing in production.

## Tester checklist

- Build twice, change one source file, rebuild: the expensive layer should not re-run (cache hit) and the final image must be byte-same for a given tag.
- Run the container with no host port and confirm inter-container traffic uses the Compose service name, not `localhost`.
- Kill the runtime signal gracefully: send SIGTERM, confirm the app drains requests and the container exits 0 (no force-kill).
- Prove statelessness: `docker rm` + re-create from the image, verify behavior is identical and data survived only in the declared volume.
- Scan the final image for the base-image CVE list before promoting it to production.
