## What this system is

A webhook is the opposite of polling: instead of your service asking "anything new?", the source *pushes* an HTTP request to your URL when an event happens. Payments, CI, GitHub, Slack, and CRMs all deliver webhooks — and the failure modes are all on the delivery side.

```mermaid
flowchart LR
  Event[Event happens] -->|webhook triggered| S[Source]
  S -->|POST + signature| R[Receiver<br/>verify HMAC + timestamp]
  R -->|verify first| Q[Dedupe by event-id + persist]
  Q -->|consume| W[Process async]
  W -->|reply fast| OK[200 after persist]
  S -->|timeout / 5xx| Retry[Retry with backoff]
  Retry -->|resend same event-id| S
```

```mermaid
flowchart LR
  A[Event happens] --> B[Source delivers POST to your URL]
  B -->|signature header| C[Verify HMAC + timestamp]
  C -->|valid| D[idempotency check]
  D -->|has seen - skipped| E[Already processed]
  D -->|new - process + ack fast| F[Reply 200]
  B -->|timeout / 5xx| G[Retry with backoff]
  G -->|exhausted| H[Dead-letter for manual replay]
```

## Pull vs push

| | Pull (polling) | Push (webhook) |
| --- | --- | --- |
| Latency | Bounded by poll interval | Near-real-time |
| Complexity on source | Low (a GET endpoint) | Signature + retry infra |
| Receiver outage | Safe — stays in queue | Source must retry |
| Firewalling | Easy | Needs an inbound endpoint exposed |
| Real-time fit | Batch-friendly | Event-driven systems |

## Delivery semantics your handler must survive

- **At-least-once**: sources retry on timeouts and 5xx (and sometimes on 2xx that arrive too late). Your handler *will* see duplicates.
- **Retries with backoff**: typical schedulings are exponential (e.g. 1m, 5m, 10m…) over hours; a delayed retry can arrive after the requirement changed.
- **Ordering** is not guaranteed across retries, and often not across events. Do not build on "the newer event always arrives after".

```mermaid
sequenceDiagram
  participant S as Source
  participant R as Your receiver
  participant Q as Your queue / store

  S->>R: POST /webhooks/orders (X-Webhook-Signature, X-Event-Id)
  R->>R: verify signature (HMAC over raw body)
  alt signature invalid
    R-->>S: 400 reject (no retry storm)
  else valid
    R->>Q: dedupe by X-Event-Id + persist
    R-->>S: 200 OK (accept after persist, not just after parse)
  end
  alt no 200 in time
    S->>R: retry POST (same X-Event-Id)
  end
```

## Security checklist for the receiver

1. **Verify the signature** over the *raw request body* using a shared secret (`HMAC-SHA256`), timing-safe compare.
2. **Check timestamp** to reject replay windows.
3. **Don't block** the callback on slow downstream work — accept → persist → process async.
4. **Return 2xx fast and only after persisting** the dedupe key; a fast 200 *before* state is saved is how events get lost.

## Tester checklist

- Replay a previously-sent webhook (same `X-Event-Id`) — must be a no-op that still returns 200.
- Corrupt the signature and confirm the receiver returns 4xx and logs without processing.
- Time the receiver: force slow processing and confirm the source's retry does not cause a duplicate side effect.
- Verify the dead-letter/monitoring path exists — retries should be visible, not silent.
