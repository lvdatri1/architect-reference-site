## What this system is

A "mobile framework" answers one question: **who draws the UI?** Native code targets each OS's own toolkit. React Native runs JS that talks to *native widgets*. Flutter ships a custom engine that *paints every pixel* in Dart. Hybrid web apps run a website inside a browser view. The framework you pick decides performance, store review, and what your team must know.

```mermaid
flowchart TB
  A[Build a mobile app?] --> B{One or both platforms?}
  B -->|single platform now| C[Native - SwiftUI / Compose]
  B -->|both, shared team| D{How much native feel}
  D -->|pixel control + perf| E[Flutter - own engine]
  D -->|reuse JS skills| F[React Native - native widgets]
  D -->|ship web-like fast| G[Hybrid - Ionic / capacitor]
```

## How each renders, compared

| | Native (SwiftUI / Compose) | React Native | Flutter | Hybrid (Ionic) |
| --- | --- | --- | --- | --- |
| Renders with | OS widget toolkit | Native widgets via JS bridge | Its own engine (Skia) | WebView / the web |
| UI parity with iOS/Android | Exact | High | Near-exact (may diverge slightly) | Web look and feel |
| Performance | Best | Great (bridge cost on hot paths) | Great, consistent | Depends on the device browser |
| Your team needs | Swift + Kotlin | JS/TS + React | Dart (new) | Web/JS as-is |
| Code sharing | None | One RN codebase | One Dart codebase | One web app reused |

The decision is really **"which constraint do I hold cheapest"**: store UX parity, raw performance, or team skills. There is no universal answer — there is a list of things each choice surrenders.

## The runtime model (why Flutter and RN behave differently)

```mermaid
flowchart LR
  App[Your app code] -->|React Native path| JS[RN: JS virtual tree]
  App -->|Flutter path| Dart[Flutter: Dart UI model]
  JS -->|complex scroll + gestures| Native[RN bridge to native widgets]
  Dart -->|60fps rendering| Engine[Flutter engine paints layers]
  Native -->|one codebase| Stores[Release to stores]
  Engine -->|one codebase| Stores
```

## The non-rendering true costs

- **Native platform code leaks in**: push notifications, biometrics, deep links, BLE, camera — all eventually need platform-specific code/plugins; that barrier decides whether sharing still pays.
- **Store review is the CI/CD** you cannot pre-trigger: an app package is an artifact you release through a human gate (App Store review, Play policy).
- **Offline, backgrounds, permissions** behave per-platform and per-framework — the classic "works in dev on iOS, dies on Android doze."

## Tester checklist

- Run the same tour on iOS and Android with real devices (or a coverage farm): gestures, back-button, keyboard, dark mode.
- Force offline, then background the app (Android Doze / iOS suspend) and verify state and notifications survive.
- Perf budget on the emulator: list scroll at 60fps, cold start under a threshold — compare RN vs Flutter honesty on your own app, not the marketing.
- Test store-readiness early: review guidelines around payments, permissions, and data collection — failing late is expensive.
