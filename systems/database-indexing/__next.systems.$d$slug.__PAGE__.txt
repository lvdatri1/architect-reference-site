## What this system is

Without an index, the database reads every row of a table to answer a `WHERE` clause. With an index, it walks a tree of keys in `O(log n)` steps. This page makes the trade-offs visible.

```mermaid
flowchart TB
  subgraph Query["Query planner"]
    Q[SELECT * FROM orders WHERE user_id = 42]
  end

  subgraph WithoutIndex["Without an index"]
    A1[Seq scan] --> A2[Read tables block by block]
    A2 --> A3[Filter every row]
    A3 --> A4[Return 3 rows after reading 1,000,000]
  end

  subgraph WithIndex["With a B-tree index"]
    B1[Index lookup on user_id] --> B2[Find key 42 in tree]
    B2 --> B3[Follow table row pointers]
    B3 --> B4[Read only matching rows]
  end

  Q -->|planner chooses| WithoutIndex
  Q -->|planner chooses| WithIndex
```

## How a B-tree works

- The index is a balanced tree of keys kept **in order**.
- Point lookups follow one root-to-leaf path — roughly `log(n)` reads.
- Range queries (`>=`, `BETWEEN`) walk the leaf nodes, which are linked in a sorted chain.
- Each leaf node stores a pointer to the actual heap (data) row: “the index (not the data) is the book’s table of contents.”

```mermaid
flowchart LR
  R[Root: user_id 20 - 60] --> L1[Node: 20 - 40]
  R --> L2[Node: 41 - 60]
  L1 --> K1[key 42]
  L1 --> K2[key 37]
  L1 --> K3[key 20]
  K1 --> D1[(Row A)]
  K2 --> D2[(Row B)]
  K3 --> D3[(Row C)]
```

## When indexes hurt

| Symptom | Cause |
| --- | --- |
| Slow inserts / updates | Every write updates the index too |
| Huge storage footprint | Index rows copy the key + pointer |
| Planner ignores index | Low selectivity — it would read most rows anyway |
| `NULL` surprises | `NULL` often isn’t in a B-tree index; `WHERE x IS NULL` may scan |

## Things a tester should check

- Does the access path show **index scan** or **seq scan** in the query plan (`EXPLAIN`)?
- Are there duplicate or unused indexes (index usage statistics)?
- Does changing the data volume change query time linearly (missing index) or logarithmically (index present)?
