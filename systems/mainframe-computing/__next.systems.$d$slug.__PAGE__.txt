## What this system is

A **mainframe** (IBM System z is the surviving member of the family) is a massive, purpose-built transactional computer that has quietly run central banking, insurance, airlines, social security, and customs systems for decades. It does not look like a server rack: it is a single, hardened machine with dedicated I/O channels, a hypervisor that runs Linux and z/OS instances side by side, and an operating system — **z/OS** — whose design (address space, data sets, batch, security) predates everything modern by forty years.

Its superpower is **deterministic throughput under heavy, mixed, concurrent transactions**. A mainframe routinely pairs the speed and reliability of a big distributed system with a *single* reconciliation point: one machine, one consistent view, no eventual consistency, no network partition. That is why banking records still live here — and why the fastest mainframe applications outperform distributed clones while the outage history is scandalously good.

```mermaid
flowchart LR
    USERS[Online users - CICS transactions] --> ZOS[z/OS - one operating system]
    BATCH[Batch jobs - JCL, night runs] --> ZOS
    ZOS --> DBZ2[Db2 for z/OS - shared data]
    ZOS --> VSAM[VSAM files - legacy data store]
    ZOS --> CICSP[CICS transaction server]
    ZOS --> RACF[Security - RACF, access lists]
```

## The two computings: online and batch

| Mode | Technology | Character |
| --- | --- | --- |
| **Online (CICS)** | Transaction server fronting DB2; each request is a short, atomic **transaction** | Sub-second, high concurrency, thousands of transactions per second |
| **Batch (JCL)** | COBOL programs driven by Job Control Language, run at night | Huge file/DB sweeps, end-of-day runs, statements, settlements |
| **Coupling** | z/OS workloads exchange via shared data + messaging (MQ) | Strong consistency between the two modes |

The *batch window* is the existential constraint: banking day ends, the batch must finish before the new day opens. Adding transaction volume shrinks the window; shrinking the window is where modernization pressure comes from — and why mainframe teams are obsessed with **parallel batch, restartability, and checkpoints**.

## The mainframe stack, top to bottom

```mermaid
flowchart TB
    TX["Customers / channels<br/>ATMs, web, cards"] -->|request| CICS["CICS transaction server<br/>maps request to transaction"]
    CICS -->|dispatch| COBOL["COBOL programs<br/>business logic"]
    JCL["Batch - JCL jobs<br/>nightly runs"] -->|night batch| COBOL
    COBOL -->|SQL / I/O| DB2["Db2 / VSAM<br/>the shared data"]
    DB2 -->|z/OS + RACF grant/deny| Z["z/OS + RACF<br/>security + integrity"]
```

The practical truth for an architect: a modern mainframe these days is really a **hybrid z/OS + Linux box** — modern cloud layers (Linux, containers via the hypervisor) sit beside the z/OS core, and the replatforming strategy leans on that split rather than cutting to zero.

## Why it survived — and when it makes sense

| Mainframe strength | What it still buys |
| --- | --- |
| Single consistent ledger | No distributed-systems reconciliation burden for money |
| Massive concurrent I/O | Thousands of transactions per second on one machine |
| Deterministic reliability | Failure rates legacy teams trust and regulators know |
| Data completeness | The whole bank in one Db2/VSAM estate — no dark data shards |

Keep a mainframe when the core is transactionally critical and the cost of moving is higher than the cost of keeping (upgrades, licensed software, skilled staff). Modernize when the *batch window* or the *integration surface* has become the bottleneck that no amount of in-place tuning fixes.

## The strangler, done right

Modernizing a mainframe is a **strangler transformation**: new capabilities live in modern services that talk to the mainframe by API; the legacy transaction stays the source of truth until the day it can be cut over. The pattern:

1. **Publish the core** — expose the CICS/COBOL transactions as APIs (COBOL via CICS Web Services / z/OS Connect), so new front-ends call it not directly but through a service.
2. **Move one capability at a time** — take order fulfillment, or statement generation, off the mainframe into a new service that reads via API and writes back to Db2.
3. **Replicate and compare** — run old and new side by side, compare results, then flip.
4. **Grow the Linux side** — the z/OS core shrinks; the Linux/container partitions and an off-mainframe data replica grow, until the last z/OS workload cuts to the new estate.

The two non-negotiables: **never break the daily batch window during a cutover**, and **keep the single-ledger property** — if you move the ledger off mainframe, you accept the distributed reconciliation you were avoiding all along.

## Tester checklist

- Online atomicity: a CICS transaction must commit or roll back fully — verify an injected failure mid-transaction leaves the Db2 state exactly as before.
- Batch restartability: kill a batch job mid-run; restart must resume from the last checkpoint, not redo the whole window.
- Window discipline: the batch completes inside the fixed night window at padded volume; a new online transaction during batch must not corrupt the shared data.
- Data integrity: Db2/VSAM totals reconcile with downstream (settlements, statements) exactly — one ledger, no drift.
- Security: RACF access is denied/explicitly granted as configured; a request through the API gateway is still subject to RACF rules, not bypassed.
- Strangler parity: old and new services produce identical outputs during parallel run; the flip is reversible.
- Cutover safety: the first day after a capability moves off the mainframe, the batch window still closes on time with the new estate.
