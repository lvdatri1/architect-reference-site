## What this system is

Two open protocols standardize how AI systems attach to the world, and they are complementary rather than competing:

- **MCP** (Model Context Protocol, Anthropic → open spec) is the *USB-C of AI*: an agent connects once and can use any tool, data source, or API exposed through a standard server — without per-integration glue.
- **A2A** (Agent2Agent, Google → Linux Foundation) is the *email of agents*: independent agents discover each other, delegate work, and exchange results as peers, across frameworks and companies.

MCP is how an agent *touches tools and data*. A2A is how an agent *partners with other agents*. A real stack uses both: your agent calls MCP servers for its own tools while delegating to remote agents over A2A.

```mermaid
flowchart TB
  subgraph Agent["Your agent"]
    Host[Host - model and session]
    MCPC[MCP client]
    A2AC[A2A client]
  end
  MCPC -->|JSON-RPC - stdio or HTTP| S1[MCP servers - tools and resources]
  A2AC -->|agent card + tasks| S2[Remote agents - A2A servers]
  Host --> MCPC
  Host --> A2AC
```

## MCP: agent-to-tool

Three roles: the **host** (your AI application — it owns the model and the conversation), **clients** (one per server connection), and **servers** (each exposes **tools** for actions, **resources** for data, and **prompts** for reusable templates). The data layer is **JSON-RPC 2.0**; the transport is **stdio** for local processes or **streamable HTTP** (Server-Sent Events for streaming) for remote servers, authenticated with OAuth.

```mermaid
sequenceDiagram
  participant H as Host
  participant C as MCP client
  participant S as MCP server
  H->>C: start session
  C->>S: initialize with capabilities
  S-->>C: supported capabilities
  C->>S: tools/list
  S-->>C: tool schemas
  C->>S: tools/call
  S-->>C: result
  C-->>H: context for the model
```

Security is built into the shape: the **host is the enforcement point**. Capability negotiation decides what each side supports; servers are isolated from each other and cannot read the full conversation. This is also where the well-known failure modes live — every tool is an attack surface, so the host must gate calls with consent and permission checks, not the model.

## A2A: agent-to-agent

A2A treats agents as opaque peers. Four concepts do the work:

| Concept | What it is |
| --- | --- |
| **Agent Card** | A JSON discovery document at `/.well-known/agent-card.json`: identity, description, skills, endpoint, and auth requirements |
| **Task** | A stateful unit of work: `submitted → working → input-required → completed / failed / canceled` |
| **Message** | One turn of a conversation, carrying **parts** (text, file, or structured data) |
| **Artifact** | A deliverable produced by a task, also composed of parts, streamable incrementally |

```mermaid
sequenceDiagram
  participant A as A2A client agent
  participant R as A2A remote agent
  A->>R: GET /.well-known/agent-card.json
  R-->>A: capabilities and endpoint
  A->>R: send message with task
  R-->>A: task submitted
  R-->>A: working with streaming updates
  R-->>A: artifact updates
  R-->>A: task completed
```

`input-required` is the mechanism for a remote agent to ask for clarification mid-task, which is what makes long-running delegation interactive. Tasks can be polled, subscribed to over SSE, or pushed to a webhook when they outlive a connection. The primary binding is **JSON-RPC 2.0 over HTTPS**, with gRPC and REST as alternates — deliberately boring plumbing.

## The two layers, compared

| | MCP | A2A |
| --- | --- | --- |
| Relationship | Client-server: an agent *uses* a server | Peer: agents *delegate* to agents |
| Unit of work | Tool call / resource read | Task with a lifecycle |
| Discovery | Capability negotiation during initialize | Agent Card at a well-known URL |
| Transport | stdio, streamable HTTP | JSON-RPC over HTTPS, gRPC, SSE, webhooks |
| Authentication | OAuth for remote HTTP | OAuth 2.0 |
| Data exchanged | Tool arguments and structured results | Messages and artifacts with typed parts |
| Trust | Servers stay isolated from the conversation | Remote agents are untrusted peers |

If MCP is "how an agent uses a capability", A2A is "how agents partner on a task". An MCP server is reachable *inside* an agent's world; an A2A remote lives outside it, behind an agent card.

## How they compose

```mermaid
flowchart LR
    U[User task] -- task --> AG[Your agent - host + model]
    AG -- context --> MC[MCP client]
    MC -- tool calls --> MS[MCP servers - tools and data]
    AG -- delegate --> AC[A2A client]
    AC -- task + artifacts --> RS[Remote agent - card + tasks]
```

The rule of thumb: **expose capabilities as MCP servers, front agent pairs with A2A cards.** A support agent might use MCP against the ticket system internally, then delegate an order-status lookup over A2A to a billing agent on the other side of a company boundary.

## Cross-boundary security notes

- **MCP**: the host gates every tool call — a compromised or prompt-injected server must not reach tools the user didn't consent to. Verify tool schemas before they influence execution.
- **A2A**: remote agents are *untrusted peers*. Validate the agent card, authenticate with OAuth, and route delegated work — especially anything that cascades back into your MCP tools — through the user's permission scope, not a broad service account.
- **Supply chain**: capability metadata (tool definitions, agent cards) is attacker-influenceable; treat changes as config and review them.

## Tester checklist

- **MCP flow**: stand up a mock server and verify `initialize` → `tools/list` → `tools/call`, including streaming over streamable HTTP.
- **Isolation**: confirm one MCP server cannot read another server's context or the full conversation.
- **A2A lifecycle**: exercise `submitted → working → completed` plus `failed` and `canceled`, and confirm terminal states end any stream.
- **Resilience**: kill a task mid-run and reconnect — `get`/subscription must recover state without losing artifacts.
- **input-required**: a remote agent asking for clarification mid-task must surface to the user and resume the same task.
- **Auth**: reject calls to remote MCP/HTTP endpoints and A2A remotes without valid credentials.
- **Cross-layer scope**: a task delegated over A2A must not let the remote agent invoke MCP tools beyond the requesting user's permissions.
