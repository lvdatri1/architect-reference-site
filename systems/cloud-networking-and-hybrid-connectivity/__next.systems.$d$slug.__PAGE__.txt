## What this system is

Cloud networks are software. A **VPC** (AWS) or **VNet** (Azure) defines an isolated IP space; you split it into subnets, decide what goes public vs private, connect regions by **peering/transit**, and reach your office through **VPN or private dedicated links**. The skill is trading connectivity against exposure.

## How VPCs talk to each other (and to you)

| Way to connect VPC/VNet | What it gives | Watch-outs |
| --- | --- | --- |
| **Peering** | Two networks, direct private IP | No transitive hops - peering is point-to-point (VPC) |
| **Transit gateway / hub** | A hub routes to many spokes | Hub becomes a SPOF - rightsize + protect it |
| **Private endpoint / VPC endpoint** | Reach a service by private IP without traversing the internet | Endpoint per service; watch costs |
| **VPN gateway / tunnel** | Site-to-site encrypted over internet | Best-effort throughput, does not beat dedicated |
| **Dedicated connect** (DX / ExpressRoute) | Private, stable, high-throughput to provider | Slow to provision, dedicated cost |

Rule of thumb: **hub-and-spoke with a transit layer**, private endpoints for sensitive services, and public internet only for what must be public. The add lecture: peerings don't cross regions silently and peering is not transitive — if you have many VPCs, use the hub, don't chain peerings.

## Private endpoint vs "just a security group"

```mermaid
flowchart LR
  subgraph PublicPath["Public - SG / NSG permit list"]
    A1[App] --> R1[Elastic IP / LB]
    R1 --> DB1[(Database public route)]
  end
  subgraph PrivatePath["Private - endpoint only"]
    A2[App in VPC] --> E2[Private endpoint IP in-VPC]
    E2 --> DB2[(Database - no public IP at all)]
  end
```

A security group/NSG *filtering* a public-facing DB is still on the public internet — one mis-rule and it leaks. A **private endpoint** takes the resource entirely off the public surface: only in-network traffic can reach it. Prefer endpoints for anything holding data.

## Security basics that differ per platform

| | AWS | Azure |
| --- | --- | --- |
| Network filter | Security group (stateful, per-ENI) + NACL (stateless, per-subnet) | NSG (stateful, per-subnet/NIC) + Azure Firewall |
| Private service | VPC/VPC endpoint | Private Link |
| Site-to-site | VPN Gateway, Transit Gateway + VPN | VPN Gateway, vWAN |
| Dedicated | Direct Connect | ExpressRoute |

The stateful/stateless difference is the classic test question: **SGs stateful** (reply traffic auto-allowed), **NACLs stateless** (you author both directions).

## Tester checklist

- Verify peering/transit has no accidental transitive path (A → hub → B must not let A reach B unless intended).
- Scanner proves a private-endpoint database has *no* public IP assigned anywhere.
- Cut the dedicated link and confirm VPN failover resumes within your RTO (dual-path designs should be tested, not hoped).
- Check that egress from spoke VPCs is bounded (via NAT/egress filtering), not "any destination OK."
