Password storage and hashing

Why passwords are never stored 'in plain', how salted slow-hashes like bcrypt and Argon2 work, and why fast hashes like SHA-256 are wrong.

DeveloperBackendSecurity Architect#security#database

What this system is

Never store passwords — store irreversible, salted, slow hashes. A leaked database of hashes must be useless to attackers. This page walks the two moments that matter: signup (hash and save) and login (recompute and compare).

Rendering diagram…

The three rules

  1. Hash, don't encrypt. Encryption is reversible (with a key) — an attacker who steals the key reads every password. Hashing is a one-way trip.
  2. Salt with a random value per user. Otherwise two identical passwords hash identically → rainbow tables crack them all at once.
  3. Use a deliberately slow KDF (key-derivation function). Speed is the enemy:
AlgorithmBuilt to beVerdict for passwords
SHA-256, MD5fast, for integrity❌ too fast — billions of guesses/sec on a GPU
bcryptmemory-light, iteration-scalable with cost factor✅ standard choice
Argon2idmemory-hard, resists GPUs✅ modern winner (won Password Hashing Competition)
scryptmemory-hard✅ good alternative
plain text—❌ catastrophic

Verify without killing the app

  • Constant-time comparison (crypto.timingSafeEqual): if comparison timing reveals how many bytes matched, a remote attacker extracts the hash character by character.
  • Cost factors drift: as hardware improves, raise the bcrypt cost / Argon2 memory on each login, and re-hash the user's password when you get a chance.
  • Pepper is optional: a secret appended server-side (not in DB) turns DB-only theft into useless data; but it complicates rotation, so treat it as defense-in-depth only.

Legends and traps

  • "We MD5 it" — instant rainbow-table material.
  • "We base64 encode it" — that's obfuscation, not security.
  • "We encrypt passwords with AES" — see rule 1: the whole DB often ships with the key in config.
  • "bcrypt is slow" — reduce iterations for the same user only via salted re-hash after login, never by disabling hashing.

Tester checklist

  • Dump the user table: confirm zero reversible values and per-row distinct salt/hash.
  • Log in with a wrong password and confirm failure timing is indistinguishable from success timing.
  • Rotate the cost factor and confirm existing users can still log in (hash upgrade path).
  • Confirm no password ever appears in app logs, metrics, or error messages.
