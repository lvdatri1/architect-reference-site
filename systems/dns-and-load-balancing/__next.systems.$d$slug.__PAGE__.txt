## What this system is

DNS is the phone book that turns `api.example.com` into an IP so TCP/IP can route your bytes. Load balancing is the traffic cop in front of many servers that answers "which healthy server handles this request?" They work together: DNS points to one or more LB VIPs, the LB spreads load across a pool.

```mermaid
sequenceDiagram
  participant B as Browser
  participant R as "Recursive resolver"
  participant A as "Authoritative DNS - example.com zone"
  participant LB as "Load balancer VIP"
  participant P as "Healthy server pool"

  B->>R: A? api.example.com
  R->>A: root -> .com -> zone
  A-->>R: A 203.0.113.10 TTL
  R-->>B: answer
  B->>LB: connect VIP
  LB->>P: L7 health check
```

```mermaid
flowchart TB
  Browser[Browser] -->|query api.example.com| R[Recursive resolver]
  R -->|root → .com → example.com NS| A[Authoritative nameservers]
  R -->|answer: 203.0.113.10 + TTL| Browser
  Browser -->|connect 203.0.113.10| LB[Load balancer VIPs]
  LB --> S1[App server 1 + health]
  LB --> S2[App server 2 + health]
  LB --> S3[App server 3 + health]
```

## DNS resolution, step by step

```mermaid
sequenceDiagram
  participant C as Client
  participant Res as Recursive resolver (ISP/local)
  participant Root as Root (. )
  participant Com as .com zone
  participant Auth as auth DNS for example.com

  C->>Res: A? api.example.com
  Res->>Root: A? api.example.com
  Root-->>Res: refer to .com server
  Res->>Com: A? api.example.com
  Com-->>Res: refer to example.com authoritative
  Res->>Auth: A? api.example.com
  Auth-->>Res: A 203.0.113.10, TTL 60
  Res->>C: answer + TTL 60
  Note over C,Res: every hop caches per TTL — the "propagation delay" is your TTL
```

Practical rules: **TTL** is your blast radius for changes. Lower it to 60 *before* a migration, not during. `CNAME` aliases follow — but a root domain can't be a CNAME (use a provider alias). Never let DNS *round-robin* multiple LB pools without validating: it's oblivious to health.

## L4 vs L7 load balancing

| | L4 (TCP/UDP-based) | L7 (application-aware) |
| --- | --- | --- |
| Looks at | IP + port (e.g. tcp/443) | HTTP request — host, path, cookie, header |
| Routing | Per connection | Per request: `/v1` → pool A, `api.` → pool B |
| Features | Fast, protocol-agnostic | TLS termination, retries, rate limit, auth, WAF |
| Health probe | TCP connect / SYN | HTTP status checks, full transaction probes |
| Unit of failover | Connection | Request |

```mermaid
flowchart LR
  In[Internet] --> LB7[L7 LB<br/>TLS term + routing]
  LB7 --> P1[Pool /v1 · API servers]
  LB7 --> P2[Pool /v2 · canary]
  LB7 --> P3[Static · CDN]
```

## What health checks really guarantee

A LB is only as smart as its health probe. An *up* service that is actually stuck (thread pool exhausted, DB down) still passes a TCP probe — probe **depth** must match risk: L7 HTTP 200 with a timeout, spread on slow pools, and a **drain** before shutdown so in-flight requests finish (gracefully transition the node to unhealthy without killing live connections).

## Tester checklist

- Change a record with a short TTL and confirm caches expire on schedule (`dig @resolver name +tcd` honestly, all resolvers are their own universe).
- Force a node unhealthy and confirm the LB removes it and re-routes new requests (and drains in-flight on the real thing).
- Check TLS termination is where you think: LB-terminated means the LB sees plaintext and must be inside your trust boundary.
- Verify DNS failover paths for your VIPs themselves (multiple A/AAAA, or DNS-based Geo-DNS) — DNS is a dependency, not a given.
