## What this system is

The Oracle database is the workhorse of enterprises that predate the cloud era — and a surprising number that don't. It's a relational database, but the real Oracle is not the SQL you write; it's the **architecture** underneath it. When a DBA says "redo," "undo," "RAC," or "Data Guard," they're describing the machinery that makes a single database a *system* you can run, recover, scale, and fail over.

```mermaid
flowchart LR
  APP[Application<br/>SQL via JDBC / OCI] -->|SQL| SGA[SGA: shared pool<br/>buffer cache]
  SGA -->|parse + execute| BG[Background procs<br/>LGWR, DBWR, CKPT]
  BG -->|dirty blocks| DATA[Datafiles]
  BG -->|LGWR: log force| REDO[Redo log groups]
  SGA -->|read-consistency + rollback| UNDO[Undo tablespace]
```

```mermaid
flowchart LR
  App[App - JDBC / OCI / SQL*Plus] --> SGA[SGA<br/>shared pool + buffer cache]
  SGA --> LGWR[LGWR - log writer]
  SGA --> DBWR[DBWR - database writer]
  LGWR --> REDO[(Redo log groups<br/>ARCH goes to archive logs)]
  DBWR --> DATA[(Datafiles + undo tablespace)]
  DATA --> CKPT[Checkpoint - sync points]
```

## The architecture that makes Oracle Oracle

| Moving part | What it does | Why you'll hear it in the room |
| --- | --- | --- |
| **SGA** | Shared memory: parse cache, buffer cache, redo buffer | "Tune the buffer cache" = most of Oracle performance talk |
| **Redo log** | Append-only journal of every change, written *by LGWR before commit returns* | "Redo too small" / "log switch storm" — commit latency is redo latency |
| **Undo** | Old copies of rows for read-consistency + rollback | "ORA-01555 snapshot too old" kills long-running readers |
| **Checkpoint** | Progress marker tying disk writes to redo | Crash recovery replays redo from the last checkpoint |
| **Datafiles** | The actual on-disk tables/indices (in tablespaces) | "Tablespace full" — a full datafile fails every insert |
| **PGA** | Per-session memory for sorts/hashes | Sort-to-disk = where big queries slow down |

**Commits are redo-bound, not datafile-bound.** When you `COMMIT`, Oracle guarantees the redo (not the data) reached disk — the datafile write happens later, batched by DBWR. That's the single idea that explains both Oracle's speed and its recovery behavior: it can always *replay* what redo recorded.

## Read consistency: undo is the time machine

```mermaid
sequenceDiagram
  participant U as Session A (updater)
  participant S as Session B (long reader)
  participant DB as Oracle

  U->>DB: UPDATE row X (new value)
  DB->>DB: keep old value in undo
  S->>DB: SELECT row X
  DB->>DB: use undo to serve pre-update version
  DB->>S: consistent snapshot, no locks needed
```

A long-running `SELECT` sees a **consistent snapshot**, not "whatever's on disk right now." Oracle builds that snapshot from current data + undo. This is why a big report doesn't block writers, and why "snapshot too old" appears when undo gets overwritten (usually an undo tablespace or retention setting).

## RAC: one database, many instances

```mermaid
flowchart LR
  Client[App / connection pool] --> L1[Instance 1 - node A]
  Client --> L2[Instance 2 - node B]
  Client --> L3[Instance 3 - node C]
  L1 --> CF[Cluster - shared cache / interconnect]
  L2 --> CF
  L3 --> CF
  CF --> ST[(Shared storage - ASM / SAN)]
```

Oracle Real Application Clusters (RAC) runs **multiple instances against one shared database** on shared storage. The payoff is high availability (a node dies, the others keep serving) and scale (more instances = more CPU/memory). The catch: it's shared-storage architecture, so everything funnels through the shared disk — and performance depends on the interconnect and on avoiding cross-instance traffic on hot blocks.

**Standby is a different animal —** that's **Data Guard**:

```mermaid
flowchart LR
  P[Primary database] -->|redo shipped live| DB[Data Guard:<br/>physical / logical standby]
  DB -->|apply, near real-time| S[(Standby database)]
  FAIL[Primary outage] -->|switchover / failover| DB
```

Data Guard keeps a **standby database** current by shipping redo and applying it. Physical standby = identical block-for-block copy (good for recovery + read-only reporting); logical standby = re-applied SQL (read/write ready but coverage varies). RAC and Data Guard are complementary: RAC covers instance/node loss inside one cluster; Data Guard covers database *site* loss and is half of every DR story.

## The parts people forget

- **Tablespaces ≠ schemas.** A tablespace is physical (datafiles on disk); a schema/user is logical. "Put the table in a big tablespace" and "give the app its own schema" are different actions.
- **PL/SQL is compiled, not interpreted.** Stored procedures run in the DB; calling one from the app avoids shipping SQL text but couples your logic to Oracle.
- **NLS/Oracle dates.** `TO_DATE`/`TO_CHAR` with explicit format masks; date arithmetic is in days. The classic "dates off by one" is an NLS format mismatch, not a timezone bug.
- **Licensing is the real constraint.** Enterprise Edition features (RAC, Data Guard, partitioning, compression) are separately licensed. Architecture decisions are often *licensing* conversations first.

## Tester checklist

- Force a kill (-9) on a session mid-transaction and confirm other readers are unaffected (relying on undo, not locks).
- Watch a `COMMIT` return while LGWR is deliberately delayed — understand why commit is redo-bound, and what `COMMIT NOWAIT` changes.
- Trigger a checkpoint and confirm recovery replays only from the last checkpoint, not from the beginning.
- Create a runaway long-running `SELECT` and update rows underneath it; confirm the reader sees a consistent snapshot and -- if undo overrites -- you get ORA-01555.
- For RAC: kill one instance and confirm the service stays up; for Data Guard: do a switchover and a real failover and time it.
