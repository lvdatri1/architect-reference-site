## What this system is

Server-side rendering is not a framework checkbox — it is a **pipeline**. A browser request is a query into a machine that resolves the route, loads data, walks the component tree, and emits HTML as a byte stream; the client then layers interactivity on top through **hydration**. Understand where the pipeline is slow and you understand every SSR performance story. Understand what it does *not* do — there is still a JS bundle to fetch — and you understand why SSR is not "the end of SPAs".

```mermaid
flowchart LR
  Req[Request] --> Resolve[Resolve route]
  Resolve --> Load[Load data on server]
  Load --> Render[Render component tree to HTML]
  Render --> Stream[Stream HTML + data]
  Stream --> Client[Browser parses HTML]
  Client --> Hydrate[Hydration - attach handlers and state]
  Hydrate --> Done[Interactive page]
```

## The pipeline, step by step

| Stage | What happens | Cost you pay |
| --- | --- | --- |
| Route resolve | Server maps the URL to a component/preload entry | Library dispatch, negligible |
| Data load | Server-side fetching (DB, APIs) *before* HTML exists | **The dominant latency for dynamic pages** |
| Render | Component tree executes to a static HTML string | CPU work on the server |
| Stream | HTML flushes progressively; shell paints first | Chunked transfer, edge buffering |
| Hydrate | JS re-attaches state and event handlers to existing DOM | Bundle download + parse on the client |
| Settle | Event handlers active; page truly interactive | Framework reconciliation |

The trap: "$ quickly because it is server-rendered". Server HTML is **inert** — it has no state and no event handlers until shipped JS hydrates it. First byte can be fast while time-to-interactive still waits on the client bundle. SSR moved work from the browser to the server; hydration keeps some of it right where it was.

## SPA shell vs server HTML

| | SPA / CSR | SSR |
| --- | --- | --- |
| First request returns | Empty `<div id="root">` + many `<script>` tags | Full HTML with content, plus scripts |
| Data for the page | Fetched client-side after mount (spinner) | In the HTML payload, already rendered |
| No-JS / crawler | Blank shell | Content visible |
| Route changes | Client router swaps views, no full reload | Full round trip (unless client router is layered on) |
| Worst latency | Bundle parse + fetch waterfall | Server data load + bundle parse |

The mix — **client-side transitions on top of server-rendered HTML** — is literally the modern full-stack framework play: SSR the first paint, then replace the document with client-routed views so navigation never reloads.

## Hydration and its failure modes

```mermaid
flowchart TB
  Server[Server HTML] --> Match{Client-side render matches?}
  Match -->|Yes - reuse DOM nodes| OK[Hydrate in place - fast]
  Match -->|No - hydration mismatch| Warn(Console mismatch warning) --> Rerender[Framework discards and re-renders on client]
  Rerender --> Flicker[Flash of wrong content + wasted work]
```

A hydration mismatch is a debug canary: dates in the server's timezone, random values, `localStorage` reads, browser-width-dependent UI. Every mismatch means the framework throws away server work and re-renders on the client — the opposite of what SSR was for. Alternatives to full hydration: **partial hydration** (hydrate only islands), **resumability** (serialize the full app state, skip the replay of render work), and **streaming with selective hydration**.

## Streaming: the shell-vs-data split

Streaming SSR flushes the static frame of the page the instant it renders, while slow data-loading sections stream in on placeholder plates (React Suspense-style). TTFB drops to near-static speed; TTI only waits on the data the user actually needs. The cost: the response is a **chunked stream**, so downstream caches must flush headers correctly and you cannot simply store the whole response.

## Caching and the CDN edge

Per-request SSR is the expensive mode — the origin re-renders on every hit. Caching turns a dynamic page into a static asset:

```mermaid
flowchart LR
  Origin[Origin server renders] --> H{Cache headers}
  H -->|Cache-Control: max-age, stale-while-revalidate| Edge[CDN edge cache near user]
  Edge --> Blade[Cached HTML to every user]
  Edge -->|Expired, background refresh| Origin
  H -->|no-store / private| Direct[Per-user response, no caching]
```

- **Public/short TTL** — pages that change rarely (blog posts, marketing) become edge-served static assets.
- **stale-while-revalidate** — serve the cached copy instantly, refill in the background; users never see a cache stampede.
- **no-store** — anything personalized (dashboards, checkout) must reach the origin every time; this is where SSR and SPA costs converge.
- **Edge rendering** — move the render itself to a CDN function (edge runtime) so the origin only supplies data; cuts round-trips for global audiences.

## The request → happy path

```mermaid
flowchart LR
  Req[Request] -->|GET + route| Load[Server<br/>resolve + load data]
  Load -->|data ready| Render[Server render HTML]
  Load -->|streaming partial| Stream[Stream HTML + data]
  Render -->|full HTML| Paint[First paint<br/>inert HTML]
  Stream -->|script tags| Hydrate[Hydration JS bundle]
  Paint -->|TTI after parse| Ready[Interactive page]
  Hydrate -->|attach handlers| Ready
```

## Tester checklist

- Measure TTFB and TTI **separately**; SSR pages with a heavy bundle look fast on TTFB and lie on TTI.
- Render in a no-JS/crawler profile: content must be in the initial HTML, not injected after a fetch.
- Grep the browser console for hydration mismatch warnings — every one is discarded server work.
- Verify streaming reaches first paint before the slowest data plate resolves, and that the response is a proper chunked stream.
- Check cache headers on a personalized route: `no-store` must prevent an edge cache from serving another user's dashboard.
- Load-test the origin with a cold cache to confirm `stale-while-revalidate` avoids a wall-of-render stampede.
