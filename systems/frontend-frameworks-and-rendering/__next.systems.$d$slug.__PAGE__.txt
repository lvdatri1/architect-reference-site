## What this system is

A "website framework" is really a bundle of two decisions: **which UI library** (React, Vue, Svelte, Angular) and **where the HTML is produced** (client, server, at build time). The second decision dominates your metrics — first byte, searchability, interactivity — so it comes first.

```mermaid
flowchart TB
  U[User request] --> D{Where is HTML produced?}
  D -->|browser only| CSR[CSR / SPA - empty shell + JS]
  D -->|server per request| SSR[SSR - full HTML from server]
  D -->|at build time| SSG[SSG - prebuilt HTML files]
  D -->|hybrid| ISR[ISR / islands - mix on demand]
```

## The rendering models, compared

| | CSR / SPA | SSR | SSG | Islands |
| --- | --- | --- | --- | --- |
| HTML arrives | Empty shell | Full page | Full page, eager | Full page with lazy areas |
| First paint | After JS loads | Fast (server) | Fast (static) | Fast, then hydrate lazily |
| SEO / no-JS | Weak | Good | Best | Good |
| Dynamic data | Best (fetch on client) | Server fetch per request | Needs rebuild/revalidation | Hybrid |
| Framework fit | Anything, SPA-style | Next/Nuxt/SvelteKit | Static sites, docs, blogs | Astro, islands architecture |

The trap is memorizing "SSR = slow": the real question is **time-to-interactive**. A CSR SPA can *paint* fast but needs a JS round-trip to *work*; SSR trades server work for control and renders text for crawlers.

## The framework map

| | React | Vue | Svelte | Angular |
| --- | --- | --- | --- | --- |
| Paradigm | Components + hooks | Components + reactive refs | Compile-to-JS, no runtime diffing | Opinionated framework (DI, RxJS) |
| Ecosystem | Largest, hardest to choose | Balanced, batteries | Growing, fast and light | Batteries-included, strict |
| Learning curve | Steep (meta-frameworks) | Gentle | Gentle | Steep (concepts first) |
| Best for | Teams hiring React devs today | Quick, maintainable SPAs | Small bundles, animated UIs | Enterprise teams wanting structure |

In practice the library barely decides the page-speed story — the **meta-framework** does (Next.js/Nuxt/SvelteKit/Astro). Choose the framework for your team's skills; choose the rendering model for your traffic.

```mermaid
flowchart LR
  B[Browser request] -->|first paint, SSR/SSG| HTML[Server / build<br/>HTML]
  B -->|load shell, SPA| Bundle[JS bundle from CDN]
  HTML -->|reuse DOM| H[Hydration<br/>attach handlers]
  Bundle -->|until JS parses| H
  H -->|time-to-interactive| Ready[Interactive page]
```

## Tester checklist

- Measure time-to-first-byte vs time-to-interactive separately — the SPA-vs-SSR argument is decided by both, not one.
- Verify SSR pages render with JS disabled in the crawler profile (SEO) and compare to the SPA story.
- Check hydration failures: a mismatched client/server render throws console errors — the suite's runtime-health check catches them.
- Prove a metrics claim: run Lighthouse/Web Vitals on the same page under CSR, SSR, and SSG builds.
