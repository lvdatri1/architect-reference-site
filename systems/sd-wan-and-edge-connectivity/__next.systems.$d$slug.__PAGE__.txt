## What this system is

Wide-area networking decides how your offices, data centers, and cloud VPCs reach each other. **SD-WAN** is the modern answer to the old trade-off between MPLS (guaranteed but expensive) and VPN-over-the-internet (cheap but best-effort): overlay tunnels across *multiple* ordinary internet links, centrally orchestrated, steering traffic per-application.

## WAN evolution

| | MPLS | VPN / IPsec over internet | SD-WAN |
| --- | --- | --- | --- |
| What you buy | Carrier-managed QoS between sites | Ordinary broadband links | Broadband + software overlay |
| Reliability | Guaranteed SLA | Single best-effort link | Multiple links, seamless failover |
| Cost | High per-site | Low | Low, plus edge hardware |
| Steering | Static/carrier policy | Per-device config | Application/cloud-aware, centrally managed |
| Today's role | Legacy gold standard | Simple point-to-point | Standard for multi-site + cloud |

## How the overlay works

```mermaid
flowchart LR
  A[App traffic: MS Teams / API / SAP] --> B[Policy engine<br/>classifies traffic]
  B --> C{Best path for this app?}
  C -->|real-time voice| D[Lowest jitter link]
  C -->|batch ingest| E[Highest throughput link]
  D --> F[IPsec tunnel over link A]
  E --> G[IPsec tunnel over link B]
  F --> H[Hub / cloud gateway]
  G --> H
```

The three pieces you should be able to explain:

1. **Edge device** per site — terminates multiple underlay links (fiber, cable, 5G) and builds encrypted tunnels.
2. **Controller** — central brain that pushes policies and monitors link health; without it you have fancy VPNs, not SD-WAN.
3. **Application-aware policy** — MS Teams goes on the low-latency path, bulk sync on the cheap one. When a link dies, sessions re-route over the survivor in seconds.

## The cloud edge

SD-WAN reaches cloud the same way it reaches HQ — a tunnel into the cloud provider's gateway (Direct Connect / ExpressRoute) or a cloud-hosted SD-WAN instance. Consistent policy across office, data center, VPC. This is why enterprises retire remote-office VPN concentrators: the branch device *is* the VPN endpoint, covered by [zero trust](../zero-trust-architecture) as a bonus.

## Tester checklist

- Drill a failover: kill the primary link mid-session with a live VoIP/streaming call and confirm no drop (or a sub-3s re-route, per your SLA).
- Verify path steering really diverges per app — a bulk job and a voice call must take different underlays *simultaneously*.
- Check that cloud-tunneled traffic follows the same policies as branch traffic (one policy engine, not two).
- Confirm underlay link quality metrics (jitter/loss/throughput) are visible and alert on degradation — not just on outages.
