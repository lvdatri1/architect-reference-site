## What this system is

The **SOC** is the team and tooling that watches your estate for attacks, not outages. Its pipeline: collect security telemetry (cloud audit logs, endpoint, network), correlate it in a **SIEM** to surface detections, triage and investigate, then respond through **SOAR** playbooks — containment, remediation, and a post-incident review that makes the next one cheaper.

```mermaid
flowchart LR
  Tele[Telemetry: CloudTrail / Activity Log, GuardDuty / Defender, EDR, flow logs] --> SIEM[SIEM: ingest + correlation]
  SIEM --> De[Detection rules / detection engineering]
  De --> Triage[Triage - real or noise?]
  Triage --> SOAR[SOAR playbook: isolate, revoke, snapshot]
  SOAR --> IR[Incident response process]
  IR --> Retro[Post-incident review feeds the loop]
  Retro --> De
```

## The threat-detection funnel

```mermaid
flowchart TB
  SRC[Telemetry sources] -->|stream| SIEM[SIEM - correlation]
  SIEM -->|alert on rule hit| TRI[Triage + investigate]
  SIEM -->|auto-playbook for known case| SOAR[SOAR playbooks]
  SIEM -->|confirmed incident| CON[Contain + remediate]
  TRI -->|escalate| CON
  SOAR -->|automated steps| CON
  CON -->|learn| LESS[Post-incident review]
```

## The core components and cloud-native mapping

| Layer | Job | AWS native | Azure native |
| --- | --- | --- | --- |
| Audit trail | Who did what, immutable | CloudTrail + S3 | Activity Log + log retention |
| Automated detection | Known attack patterns | GuardDuty, Security Hub | Microsoft Defender for Cloud, Sentinel |
| SIEM | Ingest + correlate + alert | OpenSearch / Elastic | Microsoft Sentinel |
| SOAR | Playbook-ify response | Step Functions (custom) | Sentinel automation rules |
| EDR / posture | Endpoint + cloud posture | Systems Manager, Inspector | Defender for Endpoint |

The pattern to teach: **cloud audit logs are the base truth** — if you keep nothing else, keep CloudTrail/Activity Log immutable and searchable, because every DR and SOC answer starts there.

## The SOC's five responsibilities

1. **Detect** — detection rules must be tested, tuned, and updated; an alert that never fires (or always fires) is a failed detection.
2. **Triage** — fast "is this real + how bad?" — the funnel where alert fatigue is defeated (or wins).
3. **Respond** — playbooks with *documented automated* steps: isolate the instance, revoke the key, snapshot the volume before cleanup.
4. **Hunt** — proactive looking for what detections miss (assume-breach hunting, baseline anomalies).
5. **Improve** — every incident ends in a review; the output is improved detections, playbooks, and controls.

## The detection-playbook loop

```mermaid
flowchart TB
  A[New attack / suspicion] --> B[Write detection - SIEM rule]
  B --> C[Wire to playbook - SOAR]
  C --> D[Test with positive + negative cases]
  D --> E[Deploy to monitoring]
  E -->|fires on real case| F[Incident - run the loop again]
  F --> A
```

## Tester checklist

- Feed a known-bad pattern (an exfiltration-shaped download, a failed-admin logon storm) and confirm SIEM correlation → alert → playbook fires within your SLA.
- Filter the noise: a legitimate admin task must not trip the detection (false-positive test on both sides).
- Tabletop a pivot: attacker has an IAM key and a compute box — does the playbook isolate the box *and* revoke the key *and* snapshot before evidence is lost?
- Audit-drift check: can a compromised identity delete the audit log store? If yes, fix the trust boundary (immutable, separate account).
