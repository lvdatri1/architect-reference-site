## What this system is

ITIL splits operations into two parallel tracks. **Incident management** restores service after an unplanned interruption — speed is the whole game. **Problem management** attacks the *unknown root cause* behind one or many incidents — permanence is the whole game. Every incident gets restored; only the repeat or unexplained ones earn a problem record and the root-cause work that follows.

```mermaid
flowchart LR
  I[Incident - restore now] --> P[Prioritise<br/>impact + urgency]
  P --> R[Resolve + verify]
  R --> C[Close + review]
  P -.->|repeats / unexplained| PR[Problem record]
  PR --> RC[Root cause analysis]
  RC --> KE[Known error + workaround]
  KE --> FX[Fix via change management]
```

The two tracks hand off deliberately: an incident can be closed as "workaround applied" while the problem underneath stays open. That separation is what lets you restore fast *and* stay honest that a real fix is still owed.

## The incident lifecycle

1. **Detect** — a monitoring alarm, a user report, or a ticket from a linked team. Detection latency is the first source of lost time.
2. **Log + categorise** — every incident gets a record; categorisation decides *which team* owns it.
3. **Prioritise** — impact (how many users / services are hurt) × urgency (how fast it hurts) → priority and SLA clock.
4. **Diagnose** — find the firing component and the likely cause; escalate when the diagnosis stalls or the SLA clock runs hot.
5. **Resolve + restore** — apply a fix *or a workaround*; the goal is restoration, not permafix. Verify the service actually recovered.
6. **Close + review** — the incident is closed only when the user confirms and monitoring confirms. A review decides whether a problem record is owed.

## The priority matrix

| Priority | Impact | Urgency | Example | SLA target |
| --- | --- | --- | --- | --- |
| **P1 - Critical** | Whole service down | Immediate | Payments processing fails | Minutes to respond, <4h restore |
| **P2 - High** | Major feature down | Fast | Checkout broken for all users | 15min respond, same-day |
| **P3 - Medium** | Workaround exists | Normal | One region slow, others fine | Hours, ticket tracked |
| **P4 - Low** | Cosmetic | Low | Wrong label in UI | Best effort, queue |

Priority drives where the SLA clock runs and who gets woken. The classic failure is a P3 that nobody re-grades into a P1 when usage spikes — **re-prioritisation is a first-class step**, not an afterthought.

## Escalation: functional and hierarchical

- **Functional escalation** — the record moves to a *different team* that is better equipped (network, database, vendor) because the diagnosis crossed a boundary.
- **Hierarchical escalation** — up the management chain because the SLA is at risk, resources are contested, or the user-facing impact demands an exec to unblock.

The rule: escalate to **enable**, not to comfort. Each step should add a decision-maker or a skilled responder, and the incident record has to travel with the handoff.

## The incident-to-problem pipeline

```mermaid
stateDiagram-v2
  [*] --> DetectionLogging
  DetectionLogging: Detection + logging
  DetectionLogging --> CategorisePrioritise: logged
  CategorisePrioritise: Categorise + prioritise
  CategorisePrioritise --> Escalate: no diagnosis / SLA at risk
  CategorisePrioritise --> DiagnoseResolve: owned + worked
  Escalate: Escalate - SLA at risk
  Escalate --> DiagnoseResolve: extra muscle
  DiagnoseResolve: Diagnose + resolve
  DiagnoseResolve --> RestoreVerify: fix or workaround
  RestoreVerify: Restore + verify
  RestoreVerify --> CloseReview: verified
  RestoreVerify --> ProblemRecord: repeat / unknown cause
  CloseReview: Close + review
  ProblemRecord: Problem record - find root cause
  CloseReview --> [*]
  ProblemRecord --> [*]
```

## Problem management: the cure loop

1. **Problem record** — opened from a major incident, a flood of similar incidents, or a proactive trend scan.
2. **Root cause analysis** — the technique (5 whys, fishbone, log forensics) matters less than actually *reaching* a cause you can point at.
3. **Known error + workaround** — the name ITIL gives a diagnosed cause that still has no fix: document it and drop it in the knowledge base so the next incident resolves in minutes, not hours.
4. **Fix via change** — the actual repair goes through [change and release management](../itil-change-and-release-management) so it lands with the same governance as any other production change.

The output that compounds is the knowledge base: every ticket is a candidate for a runbook entry, and every known error buys the incident desk time later.

## Tester checklist

- Run a P1 drill: alarm → incident → first response inside the SLA target, with the record surviving the handoff.
- Forced a repeat-alarm scenario (same alert twice in a day) and confirm the second incident auto-links to the existing problem record.
- Verify a workaround-closed incident correctly leaves its problem record open and re-flagged at review.
- Re-grade test: change an incident from P3 to P1 and confirm the SLA clock and escalation path actually re-arm.
- Audit escalation: pick a closed major incident and confirm every handoff preserved the timeline and added a named owner.
