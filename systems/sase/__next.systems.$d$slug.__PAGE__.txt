## What this system is

**SASE** (Secure Access Service Edge, pronounced "sassy") is the convergence of two previously separate stacks — **SD-WAN** for connectivity and **cloud-native security** — delivered as one cloud service from points of presence (PoPs) distributed around the globe. Gartner coined it in 2019: instead of a WAN that back-hauls all traffic to a data center and applies security there, each branch and remote user connects to the *nearest* PoP, where identity-based policy is enforced once, in a single pass, before routing to SaaS, private, or public internet destinations.

The security half — ZTNA, SWG, CASB, and FWaaS — is sometimes sold on its own as **SSE** (Security Service Edge). SASE = SD-WAN + SSE.

```mermaid
flowchart LR
    U[Remote / roaming user] --> POP1[SASE PoP<br/>nearest region]
    B[Branch office] --> POP2[SASE PoP]
    C[Cloud VPC] --> POP2
    POP1 -->|single-pass policy| E[Policy engine<br/>identity, device, risk]
    E -->|ZTNA| PRIV[Private apps / data center]
    E -->|SWG / CASB| SAAS[SaaS apps]
    E -->|FWaaS| INTERNET[Public internet]
```

## The problem SASE replaces

| Classic stack | Effect |
| --- | --- |
| Traffic hairpins to the corporate data center | Remote users and branches travel long, slow paths |
| VPN concentrates access inside the network | Any VPN user can reach the whole "trusted" LAN |
| Security appliances at a central choke point | Not where the traffic actually is anymore |
| Disconnected point products | SWG, CASB, firewall — separate consoles, same gaps |

SASE answers three shifts at once: users everywhere (not in the office), apps in the cloud (not in the DC), and a per-user, per-device world where the old perimeter is gone.

## The four security functions

| Function | Acronym | Role |
| --- | --- | --- |
| Zero Trust Network Access | ZTNA | Per-user, per-app access to private apps — no network-level "inside" |
| Secure Web Gateway | SWG | Filters direct-to-internet web traffic, URL and content policy |
| Cloud Access Security Broker | CASB | Policy and posture on sanctioned SaaS — DLP, shadow-IT discovery |
| Firewall as a Service | FWaaS | Cloud-native firewall and IDS/IPS where the traffic flows |

Identity is the load-bearing wall: SASE policies are **identity + device posture + destination**, evaluated at the PoP nearest the user rather than at a perimeter you no longer control.

## One pass through the PoP

```mermaid
flowchart LR
  subgraph Dest["Destinations"]
    SAAS["SaaS<br/>via CASB/SWG"]
    PRIV["Private app<br/>via ZTNA"]
    INT["Public internet<br/>via FWaaS"]
  end
  U["Remote user<br/>+ device posture"] -- "nearest PoP" --> POP["SASE PoP<br/>single-pass engine"]
  POP -- "evaluate identity + policy" --> ID["Identity & posture<br/>SSO + conditional access"]
  ID -- "classified SaaS" --> SAAS
  ID -- "least-privilege app access" --> PRIV
  ID -- "filtered web" --> INT
```

## When SASE makes sense

- **Distributed and remote workforces** — users connect to the nearest PoP instead of a distant VPN concentrator.
- **Cloud-heavy estates** — most traffic is SaaS/public; back-hauling to a DC is pure waste.
- **Branch modernization** — replace router + multiple appliances with one SD-WAN + security edge.
- **Zero Trust rollouts** — ZTNA is the natural on-ramp; identity is already the perimeter.

## Tester checklist

- Verify policy is *identity-based*: a compromised-but-authenticated user still only reaches their allowed apps (ZTNA), not the network.
- Confirm policy is enforced on the **first** pass through the PoP — no split-tunnel escape hatch from SD-WAN to internet bypass.
- Check DLP/classification behavior for unmanaged (BYOD) devices hitting SaaS.
- Test PoP failover: can a session survive a PoP region going down without re-authenticating the user?
- Review the shadow-IT/CASB discovery feed — is it actionable, or just noise?
- Validate that a revoked device loses SASE access promptly (posture is not a binder at login only).
