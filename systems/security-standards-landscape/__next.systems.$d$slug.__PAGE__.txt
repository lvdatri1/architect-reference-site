## What this system is

Security standards get conflated because they answer *different* questions. The fastest way to use them well is to know the axis: **design** vs **implementation** vs **operation** vs **compliance**.

```mermaid
flowchart TB
  subgraph Design["Design: how should access be shaped?"]
    ZT[Zero Trust - NIST SP 800-207<br/>never trust, verify every request]
    STRIDE[STRIDE threat modeling<br/>find design flaws early]
  end

  subgraph Implementation["Implementation: how should it be coded?"]
    OWASP[OWASP Top 10 + ASVS<br/>the weaknesses and their fixes]
    CIS[OWASP SAMM / CIS Benchmarks<br/>process + config hardening]
  end

  subgraph Operation["Operation: are we actually protected?"]
    CSF[NIST Cybersecurity Framework<br/>govern, identify, protect, detect, respond]
    MITRE[MITRE ATT&CK<br/>adversary playbooks for detection]
  end

  subgraph Compliance["Compliance: can we prove it to auditors?"]
    ISO[ISO 27001<br/>ISMS, audit cycle]
    SOC[SOC 2<br/>trust-services attestation]
  end

  Design --> Implementation --> Operation --> Compliance
```

## One standard per question

| Standard | Answers | When you reach for it |
| --- | --- | --- |
| **Zero Trust (NIST 800-207)** | "How is access architected?" | Greenfield design / perimeter redesign |
| **STRIDE** | "Where are the design flaws?" | Every system before heavy implementation |
| **OWASP Top 10 / ASVS** | "Which implementation bugs matter?" | Coding, code review, pentest prep, CI gates |
| **NIST CSF** | "How mature is our whole program?" | Annual maturity assessment, board reporting |
| **MITRE ATT&CK** | "What attacks should we detect?" | SOC playbooks, red-team tests, detection engineering |
| **ISO 27001** | "Does an ISMS exist and get audited?" | When customers/venue require certification |
| **SOC 2** | "Can we attest the security of your service/vendor?" | Vendor due diligence, SaaS exporting |

## The triangle nobody draws

These are **not alternatives**; they compound. A mature org runs all four layers:

```mermaid
flowchart LR
  A[Architecture: Zero Trust + STRIDE] -->|decides| B[Build: OWASP + SAMM]
  B -->|runs on| C[Run: NIST CSF + ATT&CK]
  C -->|certifies| D[Prove: ISO 27001 + SOC 2]
  D -->|feeds back lessons| A
```

The classic mistakes:

- **Marrying one layer.** "We have SOC 2" says nothing about whether your code is safe (nor does Zero Trust); "we passed OWASP scan" says nothing about governance.
- **Reading the wrong axis.** Engineering trusts to Compliance; auditors get asked to design architecture; nobody owns Operation.
- **Standard as checklist art.** ISO 27001 can be fully attested while the product is exploitable — certification measures process, not product.

## So which one should *I* start with?

| You are | Start here |
| --- | --- |
| A solution architect designing a system | Zero Trust + STRIDE → OWASP when building |
| A developer writing the code | OWASP Top 10, then ASVS as a rubric |
| A security architect setting direction | Zero Trust + NIST CSF maturity plan |
| A tester or reviewer | OWASP Top 10 as your review/walkthrough framework |
| An enterprise architect running a program | ISO 27001/SOC 2 for the org, NIST CSF for risk |
