## What this system is

Serverless means you never book capacity: you define a function and the platform runs it when an event arrives, scales it to zero when idle, and bills you per invocation and per millisecond. The flagship products are **AWS Lambda** and **Azure Functions** — the model is the same on both.

```mermaid
flowchart LR
  Client[Client / event source] -->|invoke| GW[API Gateway / Event Grid]
  GW -->|1 event in| F1[Function instance]
  GW -->|many events| F2[Function instance 2]
  GW -->|“scale up”| F3[Function instance 3]
  F1 -->|result| Client
```

The thing people miss: a function is **one unit of work**, not an application. An API with five endpoints is five functions (or one function with a router) plus the glue — the gateway, the queues, the state store — that connects them. The platform owns the server; you own the wiring.

## The execution model

```mermaid
sequenceDiagram
  participant C as Client
  participant G as Gateway
  participant P as Platform
  participant F as Function
  C->>G: HTTP request
  G->>P: route to function
  P->>P: warm or cold start?
  P->>F: execute handler
  F-->>G: response
  G-->>C: HTTP response
```

- **Invocation model**: you never start or stop anything — you define a trigger (HTTP, queue, timer), and the platform invokes your function for each event.
- **Per-invocation billing**: pay for requests, GB-seconds of memory, and duration. Idle time costs nothing.
- **Concurrency**: the platform spins up as many function instances as the event flow needs, up to your (safety) reserved concurrency limit.

## Cold starts and warm pools

The one failure mode every serverless app feels: a **cold start**. When no instance exists, the platform must bootstrap a runtime before your code runs — adding latency to that invocation (the first in a burst, or after idle expiry).

```mermaid
flowchart TB
  subgraph Cold["Cold start (the slow path)"]
    A1[Platform provisions container] --> A2[Runtime boots + deps loaded] --> A3[Your handler runs first time]
  end
  subgraph Warm["Warm start (the fast path)"]
    B1[Instance already running] --> B2[Handler runs immediately]
  end
  Event[Invocation arrives] --> Choice{Instance warm?}
  Choice -- no --> Cold
  Choice -- yes --> Warm
```

Mitigations that actually move the number:

- **Provisioned concurrency / always-on plans** (Lambda reserved concurrency with provisioned instances, Azure Functions Premium plan) keep N instances warm — you pay for them while idle, in exchange for consistent latency.
- **Smaller deployment packages** and minimal runtime overhead reduce the cold-to-ready time.
- **Static assets & config reading** should be done once and cached (outside the handler), not per invocation.
- The **first call from a warm edge** (e.g. a cold API call after a period of no traffic) is the one that stings — design timeouts around the p99 *cold* latency, not the warm p50.

## Event-driven composition

Serverless earns its keep when events chain together. The canonical pattern is **fan-out + orchestration**:

```mermaid
flowchart TB
  Upload[File uploaded] --> F1[Fan-out: split & validate]
  F1 --> Q1[(Queue / topic A)]
  F1 --> Q2[(Queue / topic B)]
  Q1 --> W1[Worker: format]
  W1 --> S1[(Job status store)]
  Q2 --> W2[Worker: enrich]
  W2 --> S1
  S1 --> W3[Step: notify on completion]
  W3 --> Done[Result notified]
```

Weak points are where the "serverless is easy" sales pitch breaks:

- **No built-in ordering or exactly-once.** Queues are at-least-once: your function may receive the same event twice. Handlers must be **idempotent** (dedupe by event id, or write-then-commit).
- **Multiple functions each invent their own retry logic** produce chaos. Put retries, dead-letter queues (DLQ), and tracing in one place.
- **Hours-long workflows** (a report, a batch) shouldn't be one big function — the platform times out individual invocations (minutes, not hours). Split into steps, persist state, and let a stateful orchestrator (Step Functions / Durable Functions / Logic Apps) resume where the previous step ended.

## Idempotency: the rule that saves you

```mermaid
flowchart LR
  E[Event arrives] --> D{Dedup token seen?}
  D -- yes --> Ignore[Already processed - ack]
  D -- no --> W[Process + record token]
  W --> Ack[Ack to queue]
```

Because at-least-once delivery is guaranteed and exactly-once is not, every side-effecting function must dedupe. Store the dedupe key (from the event) with a TTL, and make the write path itself idempotent — e.g. `INSERT ... ON CONFLICT DO NOTHING` before adding the key, or store the dedupe key in the same transaction as the side effect.

## Platform names, same ideas

| Concern | AWS Lambda | Azure Functions |
| --- | --- | --- |
| HTTP entry | API Gateway, Function URL | API Management, static web apps |
| Queue/stream trigger | SQS, SNS, Kinesis, DynamoDB streams | Queue Storage, Event Grid, Event Hubs |
| Orchestration | Step Functions | Durable Functions |
| State / table | DynamoDB | Cosmos DB / Table storage |
| Long-running code | keep it short; orchestrate | keep it short; durable orchestrate |
| Warm instances | provisioned concurrency | Premium plan |

Pick by ecosystem, not religion — an AWS shop uses Lambda because the service grid (SQS/Kinesis/Cognito) is the point, not the name.

## Tester checklist

- Trigger a burst after a period of idle and assert the **cold-start p99** is within your SLO — don't only test under warm load.
- Replay the same event twice (DLQ redrive, manual publish) and confirm the side effect runs **once**, not twice.
- Kill the DLQ consumer or point it at a bad endpoint and confirm poison messages land in the dead-letter queue, not forever in a retry loop.
- Test `reserved concurrency` throttling: when the limit is hit, verify the right error arrives and queued events are not silently dropped.
- Check **timeouts and memory**: a handler near its duration limit should fail loudly with a bounded response, and memory-constrained runs shouldn't crash the platform.
