GraphQL APIs

One endpoint, your exact data shape: how GraphQL's schema, resolvers, and queries change the API contract — and the pagination, batching, and caching trade-offs they bring.

DeveloperBackendFrontendTester#api#architecture#performance

What this system is

GraphQL is a query language for your API plus a runtime. Instead of many endpoints each returning a fixed shape, you have one endpoint (POST /graphql) where the client declares exactly which fields it wants, nested to any depth. The server answers with a matching shape. The deal: huge frontend flexibility and one round-trip — bought with graph traversal costs, cache complexity, and a resolver layer you control.

The schema is the contract

Rendering diagram…

Unlike REST, where the contract is implied by endpoints + docs, GraphQL has a machine-readable schema (type User { ... }). That schema gives you: introspection (clients discover the API), validation (a query that mentions a non-existent field fails before execution), and tooling (autocomplete, codegen, documentation).

  • Query — the reads, one entry point for fetching.
  • Mutation — the writes. All requests ride the same single endpoint.
  • Resolvers — functions that answer "where does this field's value come from?", each field resolved independently. That's where your performance either shines or catches fire.

Queries, and the graph-traversal cost

Rendering diagram…

The query asks for nested data in one round-trip — great for chatty mobile apps. But the server must resolve every requested field, and a naive resolver does N+1: fetch the user, then one query per order, then one per line item. The fix is batching (DataLoader: coalesce a query's identical field loads into one call) and depth/query-size limits so a client can't ask for a bomb-shaped query (orders { lines { orders { lines { ... } } } } tens of levels deep).

Strengths and the price

GraphQLREST
Shape of responseClient controls — no under/over-fetchingFixed per endpoint
Round-tripsOne query, nested in one callMultiple calls for related data
ContractSchema + introspection, typedDocs + conventions
CachingHard — POST endpoint, varies by queryNatural via HTTP caching (Cache-Control, ETag)
Server costResolver traversal, N+1 trapPredictable per-route work
Learning/simplicityBigger server surfaceSimple, boring, universal

The honest summary: GraphQL shines when clients differ wildly (mobile, web, third parties), when related data is fetched together, and when you value a typed contract. It costs you with cache complexity — every query is a distinct POST body, so HTTP caching doesn't help like REST; you need normalized client caches (Apollo), persisted queries, or GET-style caching for it.

Pagination and mutations: the two design questions

Rendering diagram…
  • Cursor pagination is the GraphQL default for lists (stable across inserts, like REST's modern answer). Relay Connections formalize it with edges { cursor node } + pageInfo { hasNextPage }.
  • Mutations return the mutated object (and often changed related state) so the client can update its cache in one shot — avoiding a follow-up query.

Tester checklist

  • Send a query with a non-existent field: it must fail validation before execution (schema is enforced).
  • Test depth/query-cost limits: a runaway nested query should be rejected by your size guard before it reaches resolvers.
  • Add a DataLoader and re-run an N+1 query: confirm the database request count drops from 1 + N to a small constant (watch the DB query log).
  • Verify error handling: partial resolvers failing should produce an errors array in the response, not a failed HTTP request — and know which is which.
  • Compare payload sizes: request the same data via GraphQL vs REST and confirm you're actually fetching less (that's the contract's point).
