Blockchain Fundamentals

Distributed ledgers, cryptographic hashes, consensus mechanisms, and immutability — the primitives that let mutually distrusting nodes share state without a central authority.

What this system is

A blockchain is a distributed, append-only ledger of records — blocks — chained together by cryptographic hashes. Instead of one trusted database that everyone reads, a blockchain is replicated across many nodes that do not trust each other. Each block bundles a set of transactions, a timestamp, and a hash of the previous block. That pointer is what binds the chain together: change anything in an old block and its hash no longer matches, invalidating every block built on top of it (see Secrets, certificates and PKI for the hashing primitives underneath).

Because no single party owns history, nobody can quietly rewrite it. The consequence is a shared state machine that stays consistent without a bank, broker, or cloud account being the referee.

What problem it replaces

Trust modelWithout blockchainWith blockchain
Authoritative dataA central party (bank, app, government) is trusted to store the truthTruth is the longest hash-linked chain, agreed by the network
AuditingRelies on that party's logs, which they could editEvery node holds the same append-only history
Failure domainA central outage or compromise takes the system downNodes join and leave; the ledger survives as long as replicas exist
SettlementCounterparty risk — I must trust the other side will payA transaction only lands if the network agrees it is valid
Threat modelInsider can alter records and erase tracesAltering one replica is detected by every other replica

This buys a specific kind of assurance: integrity and provenance of records among parties that do not trust each other, at the cost of throughput, latency, and privacy compared to a normal database. Blockchain is rarely the answer for "I just need a fast database" — that is what Data warehouse and lakehouse architecture is for.

Blocks and hashing

  • Block: a batch of transactions plus a header. The header includes the previous block hash, a timestamp, a nonce/attested state, and often a Merkle root that commits to the transaction list in one digest.
  • Merkle tree: transactions are hashed pairwise up to a single root, so a node can prove "this transaction is in this block" by showing only a small hash path, not the whole block.
  • Append-only: blocks are added by consensus; nobody can insert one in the middle without recomputing every hash after it, which would be detected.
  • Fork: when two blocks are mined at the same height, the chain briefly splits. Nodes adopt the branch with the most accumulated proof of work or stake — the longest/heaviest chain wins and the other branch is orphaned.

Consensus: how nodes agree

MechanismIdeaCostUsed by
Proof of Work (PoW)Pay real compute to propose a block; the first solver winsEnergy and hardwareBitcoin, (historically) Ethereum
Proof of Stake (PoS)Lock up tokens as stake; validators are selected and can be slashed for cheatingCapital, not energyEthereum after "the Merge"
PBFT / leader-based BFTNodes vote in rounds; tolerates up to ~1/3 malicious replicasSmall, permissioned networksEnterprise/government ledgers
DAG-based (IOTA, Hedera)No linear chain; transactions confirm each other as a directed acyclic graphFast, no minersIoT micro-payments, supply chain

For private networks (permissioned), PBFT-style consensus is usually the right fit because every member is known. For public networks, PoW/PoS are designed to work even when membership is open and adversarial.

When blockchain makes sense

  • Multi-party reconciliation — several organizations must agree on one shared record and none will let the others hold it (supply chain, trade finance).
  • Provenance and audit trails — a tamper-evident log is worth more than raw performance.
  • Open, permissionless networks — anyone can join and no single operator can freeze or censor.
  • Tokenization and settlement — native digital assets and programmatic payments with an existing trust problem.

Avoid it when the real requirement is confidentiality (a blockchain's history is public), or high throughput, or "we just trust our own database anyway" — in those cases a normal database plus Change data capture and Monitoring and observability is better.

Tester checklist

  • Verify immutability: create a chain, tamper with an early block's transaction, and confirm subsequent blocks' hash pointers break.
  • Test fork resolution: simulate two conflicting blocks at the same height and confirm the network converges on one chain.
  • Confirm a transaction is only final after the required confirmations, not when it first appears in the mempool.
  • Check that a malformed or unsigned transaction is rejected by full nodes before it can enter a block.
  • Validate node recovery: a node that was offline can resync and reproduce the exact same chain state.
  • Exercise consensus edge cases: an empty block, a double-spend attempt, and a block exceeding size/gas limits.
