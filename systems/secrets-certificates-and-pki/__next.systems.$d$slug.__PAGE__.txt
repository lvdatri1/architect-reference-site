## What this system is

Every identity in the enterprise — user tokens, TLS, mTLS, code signing, SSH — leans on two trust primitives: **certificates** (who can prove identity; backed by a CA hierarchy = PKI) and **secrets** (keys/tokens/passwords that unlock access). Zero Trust turns both into the same idea: *short-lived, automatically rotated, central-managed* — never hand-written, never hard-coded, never long-lived.

```mermaid
flowchart TB
  Root[Root CA - offline, highest trust] --> Inter[Intermediate CA]
  Inter --> Leaf1[Site certs - *.example.com]
  Inter --> Leaf2[mTLS / workload SVIDs]
  Inter --> Leaf3[Code-signing / SSH signed keys]
  Root --> HSM[HSM stores CA keys - cannot be copied]
  Leaf1 --> Chain[Browser / client validates chain]
```

## The certificate lifecycle

```mermaid
flowchart LR
  Issue[Cerify via ACME / RA] --> Deploy[Deploy to endpoints]
  Deploy --> Monitor[Monitor expiry + usage]
  Monitor -->|~90% lifetime| Renew[Automated renewal]
  Renew --> Issue
  Monitor -->|compromise detected| Revoke[Revoke + CRL / OCSP]
```

The modern rules are boring on purpose:
1. **Short lifetimes** (90 days is legacy-long; hours-to-days for workload identities) shrink the blast radius of a stolen cert.
2. **Automation everywhere** — ACME/SPIRE-style issuance means nothing is issued by hand, signed by hand, renewed by hand.
3. **Revocation actually propagates** — CRL/OCSP when CA is compromised; for short-lived certs you often *wait out* expiry instead of relying on revocation.

## Vaults: static vs dynamic secrets

| | Static secret | Dynamic / short-lived |
| --- | --- | --- |
| Example | Long-lived API key | Per-task DB credentials, one-time tokens |
| Lifetime | Years by accident | Seconds-to-minutes by construction |
| Rotation | Sometimes, painful | Automatic, constant |
| Leakage cost | Full access until rotated | Expires before it matters |
| Vault role | Store + access control | Generate on demand, lease with TTL |

**Vault-style systems** (HashiCorp Vault, cloud secret managers) do both: central storage + a **lease model** where services pull credentials for a window and they die after. The hard part is teaching every app to *fetch, not hard-code*.

## The failure modes that still hurt

- **Hard-coded secrets** shipped in images/CI logs — the leak that outlives two "rotations."
- **Long-lived root material** used for work (it should be offline behind an HSM).
- **Certificate expiry** on the one internal endpoint the outage-call answered with "it expired" — solved by monitoring + automation, not reminders.
- **A single trust root in software**: a CA key inside a binary the server ship accidentally contains. HSM containment or a strict split is non-negotiable.

## Tester checklist

- Pull a dynamic DB credential from the vault and confirm it expires on its lease even if the app forgets to release it.
- Rotate a TLS leaf cert mid-traffic and confirm zero-downtime drop-in (automated path, not manual).
- Compromise drill: a stolen short-lived credential must grant *bounded* time, and an HSM-bound CA key must be uncopyable.
- Audit for hard-coded secrets with a repo scan and prove the CI gate blocks them.
