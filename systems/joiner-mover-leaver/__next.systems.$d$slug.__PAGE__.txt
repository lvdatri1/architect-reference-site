## What this system is

**JML** (Joiner / Mover / Leaver) is the operating model for identity: three kinds of life-change events, each with a defined set of access consequences. Joining grants access, moving rescopes it, leaving revokes it. Done manually, these are the source of ghost accounts and admin sprawl; done as an event-driven pipeline, they become invisible and reliable.

```mermaid
flowchart LR
  HR["HR system"] -->|join / move / leave| Store["Identity store"]
  Store -->|revoke sessions| SSO["SSO sessions<br/>killed on leave"]
  Store -->|sync accounts| SCIM["SCIM apps<br/>provision + deprovision"]
  Store -->|strip privilege| PIM["PIM privileges<br/>deactivated"]
  PIM -->|every change logged| Audit["Auditable state"]
```

```mermaid
flowchart LR
  HR[(HR system)] -->|join event| ID[Identity store]
  HR -->|move event| ID
  HR -->|leave event| ID
  ID -->|provision| Apps[Apps - via SCIM]
  ID -->|rescale| Apps
  ID -->|deprovision| Apps
  ID -->|strip privilege| PIM[Privileged access]
  ID -->|suspend + kill sessions| SSO[Every SSO session]
```

## The three phases

| Phase | Trigger | The access move | Failure if skipped |
| --- | --- | --- | --- |
| **Joiner** | First day in HR | Accounts created in the right groups, right roles | Manual "set-up" tickets, late access, shadow IDs |
| **Mover** | Role/team change | Old groups removed, new groups added, privilege rescoped | Accumulated stale rights ("they used to…") |
| **Leaver** | Termination date | Sessions killed, accounts suspended/deleted, privilege stripped, license reclaimed | Orphan accounts = the #1 audit finding |

Each is a *state change in HR* that triggers a chain: HR → identity store → [SCIM](../scim-identity-provisioning) provisioning → [SSO](../single-sign-on-sso) session revocation → [PIM](../privileged-identity-management) privilege deactivation.

## The leaver chain, end to end

```mermaid
sequenceDiagram
  participant H as HR - term date
  participant I as Identity store
  participant S as SSO / IdP
  participant A as Apps (SCIM)

  H->>I: termination event with exact date/time
  I->>S: disable accounts + revoke sessions
  I->>A: deprovision / suspend via SCIM
  I->>I: PIM grants deactivated for leaver
  Note over A: device access revoked by MDM as a parallel chain
```

Notice the **date on the termination event**: identity should act *at* the boundary, not at "whenever someone remembers."

## Why JML is really an access-governance feature

- **Access reviews**: with JML wired up, reviews become *"does the current state match the events we processed?"* instead of "document everything in a spreadsheet."
- **Orphan detection**: accounts that never got a termination event are the canary — a monitoring query for "active past 90 days + no supervisor" is your safety net.
- **Separation of duties**: a lemma of JML is that moves don't *add* — a promotion shouldn't keep the leaver-tier rights of the old job unless that is a deliberate decision ([RBAC](../rbac-and-authorization)).

## Tester checklist

- Join drill: a new-hire event with a future start date must create accounts, roles, and app memberships exactly at start (not a day early).
- Move drill: change a user's team and confirm old group access *removes*, new *adds* — and the intersection is re-reviewed.
- Leaver drill with a timer: at 17:00 termination, by 17:00:30 all SSO sessions are dead and SCIM accounts suspended.
- Anti-pattern check: is there *any* manual "give this user access right now" path that by-passes the event chain? (Kill it.)
