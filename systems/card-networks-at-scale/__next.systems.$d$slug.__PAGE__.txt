## What this system is

A **card network** (Visa, Mastercard, and the card schemes) is a message switch, an interchange, and a settlement house in one. Each **card transaction touches four parties** — the cardholder, the merchant, the merchant's **acquirer** bank, and the cardholder's **issuer** bank — and the network stands in the middle of every one of them. The scale the industry quotes ("billions a day") comes from something more interesting than hardware: the network is a *nearly stateless protocol with ruthless budgets*.

```mermaid
flowchart LR
    H[Cardholder - POS / e-commerce] --> M[Merchant / POS terminal]
    M --> AQ[Acquirer bank]
    AQ --> N[Network switch - Visa / Mastercard]
    N --> IS[Issuer bank]
    IS --> R[(Risk + account systems)]
    N -.-> CLEAR[Clearing + settlement]
```

## Why fast: the authorization budget

A card payment at the terminal is a **real-time authorization**: the merchant asks "is this good?", and the answer must come back in a second or two — not minutes. The network's job is to move that request from acquirer to issuer, get a decision, and return it. Because the request is small, idempotent by reference, and largely stateless at the switch, the network is built like a high-performance message bus, not a giant database.

| Constraint | Number that drives the design |
| --- | --- |
| Authorization latency budget | ~2 seconds round trip, network included |
| Transaction size | A few hundred bytes per ISO 8583 message |
| Peak rate (global schemes) | Tens of thousands of authorizations per second |
| Failure cost | A workflow-dependent mix of false decline (lost sale) or false approve (fraud) |

## Anatomy of an authorization

```mermaid
sequenceDiagram
    participant TERM as "POS terminal"
    participant AQ as "Acquirer"
    participant SW as "Network switch"
    participant IS as "Issuer"
    TERM->>AQ: auth request
    AQ->>SW: BIN lookup
    SW->>IS: forward
    IS-->>SW: approve / decline
    SW-->>TERM: reply to terminal
```

## The switch's design secrets

- **Routing is a lookup, not a query**: the network routes by **BIN/IIN** (the first 6–8 digits of the card number) to the issuer's endpoint. It is a precomputed routing table, updated on an issuer bulletin — no per-transaction database lookup for *where* to send.
- **Stateless in the middle**: the switch does not store the account; it carries the message and returns the answer. State lives at the issuer. Losing a switch node loses nothing recoverable — the design point that makes the network horizontally scalable and cheap to run at any peak.
- **Timeout and fallback**: if an issuer doesn't answer within its SLA, the network may **stand-in authorizes** — accepting within issuer-defined limits — or route via a redundant path. That fallback is how commerce keeps moving even when a bank hiccups.
- **Idempotency and reference numbers**: each authorization carries a unique retrieval reference, so a retried message settles exactly once. This is the same once-only pattern as [Message queue delivery](../message-queue-delivery), pressed into a sub-second protocol.
- **Concurrency without locks**: money is only *reserved* at authorization (a hold) and only *moved* later. Because the switch never touches balances, throughput scales by adding nodes, not by optimizing a single database.

## Volume: clearing and settlement in batch

Authorizations are hot and synchronous; **clearing** (the actual transfer messages) runs in **batches** after the fact. The merchant's terminal captures at end-of-day or per-transaction, the network *nets* and *descends* summaries between each acquirer-issuer pair, and settlement moves the net amounts — exactly the [netting idea from payments clearing](../payments-clearing-and-settlement), applied across thousands of banks at once.

This separation is the single biggest scaling lever: the real-time path is narrow and fast, while the volume path is a batch processing system with reconciliation. Both are necessary; neither can do the other's job.

## How the scale is actually measured

The "million per second" headline is a **peak throughput headline about the whole ecosystem**, not a single request's path. What is genuinely true:

| Layer | Where the volume lands |
| --- | --- |
| Terminal to acquirer | Massive parallelism, country-scale |
| Acquirer to switch | The switch's high-volume ingress |
| Switch to issuer | Fanned out by BIN routing; issued APIs are the real cost |
| The ledger behind it | Held by issuer/acquirer banks, not the network |

For an architect building their own high-volume system, the transferable lessons are: **narrow the hot path, make the middle stateless, route by precomputed keys, reserve-then-settle instead of locking, and put the volume on a batch side-channel.**

## Tester checklist

- Routing: a card with a given BIN reaches its intended issuer, and a BIN-table update takes effect without restarting the switch.
- Timeout: an issuer that exceeds its SLA triggers the configured stand-in or fallback path, and the decision is recorded with the reason.
- Idempotency: re-sending an identical authorization reference is answered identically and does not double-hold funds.
- Latency budget: under synthetic load, a normally-routed authorization completes inside the round-trip SLA.
- Partition tolerance: a switch node failure does not lose in-flight authorizations or corrupt routing state.
- Settlement math: a day of captures nets per acquirer-issuer pair to zero at the aggregate, tieing to the [reconciliation feed](../payments-clearing-and-settlement).
- Decline vs authorize: the fraud/limit decision from the issuer is returned verbatim to the terminal code the merchant's systems parse.
