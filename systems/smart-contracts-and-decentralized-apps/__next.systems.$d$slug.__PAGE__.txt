## What this system is

**Smart contracts** are programs deployed onto a blockchain that execute deterministically on every node — code becomes a shared, verifiable public API. A **decentralized application (dApp)** is the combination of a smart contract (the back end, living on-chain) and a normal web front end (off-chain), plus a **wallet** the user uses to sign transactions.

Where a traditional app trusts a server, a dApp trusts *everyone running the contract*. There is no admin account that can edit the ledger's history for a public chain; rules are enforced by the consensus rules described in [Blockchain fundamentals](../blockchain-fundamentals), not by an operator.

```mermaid
flowchart LR
    U[User in a browser] --> F[dApp front end<br/>plain HTML/JS]
    F --> W[Wallet<br/>holds private keys]
    W -->|signed transaction| R[RPC endpoint<br/>gateway to chain]
    R --> C[Smart contract<br/>on-chain logic + state]
    C --> E[Blockchain consensus<br/>validates and executes]
```

## What problem it solves

| Classic flow | dApp counterpart |
| --- | --- |
| A server holds a database of balances and a ledger | Balances and state live in the contract's storage, visible to all |
| Back-end logic can be changed or hot-patched at will | Deployed on-chain code is immutable; upgrades are explicit and auditable |
| Users trust the operator not to freeze or censor them | No operator can silently censor a transaction that pays the fee |
| Ownership is "whoever controls the server" | Ownership is "whoever controls the private keys" (self-custody) |

The trade-off is real: the same transparency that removes the operator a trust also removes user privacy (everyone can read all balances) and places strict limits on throughput, so contracts keep only *essential* logic and state on-chain.

## Anatomy of a transaction

```mermaid
sequenceDiagram
    participant WAL as "Wallet"
    participant DAPP as "dApp front end"
    participant RPC as "RPC provider"
    participant MEM as "Mempool"
    participant EXEC as "Contract execution"
    participant FINAL as "Confirmed in a block"
    WAL->>DAPP: authorize call
    DAPP->>RPC: submit tx
    RPC->>MEM: queue
    MEM->>EXEC: included in block
    EXEC->>FINAL: committed
```

## Tokens: fungible and non-fungible

| Token type | Example standard | Behavior |
| --- | --- | --- |
| **Fungible** | ERC-20 (Ethereum) | Every unit is interchangeable — currency, staking rewards, governance votes |
| **Non-fungible (NFT)** | ERC-721 | Each token is unique — deeds, collectibles, digital art, licenses |
| **Semi-fungible / soulbound** | ERC-1155 / custom | Mixes or non-transferable credentials — the bridge to [decentralized identity](../decentralized-identity-and-verifiable-credentials) |

A token contract is itself just a smart contract keeping a mapping of addresses to balances, with rules like emit an event, transfer, approve, and mint/burn. Any contract or wallet can read those transfers — which is why [Data pipelines (ETL/ELT)](../data-pipelines-etl-elt) indexers exist to normalize on-chain events into analytics tables.

## Wallets and key custody

- **Self-custody**: the wallet holds the private keys; losing them is losing the funds. No "I forgot my password — reset me" path exists.
- **Seed phrase**: keys are derived from a BIP-039 mnemonic; it *is* the account, so it must be handled like [Secrets, certificates and PKI](../secrets-certificates-and-pki) secrets.
- **Hierarchical deterministic (HD) wallets**: one seed derives many addresses, so a dApp can request sub-accounts per session.
- **Contracts as wallets**: multi-sig and smart wallets enforce rules like "need 2 of 3 signers" — moving account policy from a human to code.

## When dApps make sense

- **Open financial primitives** — lending, swaps, stablecoins where transparency and composability beat operator trust.
- **Governance and DAOs** — tokens give votes, and the treasury is a contract, so spending is verifiable by anyone.
- **Protocols that other developers build on** — composability: your contract can call my contract, both serving the same shared state.
- **Self-custody products** — users genuinely control their assets rather than a company's account table.

When in doubt, prefer a normal app: dApps trade performance, privacy, and upgradeability for decentralization. If the "trust third party removed" is a feature you do not actually need, a traditional architecture is cheaper and faster.

## Tester checklist

- Verify the front end never holds keys: signing happens in the wallet, and the dApp only sees the signed payload.
- Test gas/revert paths: confirm the UI reflects a failed transaction (state rollback) instead of silently reporting success.
- Validate access control: call admin-only contract functions as a non-admin and confirm they revert.
- Check reentrancy and integer-overflow behavior with a dedicated security review — these are the classic exploit classes.
- Confirm the UI reads fresh state (post-confirmation) and does not show optimistic stale balances.
- Exercise multi-sig wallets: a transaction authorized by fewer than the quorum must remain pending and unexecutable.
- Verify wallet disconnect/revocation: permissions granted to the dApp are revocable and never persist keys.
