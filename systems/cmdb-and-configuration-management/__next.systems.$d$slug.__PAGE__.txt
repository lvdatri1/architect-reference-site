## What this system is

A Configuration Management Database (CMDB) is a **database of configuration items (CIs)** — servers, applications, services, licenses, network devices, databases, people-owned assets — plus the **relationships** between them, plus the attributes that matter (owner, version, environment, patch status). It is not a fancy inventory: a spreadsheet of assets is a list, and a CMDB is a *model*. The difference is the relationship graph — "this application runs on that server which connects to that database" — because that graph is what incident, change, and dependency analysis all query.

```mermaid
flowchart LR
  subgraph Assets["Configuration items (CIs)"]
    S1[Web server - v2.1]
    S2[App server - v1.8]
    DB[(Database - v19c)]
  end
  subgraph Model["Relationships = the value"]
    R1[S1 -.runs on.-> S2]
    R2[S2 -.connects to.-> DB]
    R3[App -.owned by.-> Team]
  end
```

## CIs, relationships, attributes

| Concept | Example | Why it matters |
| --- | --- | --- |
| **CI** | `web-prod-01`, `ERP application v11` | The atomic unit you reason about |
| **Attribute** | owner, env, version, patch level | What you filter and report on |
| **Relationship** | `app runs-on server`, `server connects-to db` | The graph that makes incidents diagnosable |
| **Status** | Installed, retired, in-prod | Keeps the model honest about what's real |

The useful CMDB is the one where the **relationship graph is current enough that "what breaks if this server dies?" and "who owns this CI?"** get a trustworthy answer. That trust is the whole ballgame: a CMDB that nobody believes gets abandoned, and an abandoned CMDB is worse than none because it lies with authority.

## The trust cycle (why CMDBs fail)

```mermaid
flowchart LR
  A[Data enters<br/>via discovery + humans] --> B[People trust it]
  B --> C[People keep it current<br/>- feed back changes]
  C --> A
  D[Data goes stale] --> E[People stop trusting]
  E --> F[People stop feeding it]
  F --> D
```

Every CMDB project is a bet on which cycle you'll be on in a year. The technical half is easy (discovery tools, adapters, a schema). The cultural half is decisive: if consuming a CI record costs less effort than guessing, the CMDB lives; if a stale record ever burns someone, it dies. The practices that keep the good cycle spinning:

- **Ownership as a first-class attribute** — every CI names a human; stale records get chased to their owner, not silently cleaned.
- **Discovery feeds the model automatically** — cloud, VMs, agents, network scans update CIs without a human typing them.
- **Consumers close the loop** — incident, change, and capacity teams *query* the CMDB as their default first move, which creates the feedback that keeps it honest.
- **A CI is retired the day it's retired** — the model must reflect reality or it decays from day one.

## CMDB vs asset management vs inventory

| Store | Tracks | The question it answers |
| --- | --- | --- |
| **Hardware/asset register** | Purchased things, ownership, lifecycle, cost | "What do we own and who's paying for it?" |
| **Inventory/software list** | Install counts, licenses | "What software runs and are we compliant?" |
| **CMDB** | CIs *and their relationships* | "What runs on what, and who does it affect?" |

They share data and often live in the same tool, but their purpose differs: the asset register is about money and custody, the CMDB is about **impact**. "Which users does this database support?" is a CMDB question; "how many Macs do we have?" is an asset register question. Conflating them is the most common reason a "CMDB implementation" ships an inventory that nobody consults during an incident.

## Discovery and the source of truth

```mermaid
flowchart LR
  subgraph Sources
    Cl[Cloud APIs - AWS/Azure/OCI]
    A[Agents - installed]
    N[Network scan - SNMP]
    CM[Manual / import - CSV, spreadsheets]
  end
  Cl --> D[Discovery + reconciliation]
  A --> D
  N --> D
  CM --> D
  D --> CMDB[(CMDB - golden record)]
  CMDB --> E[Enterprise service management]
```

The single-source-of-truth question is where CMDB projects overreach. The healthy answer is **federation with one reconciled layer**: discovery tools feed each asset type, humans own the exceptions, and the CMDB publishes the agreed record to whoever consumes it. The unhealthy answer is "we will model every AWS resource, VM, and network interface manually" — that's how a CMDB rots in a quarter.

## Tester checklist

- **The impact question**: pick a database CI, ask "which applications and users would be affected if it failed" — confirm the relationship graph returns the right set.
- **Staleness drill**: retire a server in reality, keep it in the CMDB, and confirm either discovery removes it or the owner gets paged within the SLA you set.
- **Trust test**: compare CMDB CI versions against reality (agents/cloud API) for a sample and measure drift — under a few percent is healthy, double digits is dying.
- **Ownership check**: every CI in a sample must resolve to a named human owner, not "IT".
- **Discovery fidelity**: create a new VM in the cloud and time how long it takes to appear as a CI with the right relationships.
