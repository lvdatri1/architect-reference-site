## What this system is

HTTP authentication is the **`Authorization` request header** (plus the `WWW-Authenticate` response header that tells you *how* to authenticate). The header carries a **scheme** and scheme-specific credentials: `Basic`, `Bearer`, `Digest`, or a custom scheme. It is the oldest, simplest layer of "who may access this endpoint" — and the one most often misused.

```mermaid
flowchart LR
  CL[Client] -->|attach header| RQ[GET /api with Authorization header]
  RQ -->|dispatch| CH{Server parses scheme}
  CH -->|valid| OK[200 - allowed]
  CH -->|missing or invalid| DENY[401 + WWW-Authenticate]
```

```mermaid
flowchart LR
  C[Client] -->|Authorization: Basic dXNlcjpwYXNz| S[Server]
  S --> V{Decode + verify?}
  V -->|yes| OK[200 OK]
  V -->|no / absent| CH[401 + WWW-Authenticate: Basic realm=...]
```

## Basic auth, honestly explained

```mermaid
flowchart LR
  U[username:password] --> B1[base64 encode] --> H1[dXNlcjpwYXNz]
  H1 --> H2[Authorization: Basic dXNlcjpwYXNz]
  H2 --> S[Server decodes and compares]
```

Basic auth is one line: **`Authorization: Basic <base64(username:password)>`**. The credentials are `base64` encoded, **not encrypted** — anyone who sees the header sees the password (base64 is trivially reversible). Three rules decide whether it's acceptable:

1. **Only over TLS** — over plain HTTP, the header *is* the password broadcast to the network.
2. **Only for low-stakes or system-to-system** credentials — a shared API key with narrow scope, never a human's master password.
3. **Never against a database of user passwords** — compare against a hash (and rate-limit to survive brute force).

The classic failure: "it's behind HTTPS so base64 is fine" — then an operator pulls the header into a log, a proxy, or an error message, and the credential leaks in plaintext where the TLS never protected it.

## The `WWW-Authenticate` dance

```mermaid
sequenceDiagram
  participant C as Client
  participant S as Server

  C->>S: GET /private (no auth)
  S-->>C: 401 + WWW-Authenticate: Basic realm="Admin"
  C->>S: GET /private + Authorization: Basic ...
  S-->>C: 200 OK (or 403 if not allowed)
```

When auth is missing/invalid, the server answers **`401`** with a **`WWW-Authenticate`** header naming the scheme (and often a `realm` describing what's protected). The client then *retries with credentials*. That's why you'll see two requests in the network tab for a Basic-protected page.

## Basic vs Digest vs Bearer vs API keys

| Scheme | How it works | Use it for | Danger |
| --- | --- | --- | --- |
| **Basic** | `base64(user:pass)` | TLS-only, low-stakes, simple | Credential in every header; replayable if leaked |
| **Digest** | Hash of user:pass + nonce | Legacy, still-plaintext apps | Weak hash; rarely worth it today |
| **Bearer** | An opaque token from an issuer | Tokens you already hold (OAuth/JWT) | Whoever holds the token is you — no password involved |
| **API key** | A shared secret, often `X-API-Key` | System-to-system, scoped | Same leak problem as Basic; also logged |
| **mTLS** | Certificate on the connection | Machine-to-machine, high-trust | Complex to roll out; strongest tie to the wire |

**Bearer and API keys are the modern defaults** for machine APIs precisely because they don't carry a *password* — a leaked token is revocable and (ideally) short-lived, whereas a leaked Basic pair is the user's real login. The recurring refrain in every auth review: "this is a credential, treat it like one."

## Reading the header: what a tester looks for

```mermaid
flowchart TB
  H[Authorization header seen?] --> A{Over HTTPS only?}
  A -->|no| B[FAIL - credential in cleartext]
  A -->|yes| C{What scheme?}
  C -->|Basic| D[Is it base64 user-pass? rate-limited? non-human?]
  C -->|Bearer / API key| E[Expiry? revocation? scope limited?]
  C -->|something custom| F[Is the scheme well-defined and not invented crypto?]
```

- Is the header **ever logged** (proxy, gateway, app logs)? One `req.headers` dumped to logs = credential leak.
- Does the server check **over** the header only, or also **caches** a response keyed by the credential (a cached 200 shared across users)?
- Is there **rate limiting / lockout** on failures? A Basic endpoint without it is a brute-force treadmill.
- Are credentials **revocable and rotated**? A static API key from 2019 with access to prod is an incident waiting.

## Tester checklist

- Confirm every Basic/Bearer API you expose **refuses** plaintext HTTP (redirect to HTTPS, or reject entirely) — the header must never travel unencrypted.
- Attempt auth with the base64 decoded and sent wrong: expect `401` with `WWW-Authenticate`, not `200` or `403`-with-data.
- Check that failed attempts are rate-limited/locked and that logs do **not** contain the full `Authorization` header.
- Verify a leaked-token scenario end to end: revoke a key/token and confirm in-flight and new requests fail (not just "stale cache").
- Distinguish 401 vs 403: unauthenticated = 401 + challenge; authenticated-but-forbidden = 403. Mixing them up hides bugs and leaks resource existence.
