## What this system is

The **software development lifecycle** (SDLC) is the spine that turns business intent into a working, supported system. Its strength is not the phases — every team has an argument about those — it is the **gates**: each phase must meet its *exit criteria* and hand over a *usable artifact* before the next phase may begin. The lifecycle only works when the artifacts, not the meetings, carry the state forward.

```mermaid
flowchart LR
  R[Requirements] --> A[Analysis]
  A --> D[Design]
  D --> B[Build]
  B --> T[Test]
  T --> P[Deploy]
  P --> O[Operate]
  O -.->|change request / defect| R
```

Whether you run it as a waterfall, a portfolio of sprints, or a continuous pipeline, the **phase logic** is the same — the delivery model changes how fast you loop, not which questions must be answered.

## The phases, the artifacts, and the exit tests

The lifecycle is a chain of hand-offs where *the artifact is the contract*. If you can't name the artifact a phase produces, you can't verify the phase finished.

| Phase | Input | Artifact produced | Exit test |
| --- | --- | --- | --- |
| **1 · Requirements** | Business need, problem statement | Prioritized requirements, success criteria | Every requirement is testable and has an owner |
| **2 · Analysis** | Requirements | Domain model, data flows, rules, edge cases | Ambiguities resolved; "what if" questions answered |
| **3 · Design** | Analysis artifacts | Architecture, API contracts, schema, UI specs | Designers + testers agree it is buildable and testable |
| **4 · Build** | Design artifacts | Code, migrations, config | Everything merges, CI is green, feature toggles in |
| **5 · Test** | Build outputs | Test evidence, defect list, go/no-go report | Coverage meets the bar; no known critical defects |
| **6 · Deploy** | Approved build | Released environment, runbook, rollback plan | Smoke tests pass in prod; rollback practiced |
| **7 · Operate** | Live system | Alerting, SLAs, incident records | Team owns the fix/change loop going forward |

The most common lifecycle failures are not phase-specific — they are **exit-test failures**: a phase was declared done on a schedule, not on evidence of completeness.

## The requirements-to-design bridge

```mermaid
stateDiagram-v2
  [*] --> Requirements
  Requirements: Requirements + success criteria
  Requirements --> Analysis: clarified
  Analysis: Analysis - domain model + rules
  Analysis --> Design: model + rules
  Design: Design - contracts + schema
  Design --> Build: contracts approved
  Build: Build - code + migrations
  Build --> Test: artifacts handed over
  Test: Test - evidence + go/no-go
  Test --> [*]
```

The fatal gap in most lifecycles sits between **Analysis** and **Design**: the requirements say *what*, the analysis unpacks *what if* (rules, edge cases, exceptions), and the design only *then* freezes contracts. Jumping straight from requirements to a schema is how the "weird one-off" becomes a production surprise.

## Where the phase gates hurt (and why they exist)

- **Waterfall** — the strict form: each phase completes before the next starts. Cheap to govern, brutal when a late discovery invalidates earlier work.
- **Agile / sprints** — the compressed form: requirements, design, and test happen *every iteration*, so the gates become lighter but never disappear.
- **Continuous delivery** — the pipeline form: build→test→deploy are automated stages with gates embedded as checks, approvals, and environments.

The discipline in every model is the same: **a gate is a question, not a ceremony**. "Does the artifact meet the exit criteria?" asked *by the person who depends on it next*. When the tester doesn't approve the design spec, the lifecycle is working.

## Tester checklist

- Traceability: take one requirement and follow it through analysis, design, build, and its passing test — any dead end is a gap.
- Gate audit: pick a recent delivery and confirm each phase actually met its exit test on evidence, not on a date.
- Defect routing: a bug found in production must map back to the phase whose exit test missed it — that is where the lifecycle should improve.
- Rollback readiness: every deploy record names its rollback play and proves it was rehearsed.
- Artifact survival: a new engineer should be able to reconstruct a feature's *why* from the artifacts alone (not from memory).
