## What this system is

DHCP (Dynamic Host Configuration Protocol) automates the boring-but-critical job of turning a blank network interface into a configured host: IP address, subnet mask, default gateway, DNS servers, NTP, domain suffix. A fleet of devices, printers, and phones that changes daily would be unmanageable if every address had to be typed by hand — DHCP leases each device an address and *reclaims* it when it's done.

It works over UDP: clients broadcast on **port 67/68**. No initiator address yet, so the client's first messages are broadcast `255.255.255.255` — the "election" that only the DHCP server wins.

```mermaid
sequenceDiagram
  participant C as Client - no IP yet
  participant R as L2 broadcast switch / relay agent
  participant S as DHCP server - scope + lease pool

  C->>R: DHCP DISCOVER - broadcast
  R->>S: forwarded via relay agent or on-link
  S-->>C: DHCP OFFER, REQUEST, ACK
  Note over C: configured - IP + gateway + DNS
```

## The DORA conversation

```mermaid
sequenceDiagram
  participant C as Client
  participant R as Relay agent (optional)
  participant S as DHCP server

  C->>R: DHCP DISCOVER (broadcast)
  R->>S: forward with giaddr (relay's address)
  S->>R: DHCP OFFER (offered IP + options)
  R->>C: broadcast OFFER on the segment
  C->>R: DHCP REQUEST (I choose this offer)
  R->>S: forward to the server
  S->>R: DHCP ACK (confirmed, lease starts)
  R->>C: ACK delivered to the client
```

That's **DORA**: **D**iscover, **O**ffer, **R**equest, **A**ck. It's four messages in two exchanges (broadcast round-trip for offer, then explicit request+ack for the chosen lease). Modern cases collapse things: when a client reconnects before its lease expires, it can go straight to `REQUEST` (renewal at T1/T2 timer thresholds) — no full DORA needed.

## Scopes, pools, leases, reservations

```mermaid
flowchart LR
  S[DHCP scope: 10.20.0.0/24] --> P[Pool 10.20.0.100 - 10.20.0.200]
  P --> L[Lease: given IP + options, for 8h]
  S --> R[Reservation: printer MAC → 10.20.0.50 fixed]
  L --> R
```

| Concept | What it is | Gotcha |
| --- | --- | --- |
| **Scope** | Boundary of addresses a server manages (a subnet) | Define via the network's subnet mask, not a guess |
| **Pool** | Range of addresses the server may assign | Overlapping pools → duplicate IPs across servers |
| **Lease** | Address + options valid for a duration | Too-short leases churn DNS; too-long stalls IP-pool reuse |
| **Reservation** | MAC → fixed IP binding | `binding clients` only works per MAC; printers & servers use these |
| **Exclusion** | Addresses the server won't assign (fixed hosts must live here) | Without exclusions the pool eats your static stats |

## Options that make an address actually useful

```mermaid
flowchart LR
  S[DHCP ACK] --> O1[Option 1: subnet mask]
  S --> O2[Option 3: default gateway]
  S --> O3[Option 6: DNS servers]
  S --> O4[Option 15: domain suffix]
  S --> O5[Option 51: lease time]
```

An IP alone is useless — the **options** are the real payload. The server is authoritative for the whole config: gateway, DNS, NTP, and even the domain search suffix. That's why "I can ping the server but DNS is broken" often turns out to be "the DHCP scope points at the wrong DNS server."

## DHCP relay: one server, many segments

A DHCP server answers broadcasts on its own subnet — but offices typically have many VLANs. The **relay agent** (often the router/switch, or `ip helper-address` on Cisco / `dhcp-relay` on Linux) catches the broadcast, stamps its own address in `giaddr`, and forwards the request **unicast** to the server. The server uses `giaddr` to pick which scope to answer from — that's why a relayed client's IP comes from the *right* subnet without any client-side config.

## Security and stability

- **DHCP starvation**: exhaust the pool with fake `DISCOVER`s so legitimate devices get nothing. Guard with DHCP snooping (trust switch ports only) and pool monitoring.
- **Rogue DHCP**: a rogue server offering `10.10.10.1` as gateway gets all traffic. Prevent with DHCP snooping; detect by watching for unexpected servers.
- **Lease hygiene**: clients renew at T1 (50% of lease) and T2 (87.5%); a client that vanishes keeps its IP until the lease lapses. After a network redesign, flush stale leases (`dhcpd lease` files / IPAM cleanup).
- **Across clouds**: in AWS/Azure, DHCP is invisible — the VPC hands each NIC an address from the VNet/VPC CIDR and your "DHCP options set" replaces options 3/6/15 (gateway is implicit, DNS is the VPC resolver, domain is the option set).

## Tester checklist

- Change the scope's gateway or DNS option and confirm a renewed client picks it up immediately (`ipconfig /renew`, `dhclient -r && dhclient`).
- Verify reservations: reboot a printer and check it still owns its fixed IP, while other devices around it get pool addresses.
- Confirm lease timers behave: set a 2-minute lease, note the T1 renewal traffic, and confirm the server reclaims the address after expiry (`release` then no renewal).
- Test relayed subnets: get a device in VLAN 400 and confirm it received a VLAN-400-scope address with the correct gateway (proves `giaddr` works).
- Check for rogue DHCP: sniff for unanswered `OFFER`s from unknown servers.
