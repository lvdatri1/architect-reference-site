## What this system is

Data modeling is deciding **how to shape data before you store it**. The data architect's core move is recognizing that the *same* business facts need two different models: a **transactional model** (normalized, write-optimized, for the apps) and an **analytical model** (denormalized, read-optimized, for reporting). The star schema is the analytical model's default shape — and misunderstanding why it's a star is where most data teams lose their way.

```mermaid
erDiagram
    "Operational DB - 3NF, write-optimized" ||--o{ "Model the same facts for analysis" : "extract + transform"
    "Model the same facts for analysis" ||--o{ "Fact table - measures and foreign keys" : "facts"
    "Fact table - measures and foreign keys" ||--o{ "Dimension date" : "date_key"
    "Fact table - measures and foreign keys" ||--o{ "Dimension customer" : "customer_key"
    "Fact table - measures and foreign keys" ||--o{ "Dimension product" : "product_key"
    "Dimension date" ||--o{ "BI queries - filter and group by dims" : "by month"
    "Dimension customer" ||--o{ "BI queries - filter and group by dims" : "by region"
    "Dimension product" ||--o{ "BI queries - filter and group by dims" : "by SKU"
```

```mermaid
flowchart LR
  OPS[(Operational 3NF)] -->|ETL/ELT| FACT[fact_sales]
  FACT -->|date_key| D1[dim_date]
  FACT -->|customer_key| D2[dim_customer]
  FACT -->|product_key| D3[dim_product]

  D2 --> BI

```

## The two models, side by side

| | Transactional (OLTP) | Analytical (star schema) |
| --- | --- | --- |
| Model | Normalized (3NF), minimal duplication | Denormalized: one fact + joined dimensions |
| Optimized for | Fast writes, consistent single records | Fast reads, big scans, filtering by dimension |
| Shape | Many small related tables | A few wide fact tables + dimension tables |
| Example | `orders`, `order_lines`, `customers`, `products` all separate | `fact_sales(amount, qty, date_key, cust_key, prod_key)` |
| Driven by | Apps, transactions | BI, reports, analytics |

A star schema is simply a **fact table in the middle** (the measurements: `amount`, `quantity`) surrounded by **dimension tables** (the descriptors: date, customer, product). Every dimension links to the fact by a surrogate key. It's a star because lots of small dimension tables point *at* one central fact.

## Facts vs dimensions: the two kinds of table

```mermaid
flowchart TB
  F[fact table] --> FM[Measures: amount, qty, duration<br/>these are the numbers you sum/avg]
  F --> FK[Foreign keys to every dimension<br/>the descriptors of each event]
  D[dimension table] --> DL[Label + attributes: name, region, category]
  D --> SK[Surrogate key - stable, not the source id]
```

- **Fact tables** hold *measures* (numbers you aggregate) and *foreign keys* into dimensions. They grow huge; queries filter and group by dimension attributes, then sum the measures.
- **Dimension tables** hold *descriptive attributes* (labels you slice by). The **surrogate key** is key: it decouples the warehouse from source-system IDs that get reused or changed.
- **Degenerate dimensions** live in the fact when a descriptor has no attributes of its own (e.g. an order number — it's a dimension with no extra columns, so keep it as a column, not a joined table).

## Granularity: the decision everything hangs on

```mermaid
flowchart TB
  Q[What does one row in the fact mean?] --> O1[One row per order line]
  Q --> O2[One row per order]
  Q --> O3[One row per day per product]
  Q --> O4[One row per event - finest]
  G[Granularity decided - <br/>you can aggregate, never split]
```

The granularity of a fact table ("each row = one order line") is fixed when you build it. You can **always aggregate up** and lose detail — you can *never* split one order line back into two rows later. Choosing granularity too coarse ("sales by day") makes "hourly by region" impossible later. Coarse granularity is the classic irreversible modeling mistake.

## Normalization trade-offs, in the architect's chair

| Choice | Wins | Costs |
| --- | --- | --- |
| 3NF operational schema | Consistent updates, no duplication, app-friendly | Slow analytical queries, many joins |
| Star/denormalized dimensions | Fast reads, obvious query paths, BI-friendly | Load-time complexity, joins in load, dimension maintenance |
| **Slowly changing dimensions (SCD)** | History preserved ("old address" still answers "what was it then") | More rows, type-1 vs type-2 trade-offs |

**SCD type-2** (keep a current row + a history row keyed by effective dates) is the standard answer to "customers change their region — do old reports rewrite history?" The answer is no: preserve the dimension version at event time. SCD type-1 (overwrite) is for attributes only useful in the present.

## Tester checklist

- Query the star and confirm the shape: any report reads *one* fact and *joins* the dimensions it needs — no dimension-dimension joins.
- Force a granularity trap: aggregate the finest fact up to "per month" and confirm it's exact; then try to split it back and confirm the data is gone for good.
- Change a dimension attribute (a customer's region) and verify type-2 history: the report for last month still shows the old region, the current view the new one.
- Confirm surrogate keys are stable: a source id reused/reassigned must not corrupt the fact (that's what the surrogate key prevents).
- Check for fan-out/duplication: one order with two line items must not double-count in the fact if your grain is per-order-line.
