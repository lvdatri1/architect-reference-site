## What this system is

DevOps is not a tool — it's the **feedback loop**: an outcome is wanted (ticket), a change is made (git), proven (pipeline), shipped (release), observed (metrics/alerts), and the loop closes when the next ticket reflects what actually happened. Each guide in this module is one stage of the loop.

```mermaid
stateDiagram-v2
  [*] --> Ticket
  Ticket: Ticket - user needs X
  Ticket --> Commit: the why
  Commit: Commit + PR
  Commit --> Pipeline: build + test
  Pipeline: Pipeline - lint, test, deploy
  Pipeline --> Release: ship
  Release: Release to prod
  Release --> Observe: is-it-fine
  Observe: Observe - metrics and alerts
  Observe --> Feedback: lessons
  Feedback: Feedback - next requirement
  Feedback --> Ticket: loop closes
  Feedback --> [*]
```

```mermaid
flowchart LR
  T[Ticket: user needs X] --> C[Commit + PR]
  C --> P[Pipeline: lint, test, build, deploy]
  P --> R[Release to prod]
  R --> O[Observe: logs, metrics, alerts]
  O --> F[Feedback: what broke / what improved]
  F --> T
```

## Who touches what, and where it lives

| Artifact | Owned by | Lives in | The job |
| --- | --- | --- | --- |
| Requirement | Product/architect | Jira | The *why* |
| Change | Dev | git branch + PR | The *what* |
| Build | Pipeline | Artifact registry | The *proof* |
| Runtime truth | DevOps/SRE | Observability stack | The *is-it-fine* |
| Feedback | Everyone | Next ticket | The *loop* |

The discipline is **immutability of each link**: the ticket says why, the commit says what shipped, the artifact matches the tested code, and the alarm links back to the deploy. Break any link and incidents become archaeology.

## Deploy vs release, observability as a habit

```mermaid
flowchart TB
  DEP["Deploy (code in prod)"] --> REL["Release (users see it)"]
  REL --> OBS[Observe - dashboard + alerts + logs]
  OBS -->|anomaly| ROL[Rollback fast / feature-flag OFF]
  OBS -->|healthy| NEXT[Next ticket learns it]
```

The strongest teams separate **deploy** (dark, wrapped in features flags) from **release** (turning it on) — then observability, not speculation, drives the next step.

## Metrics that tell the truth

| Metric | Means | Trend that's good |
| --- | --- | --- |
| Lead time | From commit to production | Shrinking |
| Deploy frequency | How often you ship | Growing (safely!) |
| Change fail rate | % of changes that break prod | Low and stable |
| MTTR | Mean time to restore | Shrinking |
| Escaped defects | Bugs reaching users | Falling |

Watch the **co-variances** — deploy frequency up *and* fail rate up is a curve to notice, not a badge. The DORA metrics are the standard vocabulary here.

## Tester checklist

- Pick one release and walk the full chain in reverse: alarm → deploy SHA → artifact → build job → committing PR → ticket. Any dead link is a gap to fix.
- Confirm a prod rollback is a *practiced* flow: someone has done a canary-off/blue-green flip recently, not just "we could."
- Check the observability story behind every alert: each alarm has a runbook that names the ticket/library that produced it.
- Report the four DORA numbers for one month from your actual systems — where is the worst coefficient?
