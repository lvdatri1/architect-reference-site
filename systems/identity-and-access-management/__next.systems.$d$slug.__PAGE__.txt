## What this system is

Zero Trust starts with identity. IAM is the layer that answers permanently *"who is this?"* and *"what may they do?"* — for humans, service accounts, and workloads. If identity is wrong, every access decision built on top of it is wrong too. The four jobs of IAM: **prove** (sign-up/sign-in), **attribute** (roles/groups/claims), **issue** (tokens), and **revoke** (when access must end).

```mermaid
flowchart LR
  U[User] -->|credentials / MFA| IdP[Identity provider<br/>directory + SSO]
  IdP -->|assert identity| SSO[Single sign-on broker]
  SSO --> App1[App A via OIDC/SAML]
  SSO --> App2[App B via OIDC/SAML]
  IdP -->|provision / deprovision| Dir[(Directory store<br/>Entra ID / Okta / corporate AD)]
```

## The sign-in flow behind "one password"

```mermaid
sequenceDiagram
  participant U as User
  participant App as App A
  participant IdP as Corporate IdP
  participant MFA as MFA / FIDO2

  U->>App: wants to open reusable App A
  App->>IdP: redirect + OIDC/SAML request
  IdP->>U: login page
  U->>MFA: passkey / code / number match
  MFA-->>IdP: proof of second factor
  IdP->>App: grant token + user claims
  App->>IdP: validate token signature
  App-->>U: session established
```

Federation means the *corporate* IdP owns the proof; each app trusts the same source. One revoke at the IdP immediately kills access everywhere — the property every ZT design depends on.

## Lifecycle: where identity actually goes wrong

| Phase | What you do | Typical failure |
| --- | --- | --- |
| Provision | Auto-create account on hire, from HR feed | Manual, slow, delayed |
| Use | Groups from management/HR drive access | Groups drift, un-reviewed |
| Change | Role change re-scopes groups | Old rights linger to "not break anything" |
| Revoke | Offboard: disable IdP + kill sessions + deprovision | "Disabled but still licensed"; orphan service accounts |

The **orphaned account** is the quiet disaster: a service account with admin rights nobody monitors. Lifecycle automation and periodic access reviews are the counter-measures.

## RBAC vs ABAC (the authorization models)

| | RBAC (roles) | ABAC (attributes) |
| --- | --- | --- |
| Decides by | "You are an admin" | attributes: user, device, time, location, data tag |
| Pros | Simple, human-readable | Granular, context-sensitive |
| Cons | Role explosion as you grow | Policy sprawl if not disciplined |
| Fit | Small estates, clear job families | Zero Trust / conditional access at scale |

Most enterprises run both: RBAC for coarse grants, ABAC/conditional access to narrow *when* they apply.

## Tester checklist

- Offboard a user: account disabled, sessions killed, and all app entitlements gone — verify *actual* revoke, not just "disabled".
- Verify SSO reaches every app: no app quietly keeps its own credential store (shadow identity).
- Replay an old JWT after revocation and confirm it's rejected (short token TTL + revocation callback).
- Walk a role change: new group grants, old group removed — then review that nothing re-attaches via nested groups.
