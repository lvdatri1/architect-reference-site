## What this system is

One large frontend, one team, one big release. **Micro-frontends** split the UI into independently owned apps (checkout, catalog, accounts) composed into a single page at **runtime** — each with its own repo, deploy, and release cadence. The benefit is organizational (autonomy), not technical: the compounding cost is versioning, shared state, and cross-app consistency.

```mermaid
flowchart LR
  Shell[App shell<br/>navigation + layout] --> C[Remote: checkout module]
  Shell --> Cat[Remote: catalog module]
  Shell --> A[Remote: accounts module]
  C --> R[Each team ships independently]
  Cat --> R
  A --> R
```

## Build-time vs runtime composition

| | Build-time composition | Runtime (module federation) |
| --- | --- | --- |
| When | Each app is npm-built into the shell | Remote apps are fetched at runtime (shared runtime) |
| Version skew | One version, one release | Each remote flows on its own release |
| Failure blast | A bad dep blocks the whole build | A broken remote can degrade a region of the page |
| Rollback | One atomic deploy | Per-remote rollback, coordination required |
| Best for | Team boundaries with shared release | Large orgs with genuinely independent teams |

Module federation (Webpack/Rspack, Vite plugins) is the current runtime tooling: the shell `remote()`-imports modules and **shares** libraries (React, router) so duplicates don't balloon the bundle.

## How a page is composed

```mermaid
flowchart LR
  Shell[App shell] -->|bootstrap| Nav[Navigation + layout]
  Nav -->|lazy mount| Checkout[Checkout remote module]
  Nav -->|lazy mount| Catalog[Catalog remote module]
  Checkout -->|its own release| Page[Composed page]
  Catalog -->|its own release| Page
```

## The three agreements that keep it from collapsing

1. **Shared runtime contract**: which React/router versions, how remotes are exposed, and how events/navigation are typed — agreed once, enforced by the shell.
2. **State ownership**: no global store written by many remotes. Each module owns its state; cross-module data goes through the shell's event bus or an API, never shared mutable objects.
3. **Design tokens, not ad-hoc CSS**: styles flow from a shared token/CDN source so visual drift against each other stays low without a monorepo.

## When it's right (and when it isn't)

- **Right**: >3 teams on one product, genuine release independence needed, a real shared shell is maintained.
- **Wrong**: a two-person team "for flexibility" — you pay federating cost with no autonomy win. If the smoke-test becomes *"did all remotes load today?",* reconsider; you turned a feature app into a micro-SPOf.

## Tester checklist

- Load every route with one remote deliberately down — the page must fail graceful (that module degrades), not produce a blank shell.
- Verify version-mix works: a new checkout-release alongside an old catalog-release on the same shell.
- Measure bundle share: confirm shared modules (React/core) are fetched once, not duplicated per remote.
- Cross-module navigation must hold state and deep-links across remote boundaries.
