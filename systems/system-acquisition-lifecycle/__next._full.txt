## What this system is

Adding a new system to an organization is a **lifecycle with decision gates**, not a procurement event. It runs from *"we have a business need and no system for it"* through selection, implementation, and years of operation, to an eventual retirement that must not orphan the data. The whole chain is a single question repeated at each gate: **what must be true before we spend the next level of money and commitment?**

```mermaid
flowchart LR
  R[Analyze requirements] --> S[Select option - build vs buy]
  S --> C[Choose software / solution]
  C --> I[Implement - deploy + migrate]
  I --> O[Operate - maintain + evolve]
  O --> T[Retire - extract + decommission]
  T -.->|lessons| R
```

Each arrow is a gate. The lifecycle succeeds when every gate is crossed on *evidence* — a documented requirement, a scored option, a signed contract, a successful go-live, a clean exit — and fails when a phase is skipped on momentum.

## The five phases and their gates

| Phase | What you do | Artifact / decision | Exit gate |
| --- | --- | --- | --- |
| **1 · Analyze requirements** | Understand the real need, not the assumed solution | Requirements spec, success criteria, stakeholders | Every requirement is testable and has an owner |
| **2 · Select option** | Decide build vs buy vs extend vs outsource | Options analysis, recommendation | The rejected options are documented *and why* |
| **3 · Choose software** | Evaluate vendors/solutions against the spec | Shortlist, scored RFP, contract | Selection is scored against the spec, not the demo |
| **4 · Implement** | Configure, integrate, migrate data, train | Cutover plan, go-live record | Data migrated + verified; users trained; rollback defined |
| **5 · Operate** | Run, support, upgrade, evolve | SLAs, release cadence, roadmap | The system is owned, measured, and improveable |
| **6 · Retire** | Extract data, stop spend, decommission | Data extract, decommission plan | Nothing still depends on it; data is preserved or disposed |

The lifecycle's dirty secret: **phase 6 is usually the one nobody planned**, so data gets stranded, integrations keep pointing at dead systems, and the "new system" spend never actually ends.

## Analyze requirements — the phase that decides everything

```mermaid
flowchart LR
  Need[Business need] -->|baseline| Current[As-is - what exists today]
  Need -->|who + why| Stake[Stakeholders + pain]
  Current -->|gaps| Spec[Requirements spec]
  Stake -->|wants + constraints| Spec
  Spec -->|prioritize| Mapped[Must / should / could]
  Mapped -->|agree scope + budget| Criteria[Success criteria + cost budget]
```

The trap here is **skipping to the solution**. Requirements analysis must describe the *need* ("orders take 3 days to approve") before anyone names a product. And every requirement needs a **must / should / could** weight and a **cost ceiling** — because the selection phase will otherwise be decided by the shiniest demo, not the spec.

## Select option: build vs buy vs extend

| Option | Pick when | Hidden cost to budget |
| --- | --- | --- |
| **Buy / SaaS** | Need is common, market is mature | Integration, data migration, vendor lock-in |
| **Build custom** | Need is a differentiator, no fit | Long lifecycle, you own the bugs and roadmap |
| **Extend existing** | Adjacent system already holds the data | Technical debt, coupling to the legacy core |
| **Outsource / BPO** | Execution is not a core capability | Governance, hand-off quality, exit penalties |

The honest rule: **buy when the process is commodity, build when it is strategy.** And an option "analysis" that never seriously scored the other three options is a memo, not a gate.

## Choose software: the scored selection

A defensible selection scores candidates against the **requirements spec** — functional fit, integration effort, total cost of ownership, vendor viability, security posture — before any demo impressions. The pattern that saves organizations:

1. **Shortlist** from the spec, not from brand awareness.
2. **Scored RFP** — every candidate answers the same questions, weighted to must/should/could.
3. **Proof of concept** — the top candidate proves the riskiest integration against *your* data, not a scripted demo.
4. **Negotiate + contract** — lock the scored commitments (uptime, support SLA, migration help, exit data rights) into the contract.

**Demo theater** is the number-one selection killer: a polished demo hides the gaps the scored spec would have caught.

## Implement: configure, migrate, cut over

```mermaid
flowchart LR
  C[Configure + integrate] --> M[Migrate data]
  M --> V[Verify - reconcile + smoke test]
  V --> T[Train + communications]
  T --> G[Go-live cutover]
  G --> R[Rollback - rehearsed, not hoped]
  G --> L[Live support + hypercare]
```

Implementation converts the signed contract into a running system. The three things that break it:

- **Data migration treated as a copy job** — it is a reconciliation project; the old system and the new must agree on counts and totals before go-live.
- **Training as an afterthought** — a system the users don't trust gets bypassed by shadow spreadsheets.
- **Rollback as a hope** — the cutover plan must name the exact condition under which you *will* roll back, and prove it was rehearsed.

## Operate, then retire

- **Operate** — the system lives inside [ITIL change and release management](../itil-change-and-release-management) and [DevOps delivery loop](../devops-delivery-loop): owned, measured, upgraded, and improved on a roadmap. A system with no owner is already retired in spirit.
- **Retire** — the end game: extract all data in a usable, documented format, confirm nothing still depends on the system (integrations, reports, people), decommission the infrastructure, and stop the spend. A good exit is part of the contract from day one — **you cannot extract data the vendor won't release** unless it was negotiated.

## Tester checklist

- Requirements traceability: follow one must-have requirement from spec → selection score → contract → acceptance test → live.
- Selection evidence: audit the RFP scores and confirm the winning candidate actually outscored, not just out-demoed.
- Migration reconcile: run the parallel count/total check and find the discrepancies *before* cutover, not after.
- Rollback drill: execute the rehearsed rollback and confirm the old system and its data are actually intact.
- Exit drill: produce the data-extract and dependency inventory as if retiring today — if it can't be done, the contract is failing.
