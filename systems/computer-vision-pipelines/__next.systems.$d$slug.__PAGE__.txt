## What this system is

Computer vision turns pixels into decisions. A camera produces frames; your system must locate objects (**detection**), describe them (**classification**), track them across time (**tracking**), and often do it fast and close to the source. The model is the star, but four things decide whether a vision pipeline survives production: **data plumbing**, **preprocessing**, **model-serving**, and **the hardware** you run it on.

```mermaid
flowchart LR
  S[Camera / source] -->|frames| A[Acquire]
  A -->|decode + stabilize| P[Preprocess]
  P -->|resize + normalize| M[Model inference]
  M -->|boxes + classes + scores| R[Post-process]
  R -->|filter + dedupe| D[Decide & act]
  D -->|annotations| S1[(Event store)]
```

## Ingestion: streams, not files

```mermaid
sequenceDiagram
  participant C as Camera
  participant P as Stream hub
  participant W as Worker pool
  participant S as Storage
  C->>P: continuous frames (RTSP/WebRTC)
  P->>W: frames to workers
  W-->>P: {object, confidence, location}
  W->>S: annotated frame (sampled)
```

- **Frame rate vs value**: 30 fps of raw video burns bandwidth and GPU for little gain. Most pipelines sample — 1–5 fps for people counting, event-triggered capture for alerts.
- **Stream middleware** (Kafka, Kinesis, MQTT) buffers and fans frames out so a slow model never forces a dropped camera.
- **Sampled persistence**: store all detections (small JSON), store a *fraction* of full frames (they're huge and rarely needed later).

## Preprocessing: small, cheap, and consistent

```mermaid
flowchart TB
  I[Raw frame - e.g. 3840x2160] --> D[Decode to RGB]
  D --> R[Resize to model input - e.g. 640x640]
  R --> N[Normalize + color space]
  N --> P[Pack into tensor]
  P --> M[Inference]
```

Three rules that matter more than any model trick:

- **Match training preprocessing exactly** — resize method, mean normalization, channel order (BGR vs RGB) all quietly destroy accuracy if mismatched.
- **Do it before the model, off the critical path** — decode/resize with hardware acceleration (GPU/DSP, or codecs), never in Python loops.
- **Resize is a trade, not a detail** — smaller input = faster, but small objects disappear. Match input resolution to the smallest object you must detect.

## Detection vs classification

```mermaid
flowchart LR
  subgraph Detect["Object detection"]
    D1[Frame] --> D2[Bounding boxes<br/>+ class + confidence]
  end
  subgraph Classify["Classification"]
    C1[Single image] --> C2[One label<br/>e.g. defect / no defect]
  end
  subgraph Seg["Segmentation"]
    S1[Image] --> S2[Every pixel gets a class]
  end
```

Pick the cheapest tool that answers the question:

- **Classification** answers *"which one?"* — a single image in, one label out. Cheapest, fastest, best accuracy per compute.
- **Detection** answers *"where and what?"* — boxes, needed when objects are among clutter or multiple.
- **Segmentation** answers *"exactly which pixels?"* — expensive; use only when pixel-level boundaries matter (medical imaging, autonomous driving).

## Model serving: the latency stack

```mermaid
sequenceDiagram
  participant A as Application
  participant S as Served model (Triton / OpenVINO / TensorRT)
  participant G as GPU pool
  A->>S: batch of frames
  S->>G: batched inference
  G-->>S: boxes + scores
  S-->>A: structured results
```

- **Batch, don't stream one-by-one**: GPUs are throughput machines; group frames (even 4–8) to amortize fixed overhead.
- **Serve next to the data**: edge deployment (Jetson, edge GPU appliance in the factory/office) beats round-tripping frames to cloud — the latency and bandwidth math usually decides it: cloud for batch, edge for real-time.
- **Post-process off the model**: NMS (non-max suppression) to collapse overlapping boxes, confidence thresholds, and class filtering run cheaply in CPU code — don't pay GPU for them.

## The hardware reality

| Where it runs | Typical stack | When |
| --- | --- | --- |
| On-device / edge | CPU + DSP/NPU, INT8 quantized model | Real-time, privacy, offline |
| On-prem GPU | TensorRT/Optimized engine box | Sustained high fps, no cloud egress |
| Cloud | GPU instances, auto-scaled | Bursty, batch analysis, elastic cost |

Quantization (FP32 → INT8) is the classic lever: ~4× throughput for a small accuracy dip. Combined with pruning and distillation it is how models the size of a small LLM end up running on a $50 camera module.

## Tester checklist

- **Data mismatch**: feed preprocessed frames and raw frames to the same model assert accuracy is the same — preprocessing must not be the silent accuracy killer.
- **Corner cases**: occluded objects, low light, mirrored images, and frames with the same object partially cut off at frame edges.
- **Determinism**: two runs over identical inputs should produce identical outputs (watch floating-point variance across batch sizes).
- **Latency SLO**: measure end-to-end p95 under load, not the model's reported single-inference time — queueing and batching dominate.
- **Drift**: the live distribution (lighting, angles, season) drifts from training data; sample new detections periodically and compare confidence distributions.
