## What this system is

A typical modern API is not one server — it is a chain of components. Understanding where time is spent (and where failures can happen) in that chain is the core of backend work.

```mermaid
flowchart LR
  A[Client] -->|HTTP 1.1 / 2| B[Load Balancer]
  B --> C[API Gateway]
  C -->|throttle + auth| D[Application Server]
  D -->|cache read| E[(Redis Cache)]
  D -->|cache miss| F[(Database)]
  D -->|async| G[(Message Queue)]
  E --> D
  F --> D
```

## The request, step by step

1. **Client** sends an HTTP request. This may set timeouts, authentication headers, and an `Idempotency-Key`.
2. **Load balancer** picks a healthy instance. Health checks prune unhealthy nodes so traffic never reaches a dead server.
3. **API Gateway** applies cross-cutting rules: authentication, rate limiting, request logging, and request validation.
4. **Application server** executes the controller logic. It checks a cache first; on a hit it skips the database entirely.
5. **Database** answers the query if the cache missed. The result is written back to cache so the next read is fast.
6. **Response** travels back along the same path.

## Components you should know

| Component | Responsibility | Failure mode |
| --- | --- | --- |
| Load balancer | Distribute traffic, health checks | Single point of failure unless configured active/passive |
| API Gateway | Auth, throttling, routing | A misconfigured rule can block all traffic |
| Application server | Business logic, orchestration | Slow downstream calls cause timeouts and cascading load |
| Cache | Serve hot reads fast | Stale data if invalidation is missed |
| Database | Durable source of truth | ACID guarantees, but slow under lock contention |

## Why it matters

Most production incidents are not "the database fell over" — they are latency cascading up the chain until the load balancer marks instances unhealthy and the platform restarts them in a loop. Knowing the chain is the difference between debugging an outage and guessing at it.

## Sequence view

```mermaid
sequenceDiagram
  participant C as Client
  participant G as Gateway
  participant A as App Server
  participant R as Redis
  participant D as Database

  C->>G: GET /orders/42
  G->>A: forward (rate limit OK)
  A->>R: GET orders:42
  alt cache hit
    R-->>A: cached order
  else cache miss
    A->>D: SELECT * FROM orders WHERE id=42
    D-->>A: row
    A->>R: SET orders:42 (TTL 300s)
  end
  A-->>G: 200 OK + JSON
  G-->>C: response
```
