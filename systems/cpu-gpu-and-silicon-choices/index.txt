## What this system is

Every compute decision comes down to two mismatches. **CPU vs GPU**: a CPU is a few very fast, generalist cores built for latency; a GPU is thousands of small, specialized cores built for throughput. **ARM vs x86**: two instruction-set architectures (ISAs) that have converged in performance while diverging in economics. Neither is "better" — each wins a different job, and choosing wrong is the most expensive mistake in cloud bills and ML latency.

## CPU vs GPU: latency vs throughput

```mermaid
flowchart LR
  subgraph CPU["CPU - few, fast, generalist"]
    c1[8-64 cores]
    c2[~3-5 GHz] --> c3[Branch prediction<br/>cache hierarchies]
  end
  subgraph GPU["GPU - many, small, specialized"]
    g1[thousands of cores]
    g2[Lower clock - ~1-2 GHz] --> g3[Massive parallelism<br/>SIMT lanes]
  end
  W[Workload] --> Q{Shape?}
  Q -- few, sequential, branchy --> CPU
  Q -- many, parallel, uniform --> GPU
```

- **CPU** is optimized for **latency**: complex control flow, big caches, deep pipelines, strong single-thread performance. It runs your web server, your database queries, anything unpredictable.
- **GPU** is optimized for **throughput**: thousands of cores execute the same instruction on different data in lockstep (SIMT). Great where the same math runs on millions of points — graphics, matrix multiply, vector search, training batches.
- The GPU is **not fast at one thing**, it is fast at *many at once*. A single serial dependency chain runs slower on a GPU than on a CPU.

## The SIMT model in practice

```mermaid
flowchart TB
  Op[One instruction] --> B1[Data element 1] --> ALU[ALU lane]
  Op --> B2[Data element 2] --> ALU
  Op --> B3[Data element 3] --> ALU
  Op --> B4["Data element N (...)"] --> ALU
  ALU --> W1[Write results in parallel]
```

Matrix a×b where both are 1024×1024 = ~1 billion independent multiply-adds. A CPU core does them mostly one at a time; a GPU spreads them across cores so the whole thing finishes in the time a CPU takes for a few thousand. That's the entire story of why ML training lives on GPUs: **the work is embarrassingly parallel, so throughput wins**.

But the same shape helps you find GPU-bound *workloads* that aren't ML: image/video encoding, cryptographic hashing at scale, string/JSON processing, and **vector search** all parallelize.

## Where GPUs are a trap

```mermaid
flowchart LR
  Lockstep[Divergent branches] -->|"if value == null - half the threads idle"| Waste[Lanes wasted]
  Transfers[CPU-GPU transfers] -->|"copying data across PCIe"| Waste2[Latency hidden]
  Serial[Long serial chains] -->|"next step needs previous result"| Waste3[GPU idles]
```

Remember the classic exchange-rate failure: **data movement outweighs the math**. Copying 10 MB across PCIe (or network for cloud GPUs) can cost more than the compute would take on CPU. Cheap workloads + expensive transfers = GPU-accelerated *slowness*.

## ARM vs x86: the ISA split

```mermaid
flowchart TB
  subgraph x86["x86 - Intel / AMD"]
    a1[Complex instructions - CISC]
    a2[Backward compatible since 1978]
    a3[High single-thread per-core]
    a4[Decode-heavy - more power per work]
  end
  subgraph ARM["ARM - Apple / AWS Graviton / Ampere"]
    b1[Simple instructions - RISC]
    b2[Licensable - many vendors]
    b3[Many, efficient cores]
    b4[Lower power per work - better perf/W]
  end
```

- **x86** (Intel, AMD) is **CISC**: complex instructions, massive backward compatibility, extremely strong single-core. It remains the default for high-clock latency-bound work.
- **ARM** is **RISC**: simpler fixed-width instructions, and — crucially — **anyone can build one**. Apple (M-series), AWS (Graviton), Ampere, and Qualcomm all ship ARM because the ISA license is buyable.
- What flipped ARM from "phone chip" to "data center chip" is the **perf-per-watt equation**: Graviton and M-series deliver comparable throughput to x86 at a fraction of the power and cost.

## The real decision: perf-per-watt and total cost

```mermaid
flowchart LR
  W[Workload] --> Q{What dominates?}
  Q -- latency / single-thread --> X[High-clock x86]
  Q -- "throughput / parallel" --> G[GPU for math, ARM for scale-out]
  Q -- "sustained load, scale-out" --> A[ARM - Graviton / Ampere]
  Q -- "training / large vectors" --> G
```

- **Power density is now the ceiling.** Data centers sell watts, not cores. A chip that does the same work for half the power lets you run ~2× the workload in the same rack — this is why cloud providers push ARM instance families so hard.
- **Total-cost math**: ARM instances (e.g. AWS Graviton) routinely come out 20-40% cheaper for the same throughput on scale-out workloads — API servers, caches, web tiers, CI fleets.
- **x86 still wins where latency is the SLA and software is tied to x86 details**: some commercial databases and legacy binaries ship x86-only, making the "cheaper" ARM option a migration project.

## Choosing compute shape by workload

| Workload | Shape | Best silicon |
| --- | --- | --- |
| Web API, gateway, app tier | Latency, spiky, serial | ARM (scale-out) or x86 high-clock |
| Database OLTP | Latency, branchy | x86 high-clock / high cache; ARM where tuned |
| Batch / ETL / CI | Throughput, parallel | ARM many-core or GPU for math-heavy |
| ML training | Parallel math | GPU |
| ML inference | Mix — batch = GPU, real-time = CPU/edge | GPU for batch, quantized on CPU/NPU for edge |
| Vector search / encode | Parallel | GPU or ARM, measure |
| Legacy commercial software | Often x86-locked | x86 |

## Tester checklist

- **Benchmark the real mix, not a microbenchmark**: an ARM vs x86 decision measured on one synthetically parallel test lies — run your actual request mix and total-cost over a week.
- **Check power, not just speed**: compare perf-per-watt, since rack power and cooling cap your actual scale.
- **Software lock-in test**: run your observability, commercial DB, and security agents on the candidate ARM image before committing — dwarves hide in middleware.
- **GPU sanity check**: profile your kernel's PCIe transfer time vs compute time; if transfers dominate, the GPU is a liability.
- **Cost per result**: for ML workloads, measure cost per 1k inferences/train-epoch, not instance-hour price.
