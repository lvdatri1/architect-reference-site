## What this system is

AWS is a catalog of services; the art is knowing the ~15 that matter and how they compose. The canonical reference deployment: a **VPC** with public/private subnets across availability zones, a load balancer up front, compute in private subnets, a managed database, and object storage — all gated by **IAM**.

```mermaid
flowchart LR
  subgraph Pub["Public layer"]
    In[Internet] -- edge --> IGW[Internet gateway]
    IGW -- public route --> ALB[ALB<br/>multi-AZ]
  end
  subgraph App["App layer - private subnets"]
    ECA[EC2 - AZ a<br/>private subnet]
    ECB[EC2 - AZ b<br/>private subnet]
  end
  subgraph Data["Data layer"]
    RDS[(RDS<br/>multi-AZ)]
    S3[(S3 bucket)]
  end
  ALB -- route --> ECA
  ALB -- route --> ECB
  ECA -- SQL --> RDS
  ECB -- SQL --> RDS
  ECA -- assets --> S3
  ECB -- assets --> S3
```

  ALB --> S1[EC2 app server<br/>AZ a - private subnet]

## The services that matter, in one map

| Category | The workhorses | When to reach for them |
| --- | --- | --- |
| Compute | **EC2**, **Lambda**, ECS/EKS, Fargate | VMs; event-driven/serverless; containers |
| Storage | **S3**, EBS, EFS | Object lake hot+cold; volumes; shared fs |
| Network | **VPC**, Route 53, CloudFront, ALB | Private networks; DNS; CDN |
| Database | **RDS**, DynamoDB, Redshift | Relational/multi-AZ; NoSQL; warehouse |
| Identity | **IAM**, Cognito | Access control; user identity |
| Orchestration | CloudFormation/Terraform | Everything defined as code |

## Serverless vs always-on compute

```mermaid
flowchart TB
  Q[Workload shape?] --> R{Load is...}
  R -->|spiky / event-driven| L[Lambda + SQS/EventBridge<br/>pay per invocation]
  R -->|steady or stateful| E[EC2 / ECS<br/>predictable, cheaper sustained]
  R -->|containerized microservices| K[ECS / EKS - managed k8s]
```

Lambda scales to zero and bills per millisecond — great for APIs, event handlers, glue. EC2/EKS wins when you need predictable sockets, long-lived state, or lowest steady cost. The trigger mapping (S3 events → Lambda, SQS → Lambda) is the glue.

## IAM in five minutes

```mermaid
flowchart LR
  U[User / service / Lambda role] --> Pol[Policy: what action on what resource]
  Pol --> Res[S3 bucket, RDS, API endpoint]
  Policy[Allow s3:GetObject on own bucket prefix]
```

Rules that never break: **identity-based policies** attach to users/roles; **resource-based policies** attach to the thing (bucket policy). A call must be allowed by BOTH where both exist. Least privilege is not a tweak — it's how you avoid "the whole team has Administrator on prod."

## The mistake repeatedly remembered

- Public security group on the database. (Fail the Friday random-scan chat.)
- One IAM user per human with an access key in a notes file — short-lived, role-using credentials, MFA.
- Single-AZ "because it's cheaper" — [fundamentals](../cloud-computing-fundamentals) says lose-one-AZ-without-down-time is the bar for anything important.

## Tester checklist

- Confirm IAM least privilege: the app's role can *only* touch its own S3 prefix, its DB, and outbound to what it needs.
- Delete/stop a Node in the private subnet and verify the ALB health-checks it out and the remaining Node serves.
- Verify an S3 event actually fires to Lambda on upload (object events are the glue in most pipelines).
- Do the cost report drill: right-size the three most expensive resources you found this month.
