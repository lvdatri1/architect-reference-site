## What this system is

The OSI (Open Systems Interconnection) model is a **reference model**: seven named layers that describe what must happen for data to leave one application and arrive at another. It is not a protocol — no packet carries an "OSI layer 5" header. Its job is to give engineers a shared vocabulary and a way to reason about *where* a problem lives before you go digging.

The internet does not run on OSI — it runs on the five-layer TCP/IP model. OSI is the lens you use to talk about it: HTTP is layer 7, TCP is layer 4, IP is layer 3, Ethernet is layer 2. When someone says "that's a layer 2 problem" or "the switch only works at L2," they are speaking OSI.

```mermaid
flowchart TB
  L7["L7 Application<br/>HTTP, SMTP, DNS"] -- down --> L6["L6 Presentation<br/>encoding, encryption"]
  L6 -- down --> L5["L5 Session<br/>dialogs, checkpoints"]
  L5 -- down --> L4["L4 Transport<br/>TCP / UDP"]
  L4 -- segments --> L3["L3 Network<br/>IP routing"]
  L3 -- packets --> L2["L2 Data link<br/>Ethernet / Wi-Fi"]
  L2 -- frames --> L1["L1 Physical<br/>signal on wire"]
  L1 -- bits --> O[Other host / network]
```

## The seven layers

```mermaid
flowchart TB
  L7[7 Application<br/>human-facing protocols: HTTP, SMTP, DNS, TLS sits above it] --> L6[6 Presentation<br/>syntax: encoding, compression, encryption]
  L6 --> L5[5 Session<br/>dialog control: who talks, checkpoints]
  L5 --> L4[4 Transport<br/>end-to-end delivery: ports, reliability, ordering]
  L4 --> L3[3 Network<br/>routing: logical addressing, hop-by-hop]
  L3 --> L2[2 Data link<br/>local delivery: MAC addressing, frames, error detection]
  L2 --> L1[1 Physical<br/>raw bits: voltage, light, radio, timing]
```

| Layer | Unit | Your cast of characters | Typical gear |
| --- | --- | --- | --- |
| 7 Application | Message | HTTP, SMTP, DNS, SSH, RDP | Apps, browsers, mail clients |
| 6 Presentation | — | TLS's crypto+encoding, JPEG/PDF decoding | Libraries, codecs |
| 5 Session | — | Sockets, RPC dialog state, checkpoint/resume | OS session layer, SMB sessions |
| 4 Transport | Segment / datagram | TCP, UDP, QUIC | OS kernels, load balancers |
| 3 Network | Packet | IP, ICMP, BGP, OSPF | Routers, L3 switches, firewalls |
| 2 Data link | Frame | Ethernet, Wi-Fi (802.11), ARP | Switches, bridges, NICs |
| 1 Physical | Bits | Copper, fibre, radio, signal encodings | Cables, optics, repeaters, AP radios |

**Mnemonic** (top-down): *All People Seem To Need Data Processing*; bottom-up: *Please Do Not Throw Sausage Pizza Away*.

## Encapsulation: each layer wraps the one above

```mermaid
flowchart LR
  A[L7 message: GET /users] --> B[L4: TCP header + message]
  B --> C[L3: IP header + TCP + message]
  C --> D[L2: Ethernet header + IP + TCP + message + FCS]
  D --> E[L1: bits on the wire]
```

The receiving host peels headers in reverse: the NIC checks the frame (L2), the kernel routes the packet (L3), demuxes the port (L4), and hands the message to the process (L7). **Middle boxes** live off to the side: a router reads L3 to forward (it does not care about your TCP or HTTP), a switch reads L2, a load balancer reads L4 (or L7 if it terminates TLS).

## Where OSI differs from TCP/IP

| | OSI (7 layers) | TCP/IP (5 layers, what's real) |
| --- | --- | --- |
| Application | 7, 6, 5 split three ways | One Application layer |
| Transport | 4 | TCP / UDP |
| Internet | 3 | IP (plus routing protocols) |
| Network access | 2 + 1 | Link + Physical |
| Status | Reference model | The actual internet |

The classic trap: "SSL/TLS is layer 6." TLS is *usually* described as layer 6 because it encrypts payloads, but it rides inside TCP (layer 4) and outside the app protocol. For debugging, what matters is **where** it sits in the byte stream, not the layer number.

## Using the model to debug

- **"Layer 2 issue"** — cables, switches, VLANs, MAC, ARP, duplicate IP on the same segment. Symptoms: link flaps, broadcast storms.
- **"Layer 3 issue"** — routing, addressing, subnets, next-hops, ACLs. Symptoms: `destination host unreachable`, asymmetric routes.
- **"Layer 4 issue"** — ports, firewalls, NAT, TCP state. Symptoms: timeouts instead of refused, connections hang after handshake.
- **"Layer 7 issue"** — app behavior: 500s, TLS handshake errors, slow queries. Everything below it worked; the problem is in your code.

Practical debugging always runs the stack top-to-bottom or bottom-to-top: `curl` (L7) → `ss -tnp` (L4) → `traceroute` (L3) → `ping` (L3) → link lights (L1).

## Tester checklist

- Reproduce a failure and classify it by layer: an HTTP 500 is layer 7 even if the server's CPU is at 100% — don't call the network team for a database timeout.
- Verify a firewall rule change at L4 (port open) still blocks nothing at L7: confirm with a real request, not just `nc -zv`.
- Check ARP (L2) when a machine "can't reach the gateway": `arp -a` shows whether the MAC for the default gateway resolved.
- Confirm TLS termination point (L6/L7) matches your threat model — if the LB decrypts, it sees plaintext.
