## What this system is

Google Cloud (GCP) is a catalog of services; the art is knowing the ~15 that matter and how they compose. Its identity differs from the other clouds in three ways: **Kubernetes-first** (GKE was Google's own creation, so containers are native), **serverless-grade managed services** (Cloud Run, BigQuery, Spanner were built by the company that runs them at Google scale), and **data/ML as a first-class story** (BigQuery, Dataflow, Vertex AI are its strongest draw). The canonical reference deployment: a **VPC** with public/private subnets across regions, a load balancer up front, compute on GKE or Cloud Run in private subnets, managed databases, object storage, and everything gated by **IAM**.

```mermaid
flowchart LR
  In[Internet] --> LB[Global load balancer<br/>regional backends]
  LB --> CR[Cloud Run - container<br/>scale to zero]
  LB --> GKE[GKE - Kubernetes<br/>cluster]
  CR --> SQL[(Cloud SQL<br/>regional HA)]
  GKE --> SQL
  CR --> GCS[(Cloud Storage - bucket)]
  GKE --> GCS
  Pub[Pub/Sub topic] --> CF[Cloud Functions -<br/>event handler]
  CF --> SQL
```

## The services that matter, in one map

| Category | The workhorses | When to reach for them |
| --- | --- | --- |
| Compute | **Compute Engine**, **GKE**, **Cloud Run**, Cloud Functions | VMs; Kubernetes (native); serverless containers; event functions |
| Storage | **Cloud Storage**, Persistent Disk, Filestore | Object storage hot+cold; volumes; shared fs |
| Network | **VPC**, Cloud Load Balancing, Cloud CDN, Cloud DNS | Private networks; global LB; edge caching; DNS |
| Database | **Cloud SQL**, **Spanner**, **BigQuery**, Firestore | Relational HA; planetary-scale relational; warehouse; NoSQL |
| Streaming | **Pub/Sub**, Dataflow | Async messages; event streams |
| Identity | **Cloud IAM**, Identity-Aware Proxy (IAP), Workforce pools | Access control; user identity |
| Orchestration | Terraform, Cloud Deployment Manager | Everything defined as code |

## The key architecture: serverless-first compute

```mermaid
flowchart TB
  Q[How to run this workload?] --> R{Shape?}
  R -->|container, autoscaled, scale-to-zero| RUN[Cloud Run -<br/>your default for services]
  R -->|event function| FNS[Cloud Functions -<br/>glue, small handlers]
  R -->|Kubernetes needed| GKE[GKE -<br/>native k8s, full control]
  R -->|stateful / very custom| VM[Compute Engine -<br/>VMs]
```

GCP's default posture is **Cloud Run first**: a container that scales to zero, autoscales, gives you a URL and canary versions, and bills only while serving. It's the "containers without Kubernetes" story. Reach for **GKE** when you need k8s-native features (stateful sets, node pools, specialized scheduling, GPU/TPU workloads), and **Cloud Functions** for event glue. Compute Engine is the escape hatch for anything that needs a plain VM. The decision, condensed: **container? Cloud Run. Needs k8s? GKE. Tiny event? Cloud Functions. Everything else? Compute Engine.**

## GKE: Kubernetes as a native service

```mermaid
flowchart TB
  subgraph Cluster["GKE cluster"]
    subgraph Control["Control plane (managed)"]
      API[API server -<br/>fully managed]
    end
    subgraph Nodes["Node pools"]
      N1[Autoscaled node pool]
      N2[GPU / TPU pool]
    end
  end
  API --> N1
  API --> N2
```

GKE is Google's own Kubernetes as a managed service: the control plane is Google-managed (you never patch the API server), and node pools autoscale. The k8s fundamentals — deployments, services, probes, scheduling, scaling — all apply ([Kubernetes and container orchestration](../kubernetes-and-container-orchestration) is the mechanics). The GCP-specific decisions: **which node pool** (standard VMs vs Spot vs GPU/TPU), **regional vs zonal cluster**, and **Autopilot vs Standard** (Autopilot = fully managed nodes and less tuning; Standard = you own node pools).

## The data crown jewels

| Service | What it is | When it wins |
| --- | --- | --- |
| **Cloud SQL** | Managed MySQL/Postgres/SQL Server with HA + backups | Your default relational database, single-region needs |
| **Spanner** | Horizontally scalable relational with external consistency | Need *global* relational: multi-region writes, no leader election problem |
| **BigQuery** | Serverless columnar data warehouse | The [warehouse](../data-warehouse-lakehouse-architecture) for big analytics; no servers, pay per query |
| **Firestore** | Managed NoSQL document store, realtime sync | Mobile/web realtime apps, game state, IoT |
| **Cloud Storage** | Object storage with classes (hot/cold/archive) | The universal "files and artifacts" layer |

The pattern that marks a GCP estate: **BigQuery as the analytics center**. Because it's serverless and fast, it becomes the destination for events (via Pub/Sub → Dataflow or BigQuery Storage Write), replacing a self-hosted warehouse. The common trap is *choosing Spanner when Cloud SQL suffices* — Spanner's power costs real money and operational nuance, and single-region relational apps are usually fine on Cloud SQL.

## Pub/Sub and the async spine

```mermaid
flowchart LR
  Prod[Producer - app / function / GKE] -->|publish| TOPIC[Pub/Sub topic]
  TOPIC -->|push / pull| SUB[Subscription]
  SUB --> C1[Cloud Run / Functions consumer]
  SUB --> C2[Dataflow / BigQuery sink]
```

Pub/Sub is Google's managed [pub/sub messaging](../pub-sub-event-streaming): topics, subscriptions with push/pull delivery, exactly-once-ish via message IDs plus at-least-once semantics, and ordering per ordering key. It's the spine that decouples GCP services (storage events → Cloud Functions, streaming data → Dataflow → BigQuery) and its serverless nature means consumers scale without you provisioning brokers.

## IAM and Identity-Aware Proxy

```mermaid
flowchart LR
  U[User / service account] --> Role[IAM role -<br/>what action on what resource]
  Role --> Res[Cloud Run service,<br/>bucket, BigQuery dataset]
  Ext[End-user - via Google / external identity] --> IAP[Identity-Aware Proxy -<br/>checks identity before reach]
  IAP --> App[Your app - no VPN needed]
```

- **Cloud IAM** is role-based: roles (owner/editor/viewer, plus fine-grained roles like `roles/run.invoker`) attach to principals (users, groups, **service accounts**) and grant actions on resources. Service accounts are the "workload identity" of GCP — every compute instance/Cloud Run revision runs as one. The rules are the same least-privilege discipline as everywhere: roles scoped as tight as possible, no "editor on everything."
- **Identity-Aware Proxy (IAP)** is GCP's zero-trust application gate: it checks identity + context *before* traffic reaches your app, so internal apps don't need a VPN or public exposure. It's the GCP-native [zero trust](../zero-trust-architecture) move — put IAP in front of private apps and lock the rest of the network down.

## The mistake repeatedly remembered

- **Public exposure of the database** — a Cloud SQL instance with an external IP and open auth, discovered by a scanner in a day.
- **Default-to-VM** — reaching for Compute Engine when Cloud Run would do; you pay for an always-on machine to run a service that idles 90% of the time.
- **Spanner "because it scales"** — planetary-scale relational that a single-region Cloud SQL would serve at a fraction of the cost and complexity.
- **Wide IAM** — a service account with `roles/editor` "so it's not annoying," leaking the blast radius across every project.
- **One region, no HA story** — everything in a single zone/region "for simplicity," violating the [cloud fundamentals](../cloud-computing-fundamentals) bar.
- **Pub/Sub duplicate blindness** — consumers that don't handle at-least-once, so a retried message creates a duplicate downstream.

## Tester checklist

- **IAM least privilege**: confirm the app's service account can only reach its own bucket prefix, its DB, and what it needs — no editor/owner anywhere.
- **Cloud Run scale-to-zero**: idle a service and confirm it scales to zero (no running instance, no billing), then a request warms it back up.
- **GKE node-pool autonomy**: drain/cordon a node and confirm the cluster re-schedules pods to a healthy pool without downtime.
- **Load balancer failover**: stop the primary backend region and confirm the global LB routes to the secondary with no client-visible outage.
- **Pub/Sub delivery**: publish a message, kill a consumer mid-delivery, and confirm redelivery (at-least-once) and that your consumer dedupes.
- **BigQuery cost guard**: run a query over a large table and confirm the bytes-scanned estimate and cost controls (no unbounded scans).
- **IAP gate**: attempt to reach a private app without IAP identity and confirm it's blocked before your app even sees the request.
