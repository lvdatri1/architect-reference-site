## What this system is

Oracle Integration Cloud (OIC) is Oracle's managed **integration service**: the tool that stitches Oracle SaaS (Fusion ERP, HCM, CX) to each other, to OCI, and to the outside world (REST, SOAP, FILE, email, on-prem). It is most often deployed because **Oracle SaaS must talk to SAP or a CRM or a warehouse**, and someone has to own the plumbing. Its reason to exist mirrors Oracle Cloud Infrastructure's: native, managed connectivity into the Oracle estate where a generic iPaaS is a worse fit.

```mermaid
flowchart LR
  subgraph OIC["Oracle Integration Cloud"]
    I[Integrations -<br/>REST / SOAP / DB adapters]
    F[FBDI / file flows -<br/>bulk load]
    P[Process Automation -<br/>human workflow]
    M[Monitoring -<br/>dashboards, DLQ, logs]
  end
  subgraph Sources
    S1[Oracle Fusion ERP / HCM / CX]
    S2[OCI services]
    S3[On-prem - via remote agent]
  end
  subgraph Targets
    T1[SAP / legacy]
    T2[Files - SFTP / object storage]
    T3[CRM / custom REST]
    T4[Databases - DB adapter]
  end
  Sources --> OIC
  OIC --> Targets
```

## The layers that matter

| Layer | What it is | The mental model |
| --- | --- | --- |
| **Integrations** | The workhorse unit: a flow of connections + expressions + mapping | OIC is "an integration per business process" |
| **Connections** | Pre-built adapters and endpoints (Fusion, REST, SOAP, DB, FILE, FTP, Kafka...) | Each is a configured tile you wire into flows |
| **FBDI / file uploads** | Bulk data exchange into Fusion via Oracle's own file batch templates | Load data *in bulk*, not via per-record APIs |
| **Process Automation** | Human-in-the-loop workflows (approvals, forms) — the old OIC Process Cloud | The "Logic Apps-style" orchestration arm |
| **Remote agent** | On-premise connector agent for reaching internal systems securely | Bridges OIC in the cloud to your network |
| **Monitoring / dashboards** | Run state, errors, dead-letter messages, metrics | OIC owns an ops surface, not just a flow editor |

The one-line mental model: **an integration is a named flow with a trigger** — maybe REST or SOAP, maybe a file drop or an on-prem DB query — that calls one or more downstream connections and maps data between them.

## Anatomy of an integration flow

```mermaid
sequenceDiagram
  participant T as Trigger (REST / SOAP / FILE / SCHEDULE)
  participant E as Expression & mapping (XSLT)
  participant S as Stage - call connection
  participant M as Monitoring / error handler

  T->>E: payload arrives
  E->>S: map + enrich data
  S-->>S: invoke Fusion SOAP / REST adapter
  alt success
    S-->>M: log success, close tracking
  else error
    S-->>M: dead-letter / retry policy
  end
  M-->>T: response to caller
```

- **Triggers** define *how* the integration starts: a REST endpoint you expose, a scheduled batch (poll an FBDI or DB), or a file-arrival watcher.
- **Stages** hold the orchestration: invoke adapters, run expressions, add conditions, branch, transform with the built-in XSLT mapper.
- **Every run is trackable**: OIC tracks each instance with a business identifier, status, and error detail — that's the "why did it fail?" answer you get without writing observability.
- **Error handling** is a first-class stage: catch, retry with backoff, and write to a dead-letter location so a bad payload never silently disappears.

## FBDI: how bulk data actually moves

| Mechanism | When used | Gotcha |
| --- | --- | --- |
| **REST/SOAP APIs** | Point-to-point, low-volume, event-driven | Per-record; slow for thousands of rows |
| **FBDI file load** (`File-Based Data Import`) | Bulk: GL journals, invoices, employees | Schema is Oracle's; validate before upload |
| **BIP/BICC export** | Getting reports/data *out* of Fusion | Bulk extracts land as files, not events |
| **DB adapter / polling** | On-prem or OCI database integration | Needs the remote agent, polling latency |

The architectural lesson inside OIC is the same as every integration stack: **low volume = API; high volume = bulk file flows.** OIC's file support is its strength for Oracle estates because Fusion has first-class bulk interfaces (FBDI) that a generic iPaaS doesn't know about — OIC surfaces them as a native file-upload flow with error reporting to an output file channel.

## OIC vs the alternatives

| Decision | When you choose OIC | When you don't |
| --- | --- | --- |
| Cloud | Mostly Oracle SaaS/Fusion in the picture | Pure multi-cloud iPaaS, cloud-agnostic team |
| iPaaS | OIC has managed Fusion adapters + bulk | Strong developer, wants Kubernetes/high-throughput |
| Logic Apps / Service Bus | ...your estate is Azure | ...estate is Oracle |
| Webhook / hand-rolled | Only 1-2 point integrations | Many integrations to govern |

The honest take: OIC is the right tool when the *center of gravity is Oracle*. It has managed adapters for Fusion that nothing else ships with, FBDI handling built in, and a license that typically comes bundled with Oracle SaaS entitlements. If your estate is cloud-native, polyglot, or high-throughput, a general iPaaS or Azure integration services will serve you better — drag in [Azure integration services](../azure-integration-services) if that's your main cloud.

## Getting data out of Oracle into the rest of the world

```mermaid
flowchart LR
  Fusion[Oracle Fusion ERP / HCM] -->|"SOAP/REST - OIC adapters"| OIC[OIC]
  OIC -->|"FBDI bulk - file"| Files[File / SFTP sharing]
  OIC -->|"webhook / REST"| AB[Anything that speaks HTTP]
  OIC -->|"ambassador - outbound"| SAP[SAP / legacy adapters]
  OnPrem -->|"remote agent"| OIC
```

OIC doesn't just expose Oracle to HTTP — it reverses: with the **remote agent** installed on-prem, OIC reaches back into SAP's BAPI/JCo, legacy files, and databases that live inside your network. That's the classic Oracle-adjacent integration: Fusion talks to SAP because OIC owns the bridge in both directions.

## Tester checklist

- **Trigger matrix**: hit the integration via REST, by file drop, and by schedule — confirm each trigger path lands and tracks an instance.
- **Failure trail**: make the downstream adapter fail (bad SOAP response), confirm retries with backoff, then confirm the error dead-letters and is visible in Monitoring with the business identifier.
- **Bulk import**: run an FBDI file with one bad row in the middle — confirm the partial-vs-failed semantics, the output error file, and that bad row didn't silently drop.
- **Idempotency**: deliver the same REST payload twice and confirm the integration doesn't create duplicates (validate its business-logic dedup).
- **Agent reach**: from OIC in the cloud, confirm the on-prem remote agent round-trip returns an accurate latency and a reliable connection status.
- **Data fidelity**: a mapping of a date, a decimal, and a null from Fusion → target must survive the XSLT map without drift.
