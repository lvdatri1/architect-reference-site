## What this system is

A backend framework turns "here is an HTTP request" into "here is a behaved response" in a predictable way: **middleware** runs first, a **router** picks a handler, the **controller/service** does the work, and the response goes back out — with error handling, auth, and logging as layers in between.

```mermaid
flowchart LR
  Req[HTTP request] --> MW[Middleware chain<br/>logging, auth, body parsing]
  MW --> RT[Router matches path + method]
  RT --> CT[Controller / handler]
  CT --> SV[Service layer - business logic]
  SV --> DB[(Database / external API)]
  DB --> SV
  SV --> CT
  CT -->|JSON / HTML| Res[Response]
  MW -->|error handler| Res
```

## A request through the framework

```mermaid
flowchart LR
  Req[HTTP request] -->|enter chain| MW[Middleware<br/>auth, logs, parse]
  MW -->|pass through| Router[Router<br/>method + path]
  Router -->|invoke handler| Svc[Controller to service]
  Svc -->|async IO| DB[(Database / IO)]
  DB -->|build payload| Res[Serialized response]
```

## Framework vs library

| | Library (Express, Fastify, Flask) | Framework (NestJS, Spring Boot, Rails, Django, ASP.NET Core) |
| --- | --- | --- |
| Who calls whom | Your code calls it per route | It provides a lifecycle; it calls you |
| Structure | You decide folders/patterns | Conventions + scaffolding baked in |
| Boilerplate | Minimal at first | More, but consistent across teams |
| The trade-off | Freedom, drift between devs | Discipline, harder to bend |

The classic first-project algorithm: **few endpoints + a small team → library; a product with many engineers → framework** — so the architecture isn't reinvented per feature.

## The framework map

| Framework | Language | Shape | Stands out for |
| --- | --- | --- | --- |
| Express / Fastify | Node.js | Minimal, middleware | APIs, microservices, start-ups of any size |
| NestJS | Node.js (TS) | Opinionated, DI modules | Structure, decorators, testability |
| FastAPI | Python | Async, type-driven | Fast iteration, auto OpenAPI docs |
| Django / Rails | Python / Ruby | Batteries, MVC, admin | CRUD products fast; conventions |
| Spring Boot | Java/Kotlin | Heavyweight, enterprise | Large orgs, strong typing, DI |
| ASP.NET Core | C# | High-perf, structured | Windows orgs, high throughput |

## Sync vs async (where the bugs live)

- **Thread-per-request** (Spring/Rails with blocking DB drivers): each request holds a thread. Fine until your pool fills under a slow DB — then requests queue.
- **Event-loop/async** (Node, Python `asyncio`, Kotlin coroutines): few threads multiplex many requests. Great for IO-bound work; dangerous if a handler blocks the loop with CPU work or a sync call.
- The bug that bites either way: **blocking the wrong model** — a CPU loop on an async loop, or seconds-long work on a single thread pool.

## Tester checklist

- Verify the full pipeline fires for one request: middleware ran in order, route matched, service called once, response shaped right (inspect logs/body).
- Confirm a middleware abort short-circuits the whole chain (auth rejection must not reach the controller or DB).
- Test error handling: an exception in the service must produce the framework's standardized error body, not a raw stack trace.
- Probe the blocking failure: hammer an endpoint that calls a slow service and confirm throughput degrades predictably (that's the async/latency signature).
