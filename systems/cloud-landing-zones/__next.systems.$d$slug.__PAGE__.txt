## What this system is

A **landing zone** is the scaffolding below your cloud: the account/subscription structure, shared identity, central networking hub, and governance guardrails that every new team consumes instead of rebuilding. Its job is to make *"deploy something new in the cloud"* a safe, fast, repetitive action — not a blank check.

```mermaid
flowchart TB
  Root[Organization / root] --> Mgmt[Management account]
  Root --> Security[Security account]
  Root --> Infra[Network account]
  Root --> Prod[Prod workload accounts]
  Root --> NonProd[Non-prod workload accounts]
  Mgmt -->|guardrails pushed down| Prod
  Mgmt -->|guardrails pushed down| NonProd
  Infra -->|shared VPC/VNet + egress| Prod
  Infra -->|shared VPC/VNet + egress| NonProd
```

## The pattern in one picture

```mermaid
flowchart LR
  A[Team: we need a workload] --> B[Pipeline asks for a new account/subscription]
  B --> C{Pre-built scaffolding applies}
  C --> D[Identity: SSO + least-privilege roles]
  C --> E[Network: landing zone VPC/VNet + peering]
  C --> F[Policy: encryption, budget, tagging]
  C --> G[Monitoring: logging + alert baseline]
  D --> H[Workload runs compliant from day one]
  E --> H
  F --> H
  G --> H
```

## The core building blocks

| Layer | What it provides | Without it |
| --- | --- | --- |
| Account/subscription structure | Separation between prod and non-prod, per-business-unit | One shared account with everything in it |
| Identity foundation | SSO, sign-on roles, break-glass, role per workload | Shared root keys, admin-role-everything |
| Network hub | Shared transit VPC/VNet, egress, private endpoints, on-prem links | Every team re-creates IP space, VPNs multiply |
| Guardrails | Policy (encryption, compliance), budgets, tagging | Config drift you discover in audits |
| Observability baseline | Central logging/audit trail, alert channels | Teams fly blind, incidents are archaeology |

## The identity and network seams

```mermaid
flowchart LR
  subgraph Seams["Workload seams"]
```

## Rules of the game

- **Guardrails beat documentation.** Policy turning a wrong config into a deploy failure beats a 40-page "cloud conventions" doc that nobody reads.
- **Every workload is its own isolated unit.** A future incident in one account can't pivot through the landing zone into the rest (the same logic as [micro-segmentation](../zero-trust-architecture)).
- **The landing zone is a product with an owner**, continuously versioned — not a one-time setup you did and forgot.
- **Break-glass stays boring.** Emergency access exists, sealed, rotated, and tested — used only when the normal path fails.

## Tester checklist

- Create a fresh workload account/subscription from the pipeline and verify it inherits policy, encryption, budget, and monitoring *before* any resource exists.
- Try to bypass: can a lone dev create a resource with no owner tag, or an unencrypted bucket, or an external VPN? The guardrails must block, not warn.
- Verify identity: the new account's only admin path is SSO + MFA; there is no long-lived root key in use.
- Break-glass drill: emergency admin credentials work, alert on use, and can be rotated/revoked afterwards.
