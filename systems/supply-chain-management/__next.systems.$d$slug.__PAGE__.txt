## What this system is

Supply chain management (SCM) is the **whole journey a product takes** from raw material to the customer's hands. It is not one system — it is a chain of systems (ERP, procurement, warehouse, transport, and planning tools) coordinated by a common set of numbers. The classic framing is the SCOR reference model: **Plan, Source, Make, Deliver, Return**.

```mermaid
flowchart LR
  PL[Plan] --> SO[Source]
  SO --> MK[Make]
  MK --> DE[Deliver]
  DE --> RE[Return]
  RE --> PL
```

## The two halves: planning vs execution

| | Planning (SCP) | Execution (SCE) |
| --- | --- | --- |
| Asks | *What should happen?* | *What is happening?* |
| Horizon | Weeks to months | Minutes to days |
| Key systems | Demand planning, S&OP, inventory optimization, supply planning | ERP, WMS, TMS, MES, OMS |
| Output | Forecasts, plans, purchase/delivery signals | POs, picks, shipments, production orders |
| Failure mode | Plan and reality drift apart | Firefighting without a plan |

The recurring architecture problem in SCM is **plan-execution gap**: the plan says X, the execution says Y, and nobody reconciles. The systems that close that gap — demand sensing, control towers, exception alerts — are where the real SCM value is being built.

## The demand → fulfillment chain

```mermaid
flowchart LR
  FC[Demand forecast] --> PL[Supply / inventory plan]
  PL --> PO[Purchase or production order]
  PO --> RCV[Receive or build]
  RCV --> ST[Stock position]
  ST --> ORD[Customer order]
  ORD --> OOS[Ship and deliver]
  OOS --> LF[Demand feedback - refresh forecast]
```

## The planning loop

Demand planning is a **closed feedback loop**, not a one-shot forecast: historical demand, sales inputs, and market signals feed a forecast; that forecast becomes a supply/inventory plan; execution produces actuals; actuals are compared to forecast; the plan is re-forecast. The metric that shows you a healthy chain is *forecast accuracy* — a single number that every downstream sub-system inherits.

```mermaid
flowchart LR
  Sig["Demand signals"] -->|model| FC["Forecast"]
  FC -->|net requirements| Plan["Supply + inventory plan"]
  Plan -->|signals| Exec["Execute - buy / make"]
  Exec -->|results| Act["Actuals + stock"]
  Act -->|actuals| Recon["Reconcile + re-forecast"]
  Recon -->|re-forecast| FC
```

## The bullwhip effect

Small demand changes amplify upstream: **order variability grows with distance from the customer**. A 5 % dip in retail demand can become a 40 % swing in factory orders if every tier over-reacts. The architectural cure is visibility and sharing: demand data propagating across tiers (not just order messages) and planning horizons that dampen reaction. When you test a "supply chain", this is the dynamics you are really testing.

## Tester checklist

- Forecast accuracy: given actuals, re-run the forecast and assert the accuracy metric and its tolerance are met/exceeded.
- Plan-execution reconciliation: inject a planned PO that the execution side fails to honor — a real exception must surface, not vanish.
- Netting logic: stock on hand + on order − demand must produce a defensible net requirement (no double-count, no missed safety stock).
- Data freshness: the plan must use the latest actuals; stale data must trip an alert, not silently plan from old numbers.
- End-to-end: a demand spike must cascade through forecast → plan → PO → receive → ship in a coherent trace.
