## What this system is

A **topic** in a pub/sub broker (Kafka, GCP Pub/Sub, SNS, RabbitMQ topic exchanges) decouples the thing that *happens* from everything that *reacts*. The moment an event lands, every subscriber that cares gets a copy — checkout service listeners, analytics pipelines, email senders, AI feature stores.

```mermaid
flowchart LR
  P[Checkout service] -->|publish order.placed| B[Broker: order.placed topic]
  B -->|fan-out copy| EM[Consumer: emailer]
  B -->|fan-out copy| AN[Consumer: analytics]
  B -->|fan-out copy| RE[Consumer: recommender]
  EM -->|at-least-once → dedupe| C[Persist id + commit offset]
```

```mermaid
flowchart LR
  P[Publisher<br/>checkout service] -->|event: order.placed| T{Order.placed<br/>topic}
  T --> C1[Email service]
  T --> C2[Inventory update]
  T --> C3[Analytics sink]
  T --> C4[AI recommender]
```

## Queue vs pub/sub

| | Queue (SQS, Rabbit work queue) | Pub/Sub (Kafka topics, SNS) |
| --- | --- | --- |
| Semantics | One consumer takes each message (competing consumers) | Every subscribed consumer group gets its own copy |
| Suits | Work distribution — jobs, tasks | Fan-out — events many systems must react to |
| State | Message deleted on ack | Retained in the topic (by retention/compaction) |

## Partitions and consumer groups

```mermaid
flowchart TB
  subgraph Topic["Topic: order.placed · 3 partitions"]
    P1[partition 0]
    P2[partition 1]
    P3[partition 2]
  end

  subgraph Group["Consumer group: recommender"]
    W1[consumer 1]
    W2[consumer 2]
  end

  P1 --> W1
  P2 --> W1
  P3 --> W2
```

Brokers scale a topic by splitting it into **partitions** (segments). Within a partition, order is preserved; across partitions it is not. A **consumer group** splits partitions among its members for parallel processing — but if you read in groups, you trade global order for throughput.

## The full journey of one event

```mermaid
sequenceDiagram
  participant P as Checkout service
  participant B as Broker
  participant C as Email consumer
  participant S as Email API

  P->>B: publish order.placed (key=order-42)
  B->>B: append to partition by key
  C->>B: poll (groupId=emailer)
  B-->>C: event + offset 481
  C->>S: send confirmation email
  C->>C: persist processed id order-42
  C->>B: commit offset 481
```

Note the guard: the consumer **commits the offset only after the side effect and its idempotency marker are persisted**. Crash between send and commit → redelivery → the `order-42` dedupe marker prevents the second email.

## Design questions that decide everything

| Question | Trade-off it exposes |
| --- | --- |
| One consumer or many consumers per topic? | Queue vs pub/sub semantics |
| Required ordering across all events or per key? | Partitioning strategy |
| Read-again or read-once? | Retention, replay, compaction |
| Deadline when a consumer stalls? | Rebalance, dead-letter, lag alerting |
| What happens to a poison event? | When it retries infinitely |

## Tester checklist

- Publish one event and confirm *all* subscribed groups receive it (fan-out), not just one.
- Crash a consumer mid-processing and confirm redelivery plus no duplicate side effect.
- Verify ordering guarantees you actually promised: same-partition ordered, cross-partition not.
- Check consumer lag is visible and alerting exists before queues grow unbounded.
