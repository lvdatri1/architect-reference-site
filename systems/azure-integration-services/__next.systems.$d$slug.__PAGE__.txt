## What this system is

Azure's integration story is a toolkit, not a product: **Service Bus** (enterprise messaging), **Event Grid** (event routing between Azure services), **Event Hubs** (high-throughput stream ingestion), **Logic Apps** (no/low-code orchestration glue), plus **API Management** as the front door. There is no "right" single service — each solves a different delivery-semantics problem, and real systems use several at once.

```mermaid
flowchart LR
  Src[SaaS / line-of-business apps] -->|events| EG[Event Grid]
  Src -->|rare ever| A[Azure functions]
  A -->|messages| SB[Service Bus]
  Comp[Other Azure services] -->|telemetry / events| EH[Event Hubs]
  LOG[Logic Apps - orchestration] --> SB
  LOG --> EG
  APIM[API Management] --> Functions[Functions / App Service]
```

## The four services, and when each wins

| Service | Delivery model | Best for |
| --- | --- | --- |
| **Service Bus** | Ordered queues + topics, at-least-once, TTL, DLQ | Enterprise work queues, durable decoupling, competing consumers |
| **Event Grid** | Pulses events to subscribers, auto-retry, dead-letter | Connecting Azure resources ("blob created → trigger function"), fan-out |
| **Event Hubs** | Massive throughput, partition-keyed, no per-message ack | Telemetry, click-streams, anything with very high event volume |
| **Logic Apps** | Orchestration engine (low-code) | Workflows across systems, human approvals, no-code glue |

The selector rule: **a system that must process a message reliably later = Service Bus; an event Azure itself should react to = Event Grid; a firehose of telemetry = Event Hubs; a multi-step workflow = Logic Apps.** They compose — it's common to receive on Service Bus, route decisions through Logic Apps, and publish results onto Event Grid.

## Service Bus: the durable work horse

```mermaid
sequenceDiagram
  participant P as Producer
  participant Q as Service Bus queue
  participant C1 as Consumer 1
  participant C2 as Consumer 2
  participant DLQ as Dead-letter queue

  P->>Q: send message (+ properties, TTL)
  Q->>C1: "lock" the message
  Q->>C2: competing consumer - one gets it
  C1-->>Q: ack (complete) OR
  C1-->>Q: abandon (redeliver) OR
  C1-->>Q: dead-letter (poison)
  Q->>DLQ: messages past max-delivery / TTL
```

- **Queues & topics**: a queue has one logical consumer pool (competing consumers share work); a topic fans out to many subscriptions, each with its own durable copy.
- **Locking** gives exactly-once-ish *processing*: a consumer gets an exclusive lock, must `complete()` within the lock duration, or the message is retried — never duplicated-in-flight, but at-least-once overall, so handlers stay idempotent.
- **Settle one way**: `complete` (done), `abandon` (redeliver), `defer` (park to peek later), or **dead-letter** for poison messages — the DLQ is where bad payloads go instead of poisoning the queue forever.
- **Ordering caveat**: queues/topics give ordering only per the `session`/partition key you set; safest for meaningful order is a **sessionful** queue where each session id is processed serially.

## Event Grid: the reactive router

```mermaid
flowchart LR
  subgraph Sources
    S1[Blob storage - new blob]
    S2[Container registry - image push]
    S3[Resource group events]
    S4[Custom topics - your apps]
  end
  S1 --> EG[Event Grid topic]
  S2 --> EG
  S3 --> EG
  S4 --> EG
  EG --> D1[Function - process]
  EG --> D2[Logic App - workflow]
  EG --> D3[Service Bus - re-queue]
  EG --> H[Event Hubs - land in stream]
```

The defining trait of Event Grid: it **routes, not stores**. Events are small facts ("a blob appeared"), delivered to matching subscribers with retries and a dead-letter sink, but there's no per-message-audit log like Service Bus. It's the fastest path between Azure resources — trivial to wire `blobCreated → Functions` with no code in the middle.

## Event Hubs: the firehose

Event Hubs is a **streaming ingestion bus**: it mirrors Kafka's partition/offset model so that high-volume producers land events quickly and consumers (Functions, Spark, AKS) read at their own pace. Order is guaranteed per `PartitionKey`. It is not for workload queues (no per-message ack like Service Bus) and not for routing (that's Event Grid) — it's the place *before* processing, where millions of events/sec arrive and get persisted briefly.

## Logic Apps: orchestration without app code

```mermaid
flowchart TB
  T[Trigger - HTTP / schedule / Service Bus] --> C[Condition on the payload]
  C -- yes --> A[Call an API - e.g. ERP, CRM]
  A --> H[Human approval - the workflow pauses]
  H -- approved --> N[Notify + write result]
  H -- rejected --> R[Handle rejection path]
  C -- no --> S[Skip / log]
```

Logic Apps is **control flow, not compute**: it sequences steps (calls, approvals, transforms), persists state, handles retries, and shows you the whole workflow visually. When a process is "send invoice → get finance approval → update ERP → email the submitter", that's a Logic App — because encoding it in a service would be glue, not value.

## Putting it together: a reference shape

```mermaid
flowchart LR
  User[User action] --> APIM[API Management - auth, rate limit]
  APIM --> FA[Function App - validate + enqueue]
  FA -->|message| SB[Service Bus - durable queue]
  SB --> W[Worker - Function - process]
  W -->|outcome event| EG[Event Grid]
  EG --> Notify[Notify service]
  EG --> LOGC[Logic App - follow-up workflow]
```

For most integration-first estates the shape is remarkably consistent: **APIM at the front, Service Bus for durable work, Functions as workers, Event Grid to fan results out, Event Hubs only when there's a true firehose, Logic Apps for the human-step workflows.**

## Tester checklist

- **Delivery semantics drill**: kill a consumer mid-message; verify the message is redelivered (at-least-once) and that the handler's idempotency dedupes the duplicate.
- **Poison message**: send a bad payload repeatedly; confirm it dead-letters, and that the DLQ is inspected and drained on a schedule.
- **Session/order**: with a sessionful queue, insert out-of-order and verify each session id processes serially.
- **Fan-out**: publish one topic message; confirm every subscription received its own durable copy.
- **Event Grid retry**: fail a subscriber endpoint and verify retries + dead-letter sink, and check `deliveryCount`/diagnostics logs.
- **Lock expiry**: set a short lock, process slowly, and confirm `complete()` on an expired lock surfaces as a duplicate/retry the consumer must tolerate.
