Data warehouse and lakehouse architecture

Warehouse vs data lake vs lakehouse: where curated, governed, analytical data lives, how they differ on storage and schema, and the decisions that make one the right home for your data.

Data ArchitectSolution ArchitectCloud EngineerEnterprise Architect#database#cloud#architecture

What this system is

Where does analytical data live? Three architectures answer differently. A warehouse curates data into a governed, queryable store. A data lake keeps raw files at low cost, schema optional. A lakehouse tries to merge them: lake storage cost, warehouse governance and SQL on top. The data architect's job is to pick the right home per data set — not to have one religious position.

The one-paragraph summary: warehouses win on trust, lakes win on cost, lakehouses try to take both. In practice most orgs run both: a lake holds raw and semi-raw data cheaply, and a warehouse/lakehouse curates the governed views people actually query.

The lakehouse mechanism: open table formats

Rendering diagram…

A lakehouse is not "SQL on files" (that's a lake with extra steps and fragile consistency). The table format (Delta Lake, Iceberg, Hudi) adds ACID transactions over object storage: writers commit atomically, readers see a consistent snapshot, and you can time-travel to previous versions. That's what turns cheap lake storage into something you can trust for a report.

What belongs where

Rendering diagram…
  • Warehouse-first: canonical business reporting, finance, anything you answer for in an audit — needs ACID, roles, and lineage now.
  • Lake-first: raw clickstreams, sensor dumps, ML feature exploration — storing everything curated would cost too much and nobody knows the schema yet.
  • Lakehouse pattern: land raw in the lake, then define refined governed tables (via the table format) for the queries that matter — keeping one copy of the data instead of duplicating it into a warehouse.
  • The universal law: never let analysts query production OLTP directly; everything analytical flows through curated copies.

The failure modes a data architect owns

  • The data swamp: a lake without governance is a lake where nobody trusts the data — the fix is catalogs, owners, and at least a bronze/silver/gold (raw/refined/aggregated) layer naming.
  • Two sources of truth: a warehouse and a lake storing the same fact differently, reconciled by nobody — pick per-data-set ownership and a single definition per metric.
  • Schema drift: source columns change and the pipeline breaks silently; the lakehouse's schema-evolution rules and validation are what catch it.
  • Buying only one answer: choosing lakehouse and storing nothing governed, or warehouse and paying to store gigabytes nobody queries.

Tester checklist

  • Verify ACID: read the table while a load is mid-write — readers must see either the old or the new snapshot, never a half-written middle.
  • Enable time travel ability: query the table as of yesterday and confirm the row counts match that version exactly.
  • Check governance: a member of the BI group can not read the raw lake's sensitive columns unless granted; readers see a defined view, not the files.
  • Confirm pipeline schema drift detection: a renamed source column either transforms or explicitly fails the layer, not silently corrupts.
  • Cost test: query the same report from warehouse vs lakehouse and compare latency and scan cost per run — know what you're paying for curation.
